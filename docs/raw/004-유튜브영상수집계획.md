# 유튜브 영상 수집 — 구현 계획

**2026-08-28 구현 완료.** 실측과 구현 결과를 반영해 갱신했다 — 3중 방어 10/10, 단위 테스트 46건 통과, 마이그레이션 `0002` 적용. 남은 것은 `YOUTUBE_API_KEY` 발급뿐이다.

## Context

로또·복권 관련 유튜브 영상의 **메타데이터만** 수집해 사이트에 목록으로 걸고, 전용 페이지에서 공식 임베드 플레이어로 재생시킨다. 영상 파일은 내려받지 않는다. 쇼츠와 일반 동영상을 구분하고 중복 수집을 막는다.

지금 사이트에는 뉴스(`lotto_news`)가 있고 매시간 수집된다. 영상은 그보다 체류시간이 길고 검색 유입에 유리하지만, **뉴스와 같은 방식으로 만들 수 없다.** 유튜브 API 의 쿼터 구조와 데이터 보관 정책이 네이버 검색 API 와 근본적으로 다르기 때문이다. 이 문서의 설계 대부분은 그 차이에서 파생된다.

이 계획은 **워커 세션의 범위**만 다룬다. 백엔드 API 와 프론트 화면은 다른 세션이 만들며, 넘길 내용은 코드가 아니라 `docs/wiki/10-contracts/` 의 계약으로 전달한다.

### 쿼터 — 뉴스와 완전히 다르다

**`search.list` 는 2026-06-01 부터 자체 쿼터 버킷이고 하루 100회가 상한이다.** 10,000 유닛과 별개다. 네이버 검색(25,000회/일, 우리는 0.2% 사용)과 자릿수가 다르다.

- `videos.list` · `channels.list` · `playlistItems.list` 는 각 1 unit, 공통 10,000 유닛 버킷
- **`videos.list` 는 `id` 에 50개를 콤마로 묶어 1 unit** 에 조회한다

- `maxResults` 최대 50

**뉴스처럼 매시간 돌릴 수 없다.** 검색어 4개 × 24회 = 96회로 상한을 스치고, 429 재시도 한 번에 터진다.

## 설계

### 잡을 셋으로 나눈다

| `job_nm` | 하는 일 | 크론 (KST) | 쿼터 버킷 |
|---|---|---|---|
| `video_channel` | 화이트리스트 채널 신규 영상 수집 | `0 */6 * * *;20,50 21 * * sat;20 22 * * sat` | 유닛만 (약 33/회) |
| `video_search` | 검색 보조 수집 | `15 */4 * * *` | **search 100 버킷** 4회/회 |
| `video_refresh` | 갱신·만료 삭제 | `30 4 * * *` | 유닛만 (2~10/일) |

**왜 합치지 않는가.**

- **쿼터 버킷이 다르다.** `video_search` 만 100회 버킷을 쓴다. 합치면 검색 쿼터가 마른 날 채널 수집까지 멈춘다.
- **락이 하나가 된다.** 이 프로젝트가 전역 락을 버리고 잡별 락으로 간 이유와 같다. 채널 30개를 도는 동안 검색이 대기할 이유가 없다.
- **실패의 의미가 다르다.** 수집 실패는 "새 영상이 안 들어왔다"(무해)지만, **갱신 실패는 "30일 초과 데이터가 남아 있다"(정책 위반)** 다. 같은 `job_nm` 이면 이력에서 구분되지 않는다.
- **`collected_cnt` 의 의미가 다르다.** 갱신 잡의 그 숫자는 신규 행이 아니라 갱신+삭제 행수다. 섞으면 이력이 거짓말을 한다.

**이름이 `youtube_*` 가 아니라 `video_*` 인 이유**: 테이블이 `lotto_video` 이고 소스는 `provider_nm` 컬럼이 표현한다. `news` 잡 + `provider_nm='naver'` 와 같은 구조다. 잡 이름에 소스를 박으면 다른 provider 가 붙을 때 이름이 거짓이 된다.

### 크론 주기의 근거

**채널 = 6시간 + 토요일 야간 3회.** 화이트리스트 채널의 업로드는 하루 0~3건이다. 매시간이면 24번 중 21번이 완전히 동일한 응답이다. 24시간이면 토요일 추첨 영상이 일요일에야 들어온다. 토요일 21:20·21:50·22:20 을 더하는 것은 `lotto` 잡이 20:40·20:50·21:00 세 번 도는 것과 **같은 논리**다 — 결과가 소스에 반영될 시간을 여러 번 노린다. 추첨은 20:35~20:45 이고 실황·결과 영상은 21:00~22:30 에 몰린다.

**검색 = 4시간마다.** 4질의 × 6회 = **24회 / 100**. 3시간(32회)도 예산 안이지만 여유를 남긴다 — 429 백오프가 최악 3배로 튀면 72회이고 수동 트리거가 겹칠 수 있다. 분을 `15` 로 어긋내는 것은 정시의 채널 잡과 `videos.list` 가 겹치지 않게 하기 위해서다(락이 잡별이라 동시 실행된다).

**갱신 = 매일 04:30.** 쿼터 리셋이 태평양시 자정(KST 16~17시)이라 새벽은 잔여 쿼터가 가장 넉넉하다.

**총 소비: 평시 약 145 units/일(10,000 의 1.5%), 토요일 약 250. search 버킷 24/100.**

### 신규 감지에 RSS 를 쓰지 않는다 (1단계 기준)

채널 RSS(`feeds/videos.xml?channel_id=`)는 쿼터를 전혀 안 쓰고 **`/shorts/` 링크로 쇼츠를 확실히 알려준다.** 실측으로 확인했다. 그런데도 1단계에서는 쓰지 않는다.

1. **미문서화 기능이다.** 이 프로젝트는 이미 `dhlottery` 공식 API 차단을 겪고 네이버 위젯 파싱으로 우회한 이력이 있다. 그 비용을 아는 프로젝트가 두 번째로 같은 선택을 하지 않는다.
2. **약관 적용 여부가 불명확하다.** 30일 정책과 `madeForKids` 의무를 성실히 지키는 설계가 수집 입구에서 회색지대를 쓰면 정책 준수 주장 전체가 약해진다.
3. **영상 길이를 주지 않는다.** 어차피 `videos.list` 를 2단계로 불러야 하므로, RSS 가 아끼는 것은 채널당 1 unit 뿐이다.
4. **최신 15~20건 상한에 pageToken 이 없다.** `playlistItems.list` 는 `maxResults=50` + 페이징이라 초기 백필이 가능하다.

**대신 `channels.list?part=contentDetails` → `playlistItems.list` 를 쓴다.** `UC…`→`UU…` 치환은 관례일 뿐 문서화된 규칙이 아니라 쓰지 않는다 — RSS 를 미문서화라고 거부하면서 그 치환을 쓰면 일관성이 없다. `channels.list` 는 채널 50개를 콤마로 묶어 1 unit 이다.

**단, 이 결정은 재검토 대상이다.** 쇼츠 오분류율을 실측한 뒤(아래 검증 절차) 30% 를 넘으면 RSS 의 `/shorts/` 링크를 **보조 신호로만** 쓰는 안을 다시 검토한다. 그때는 위키에 판단을 기록하고 결정한다.

### `lotto_video` 테이블

| 문제 | 결정 | 근거 |
|---|---|---|
| 유튜브 영상 ID(11자 문자열) | **새 접미어 `_key`** = 외부 시스템이 발급한 문자열 식별자, `text` → `provider_video_key` | `_id` 는 bigint 대리키 전용이라 재정의하면 `news_id`·`job_log_id` 와 의미가 갈린다. `_nm` 은 사람이 읽는 이름이지 식별자가 아니다. `_cd` 는 값 집합이 닫힌 코드 전용인데 영상 ID 는 열려 있다 |
| 재생시간 | **새 접미어 `_sec`** = 초 단위 길이, `integer` → `duration_sec` | 기간은 시각(`_dttm`)도 수량(`_cnt`)도 아니다. `interval` 을 안 쓰는 것은 "3분 이하" 필터·정렬이 integer 로 단순하고, 클라이언트마다 직렬화가 달라 API 응답에서 사고가 나기 때문 |
| 조회수 | `_cnt` 이지만 **bigint** → `view_cnt` | 유튜브 조회수는 int4 상한(21억)을 넘는다. 표준 문서에 단서 한 줄 추가 |

> **대안 B** — `_key` 추가가 거부되면 `video_url text` 를 `https://www.youtube.com/watch?v={id}` 로 정규화해 저장하고 UNIQUE 를 건다. 새 접미어가 없고 `lotto_news.link_url` 과 동형이다. 대가는 11자 키가 필요할 때마다 파싱해야 하고, `youtu.be/`·`/shorts/` 정규화가 조용히 틀리면 중복이 샌다는 것. **주안(`provider_video_key`)을 권한다.**

`_yn`/boolean 접미어가 표준에 없으므로 3-값은 전부 `_cd` + CHECK 로 표현한다. 결과적으로 **"아직 확인 못 했다"가 스키마에 드러나** 오히려 낫다 — boolean NULL 은 "false"와 "모름"을 사람이 헷갈린다.

```sql
CREATE TABLE IF NOT EXISTS lotto_video (
    video_id                bigint      GENERATED ALWAYS AS IDENTITY,
    provider_nm             text        NOT NULL DEFAULT 'youtube',
    provider_video_key      text        NOT NULL,
    provider_channel_key    text        NOT NULL,
    channel_nm              text,
    title_nm                text        NOT NULL,
    summary_desc            text,
    thumbnail_url           text,
    published_dttm          timestamptz NOT NULL,
    duration_sec            integer,
    view_cnt                bigint,
    shorts_estimate_cd      text        NOT NULL DEFAULT 'unknown',
    shorts_basis_desc       text,
    made_for_kids_cd        text        NOT NULL DEFAULT 'unknown',
    embeddable_cd           text        NOT NULL DEFAULT 'unknown',
    privacy_status_cd       text        NOT NULL DEFAULT 'unknown',
    discovery_cd            text        NOT NULL,
    round_no                integer,
    game_cd                 text        NOT NULL DEFAULT 'unknown',
    keyword_list            text[],
    collected_dttm          timestamptz NOT NULL DEFAULT now(),
    refreshed_dttm          timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT pk_lotto_video PRIMARY KEY (video_id),
    CONSTRAINT uk_lotto_video_provider_key UNIQUE (provider_nm, provider_video_key),
    CONSTRAINT ck_lotto_video_provider_key CHECK (provider_video_key <> ''),
    CONSTRAINT ck_lotto_video_shorts_estimate
        CHECK (shorts_estimate_cd IN ('likely', 'unlikely', 'unknown')),
    CONSTRAINT ck_lotto_video_made_for_kids
        CHECK (made_for_kids_cd IN ('yes', 'no', 'unknown')),
    CONSTRAINT ck_lotto_video_embeddable
        CHECK (embeddable_cd IN ('yes', 'no', 'unknown')),
    CONSTRAINT ck_lotto_video_privacy_status
        CHECK (privacy_status_cd IN ('public', 'unlisted', 'private', 'unknown')),
    CONSTRAINT ck_lotto_video_discovery
        CHECK (discovery_cd IN ('channel', 'search')),
    CONSTRAINT ck_lotto_video_game
        CHECK (game_cd IN ('lotto', 'pension', 'unknown')),
    CONSTRAINT ck_lotto_video_round_no
        CHECK (round_no IS NULL OR round_no > 0),
    CONSTRAINT ck_lotto_video_duration_sec
        CHECK (duration_sec IS NULL OR duration_sec >= 0),
    CONSTRAINT ck_lotto_video_view_cnt
        CHECK (view_cnt IS NULL OR view_cnt >= 0)
);

CREATE INDEX IF NOT EXISTS ix_lotto_video_published_dttm
    ON lotto_video (published_dttm DESC);
CREATE INDEX IF NOT EXISTS ix_lotto_video_refreshed_dttm
    ON lotto_video (refreshed_dttm);
CREATE INDEX IF NOT EXISTS ix_lotto_video_shorts_published
    ON lotto_video (shorts_estimate_cd, published_dttm DESC);

-- 회차별 영상 조회(상세 페이지에서 "이 회차의 다른 영상")
CREATE INDEX IF NOT EXISTS ix_lotto_video_game_round
    ON lotto_video (game_cd, round_no)
    WHERE round_no IS NOT NULL;
```

전 컬럼에 `COMMENT ON COLUMN` 을 단다(`lotto_news` 와 같은 규약). 핵심 주석은 이렇다.

- `provider_video_key` — "`_id` 는 대리키 전용이라 `_key` 접미어를 쓴다"
- `title_nm` — "원문 그대로. **변조하지 않는다 — 정책 위반이다**"
- `shorts_estimate_cd` — "**확정이 아니다.** 공식 판별 API 필드가 없고 원본 화면비를 얻을 수 없어 재생시간·게시일만으로 추정한다"
- `shorts_basis_desc` — "추정 근거. 판정 규칙이 바뀌었을 때 기존 행이 어떤 규칙으로 매겨졌는지 알기 위해 남긴다"
- `refreshed_dttm` — "**30일 정책의 시계다.** 값이 하나도 안 바뀌어도 확인만 하면 갱신한다"
- `discovery_cd` — "검색 유래는 신뢰도가 낮아 표시 우선순위를 낮춘다. 검색으로 먼저 발견된 뒤 화이트리스트 채널로 확인되면 `channel` 로 승격"
- `round_no` — "제목에서 파싱한 회차. **FK 를 걸지 않는다** — 아직 추첨 전인 회차를 예고하는 영상이 있고, 연금복권 330회와 로또 330회는 다른 것이라 번호만으로 참조 대상이 정해지지 않는다. 파싱 실패 시 NULL"
- `game_cd` — "회차가 어느 게임의 것인지(lotto/pension/unknown). `round_no` 는 이 값과 짝을 이뤄야만 의미가 있다"

**길이 11 을 CHECK 하지 않는다.** 11자는 YouTube 의 현재 규칙일 뿐이고 provider 가 늘면 달라진다. 형식 검증은 소스 클라이언트의 일이다.

**`link_url` 컬럼을 두지 않는다.** `provider_video_key` 에서 파생 가능하고, 파생값을 저장하면 두 곳이 어긋난다. 조립은 백엔드·프론트의 일이다.

**채널 화이트리스트를 테이블로 두지 않는다.** 편집 수단(관리자 UI)이 필요해지는데 워커는 관리자 UI 를 만들지 않는다. 뉴스 검색어·제외어가 env 인 것과 일관되게 `YOUTUBE_CHANNEL_KEY_LIST` 로 주입한다.

### 중복 제거 — 다섯 겹

1. **실행 내** — `merged.setdefault(provider_video_key, item)`. 질의 4개가 같은 영상을 물어오면 한 번만 INSERT 되고 `keyword_list` 에 매칭 질의어가 합집합으로 들어간다. 따로 INSERT 하면 두 번째가 `DO NOTHING` 으로 죽어 키워드가 하나만 남는다 — 뉴스가 이미 겪은 함정이다.

2. **`videos.list` 호출 전 기존 키 제거** — 뉴스에는 없는 단계이고 **쿼터 때문에 필수다.** `playlistItems.list` 는 매번 최신 50개를 통째로 준다. 이 필터가 없으면 6시간마다 채널 30개 × 50건을 다시 부르고, `video_refresh` 의 일과 겹쳐 갱신 주기를 제어할 수 없게 된다.

3. **실행 간(DB)** — `uk_lotto_video_provider_key` + `ON CONFLICT DO NOTHING`.

4. **화이트리스트 ↔ 검색 교차** — 같은 UNIQUE 가 잡는다. 다만 `video_channel` 은 조건부 승격을 한다.

   ```sql
   ON CONFLICT (provider_nm, provider_video_key) DO UPDATE
      SET discovery_cd = 'channel', channel_nm = EXCLUDED.channel_nm
    WHERE lotto_video.discovery_cd = 'search'
   RETURNING (xmax = 0) AS inserted
   ```

   **함정**: `DO UPDATE` 를 쓰면 `cur.rowcount` 로 신규 건수를 셀 수 없다. 승격도 1로 세어져 `collected_cnt` 가 부풀고 이력이 거짓말을 한다. `RETURNING (xmax = 0)` 으로 삽입인지 갱신인지 가려 **삽입만** `progress.collected` 에 더한다.

5. **★ 같은 콘텐츠의 쇼츠판/롱폼판** — 실측에서 발견한 것이다. 동행복권은 같은 영상을 쇼츠와 롱폼 두 벌로 올린다(`황금손의 기부 챌린지 제1237회` → 08-18 watch / 08-19 shorts). 영상 ID 가 달라 위 네 겹이 전부 통과한다. **제목 정규화 기준으로 같은 채널·7일 이내·동일 제목이면 롱폼을 우선하고 쇼츠판은 담지 않는다.** 이 규칙은 env 토글(`YOUTUBE_DEDUPE_SAME_TITLE`)로 끌 수 있게 한다 — 실측 없이 도입하는 규칙이라 틀릴 수 있다.

### 필터 파이프라인

**싼 것 → 비싼 것 → 쿼터 쓰는 것** 순서. 뉴스의 `_is_on_topic` → `_is_fresh` 를 확장한 것이고, 각 단계마다 `조회 N → …제외 M` 로그를 남긴다.

| # | 단계 | 판정 | 결과 |
|---|---|---|---|
| 0 | API 사전 필터 | `type=video`, `regionCode=KR`, `relevanceLanguage=ko`, `order=date`, `publishedAfter`, `videoEmbeddable=true`, `safeSearch=moderate` | 검색 경로만 |
| 1 | 채널 차단 | `YOUTUBE_BLOCK_CHANNEL_KEY_LIST` | 버림 |
| 2 | **채널명 대조** | 저장된 채널명과 응답의 채널명이 다르면 경고 + 그 채널 건너뜀 | 채널 경로만 |
| 3 | 주제 적합성 | 제목에 질의어가 없으면 버림 + `YOUTUBE_EXCLUDE_KEYWORDS` | 버림 |
| 4 | **금지 표현 — 규칙** | `YOUTUBE_FORBIDDEN_KEYWORDS` (제목 **+ 채널명**) | 버림 |
| 4-b | **금지 표현 — LLM 보조** | 규칙을 통과한 것만 `gpt-5-nano` 에 배치로 물어 판정. **화이트리스트 채널은 건너뛴다** | 버림 |
| 5 | 신선도 | KST 변환 후 날짜 비교. 미래·NULL 버림 | 버림 |
| 6 | 기존 키 제거 | DB 선조회 | 조회 대상 제외 |
| 7 | **`videos.list` 2단계** | 50개씩, `part=snippet,contentDetails,statistics,status` | — |
| 8 | 표시 가능성 | `privacyStatus=='public'` AND `embeddable` AND `madeForKids==False` | 버림 |
| 9 | 쇼츠 추정 | **필터가 아니라 분류.** 버리지 않는다 | `shorts_estimate_cd` |
| 9-b | **회차 파싱** | 제목에서 `제?(\d{3,4})회` 추출 + 게임 판정. **분류이지 필터가 아니다** | `round_no`·`game_cd` |
| 10 | 제목 중복 | 같은 채널·7일 이내 동일 제목이면 롱폼 우선 | 버림 |
| 11 | UPSERT | — | `progress.collected += 삽입건수` |

**금지 표현 필터를 4번에 두는 이유 셋.** ① 문자열 검사라 싸다. ② `videos.list` 를 부르기 전이라 쿼터를 아낀다. ③ **DB 에 한 번 들어가면 다시 판단할 기회가 없다** — UNIQUE 때문에 재수집 시 `DO NOTHING` 으로 죽는다.

**주제 필터와 금지 표현 필터를 분리하는 이유.** 뉴스는 제외어가 한 종류였다("로또 청약" = 주제 밖). 여기는 두 종류다 — 주제 밖(`청약`·`부동산`·`공모주`)과 **정책 위반**(`예상번호`·`고확률`·`필승`·`명당번호`). 섞으면 로그에서 **정책 때문에 몇 건이 걸렸는지 셀 수 없다.** 그 통과율은 측정해야 하는 값이다 — 애드센스 대비 근거이고, 화이트리스트 채널이 변질됐는지 알아채는 신호다.

**낱말은 코드에 박지 않는다.** env 기본값에만 두고 `@property` 로 파싱한다(`news_exclude_keywords` 와 같은 쉼표 규약).

**화이트리스트 경로에도 건다.** 화이트리스트는 발견 경로일 뿐 면제가 아니다 — 오늘 통계 해설 채널이 내일 예상번호 채널이 된다.

**쇼츠 추정 규칙 (초기)**

```
duration_sec is None                              → ('unknown',  'duration 파싱 실패')
<= 180초 and published >= 2024-10-15              → ('likely',   'duration<=180s,published>=2024-10-15')
<= 180초 and published <  2024-10-15              → ('unknown',  'duration<=180s,published<2024-10-15')
그 외                                              → ('unlikely', 'duration>180s')
```

세로 화면비 조건을 **검사할 수 없다.** 이것이 부정확성의 유일한 원천이고 컬럼 COMMENT 에 그대로 적는다.

**`madeForKids=true` 와 `unknown` 은 버린다.** 담고 표시만 막을 수도 있지만, 담으면 30일 갱신 쿼터를 영원히 치른다. 로또 콘텐츠에 아동 대상 영상이 있을 리 없어 손실이 0에 가깝다. `unknown` 을 버리는 것은 정책이 조회 의무를 지우는데 결과를 모르는 채로 임베드할 수 없기 때문이다.

### 30일 갱신 파이프라인

**실행 순서가 정책을 보장한다.**

```
1. 하드 만료 삭제 (API 호출 없음)          ← ★ enabled 가드보다 먼저
2. enabled 가드 — 키가 없으면 RuntimeError
3. 보관 기간 초과 삭제
4. 갱신 대상 선정 → 50개씩 videos.list → UPDATE / DELETE
```

**1번이 2번보다 먼저인 이유**: 갱신에 성공해야만 삭제된다면 **API 장애가 곧 정책 위반**이 된다. 키가 만료됐든 Google 이 죽었든 30일 제한은 지켜져야 한다. 순서 하나가 정책 준수를 코드가 아니라 구조로 보장한다. 이 근거를 함수 주석에 남긴다 — 설명이 없으면 다음 사람이 "버그"로 보고 순서를 바꾼다.

```sql
-- 1) 하드 만료 — 30일을 넘긴 행은 무조건 삭제
DELETE FROM lotto_video
 WHERE refreshed_dttm < now() - make_interval(days => 30);

-- 3) 보관 기간 초과 — 목록에 노출되지도 않는 영상은 갱신하지 않고 지운다
DELETE FROM lotto_video
 WHERE published_dttm < now() - make_interval(days => 60);

-- 4) 갱신 대상 — 가장 오래 확인 안 된 것부터
SELECT provider_video_key FROM lotto_video
 WHERE provider_nm = %(provider_nm)s
   AND refreshed_dttm < now() - make_interval(days => 25)
 ORDER BY refreshed_dttm LIMIT 500;
```

**25일인 이유**: 30으로 두면 정확히 30일째에만 여유가 없어 잡이 하루 실패하면 즉시 위반이다. 5일 버퍼는 "5일 연속 실패해도 안전"을 뜻한다.

**500행 상한**: `videos.list` 10 units. 상한에 걸리면 경고 로그를 남긴다 — 유입이 갱신 능력을 넘었다는 신호다.

**응답에서 영상이 사라졌을 때**

```
요청 50개 → 응답 N개
  N == 0 이고 요청 > 1  →  ★ 삭제하지 않는다. 경고만 남기고 배치를 건너뛴다.
                           50개가 동시에 사라질 확률보다 요청/응답이 이상할 확률이 높다.
                           안전판이 없으면 API 스펙 변경 한 번에 테이블이 통째로 비워진다.
  N >  0                →  요청에 있었으나 응답에 없는 키 = 삭제·비공개 → DELETE
```

**HTTP 오류와 "응답에 없음"을 반드시 구분한다.** 요청 자체가 실패했으면 아무것도 지우지 않고 예외를 올린다.

갱신 후 표시 가능성을 **다시** 판정한다. 비공개로 바뀌었거나 임베드가 막혔거나 `madeForKids` 가 켜졌으면 삭제한다.

`published_dttm`·`discovery_cd`·`collected_dttm` 은 갱신하지 않는다(게시 시각은 변하지 않고, 발견 경로는 역사다). `shorts_estimate_cd` 는 매번 재계산하므로, 추정 규칙을 고치면 25일 안에 전 행이 새 규칙으로 재판정된다 — 세 잡이 같은 함수를 공유해야 하는 이유다.

**쿼터 소모**: 보관 행수 V, 25일 주기 → 하루 `V/1250` units. `RETAIN_DAYS=60` 이면 V ≈ 1,200~2,400행 → **하루 2~3 units.** 무시해도 되는 수준이다.

### 검색 쿼터 가드

`search.list` 상한은 100이고 워커는 정확한 소비량을 알 수 없다(Google 측 카운터가 정본). 두 겹으로 막는다.

- **실행당 상한** `YOUTUBE_SEARCH_MAX_CALL_PER_RUN`(기본 4) — 질의를 늘려도 한 실행이 이를 넘지 않는다
- **일일 근사 가드** — 잡 시작 시 `collect_job_log` 에서 오늘의 `video_search` 실행 횟수를 세고, `횟수 × MAX_CALL_PER_RUN >= YOUTUBE_SEARCH_DAILY_BUDGET`(기본 60)이면 **호출 없이 0건 success 로 종료.** `failed` 가 아닌 이유는 쿼터 보호가 오류가 아니기 때문이다

이것이 **추정**임을 로그와 문서에 명시한다. 정본은 Cloud Console 의 Quotas 페이지다.

### ★ API 키 유출 방지

Google API 의 표준 인증은 `?key=` **쿼리스트링**이다. httpx 예외 메시지에는 request URL 이 실리고, `naver_news.py` 패턴대로 `f"... {last_exc}"` 로 감싸면 그것이 `collect_job_log.error_desc` 에 저장되어 **DB 와 로그에 API 키가 평문으로 남는다.** `alembic.ini` 가 `app_writer` 비밀번호를 뱉었던 사고(2026-07-09, 실제로 비번을 교체해야 했다)와 같은 형태다.

- `X-goog-api-key` **헤더**로 보낸다 (Google 공식 지원)
- 예외를 그대로 올리지 않는다 — `type(exc).__name__` 과 status_code 만 싣는다
- Cloud Console 에서 키에 **API 제한**(YouTube Data API v3 만)을 건다. IP 제한은 서버 IP 가 바뀔 수 있어 걸지 않는다

**403 이 두 의미다.** `quotaExceeded`(그날은 회복 불가, 백오프 무의미) vs `keyInvalid`/`accessNotConfigured`(영구). `error.errors[].reason` 으로 가른다. 둘 다 즉시 포기하되 메시지가 달라야 사람이 대응할 수 있다.

## 금지 표현 LLM 보조 판정

규칙 기반 제외어는 **목록에 없는 신조어를 통과시킨다.**

```
목록에 있음:  "예상번호" "고확률" "필승"        → 걸림
목록에 없음:  "필출 2수" "고정수 5" "가지치기"  → 통과 ✗
```

로또 유튜브는 이런 표현이 계속 새로 생기는 영역이라 목록 유지보수가 따라가지 못한다. 그래서 규칙을 통과한 것만 LLM 에 한 번 더 묻는다.

### 설계 원칙

- **생성이 아니라 분류다.** 제목·채널명을 주고 "예상번호·당첨 예측을 제공하는가"를 판정만 시킨다. 텍스트를 만들지 않으므로 환각이 결과물에 섞이지 않고, 오답이 나와도 **영상 하나가 안 들어오는 것**으로 끝난다.
- **규칙 필터 뒤에 둔다.** 규칙이 이미 잡은 것을 LLM 에 물을 이유가 없다. 호출 수와 비용이 줄고, 규칙이 정본이라는 관계가 유지된다.
- **화이트리스트 채널은 건너뛴다.** 동행복권·MBC 공식 채널의 제목은 `제1238회 당첨번호` 형식이라 판정할 것이 없다. 판정 대상은 검색 유래(하루 5~15건)뿐이다.
- **LLM 이 죽어도 수집은 계속된다.** API 실패·타임아웃 시 **규칙 필터 결과를 그대로 채택하고 경고만 남긴다.** 잡을 실패시키지 않는다 — 보조 판정이 주 파이프라인을 멈추면 안 된다.
- **배치로 묶는다.** 20건을 한 요청에 넣어 시스템 프롬프트를 한 번만 낸다.

### 모델과 비용

`gpt-5-nano` — 입력 $0.05/1M, 출력 $0.40/1M (2026-08-28 공식 가격).

| 규모 | 월 비용 |
|---|---|
| 하루 18건 (예상) | **$0.006** |
| 하루 100건 (10배) | $0.032 |

**월 10원 안팎이라 비용은 판단 요소가 아니다.** 실제 비용은 실패 지점이 하나 늘어난다는 것이고, 위의 "LLM 이 죽어도 수집은 계속된다" 가 그 대가를 갚는 장치다.

Batch API 의 50% 할인은 **쓰지 않는다** — 24시간 비동기 완료 방식이라 수집 잡의 즉시 판정과 맞지 않는다.

### 프롬프트 규약

시스템 프롬프트에 **금지 표현 목록을 그대로 넣지 않는다.** 넣으면 규칙 필터와 중복이고, LLM 에게 기대하는 것은 목록 매칭이 아니라 **목록에 없는 것의 판정**이기 때문이다. 대신 판정 기준을 서술한다 — "이 영상이 다음 회차의 당첨번호를 예측·추천·제공하는 성격인가".

응답은 JSON 배열로 강제하고, **파싱에 실패하면 전건을 통과(규칙 결과 채택)로 처리한다.** 판정 실패가 대량 차단으로 이어지면 안 된다.

## 전용 페이지의 자체 콘텐츠 — 회차 연결

영상만 나열된 페이지는 III.G.1.d 의 "독립적 가치" 요건을 못 맞추고, 애드센스에서도 낮은 가치 콘텐츠로 분류된다. 그래서 영상 아래에 **우리 데이터**를 붙인다. 새로 만들 것은 거의 없다 — 당첨번호 볼, 통계 계산, 회차 조회가 이미 있다.

### 왜 회차인가

화이트리스트 두 채널의 제목이 정형화돼 있어 **회차 번호를 파싱할 수 있다.** 실측 제목이다.

```
로또6/45 제1238회 당첨번호 2026년 08월 22일        → 1238 / lotto
MBC 생방송 행복드림 로또 6/45 _ 1238회             → 1238 / lotto
[로또 1238회] 당첨 번호는?!                        → 1238 / lotto
연금복권 제330회 당첨번호 2026년 08월 27일          → 330  / pension
황금손의 기부 챌린지｜제1237회 배우 '오영실'         → 1237 / lotto
```

회차를 알면 `lotto_draw` 와 이어지고, **유튜브 데이터를 통째로 걷어내도 "1238회차 당첨번호·당첨금·통계"가 남는다.** 조항이 요구하는 것이 정확히 이것이다. 덤으로 "1238회 당첨번호"는 토요일 밤 검색량이 폭발하는 키워드다.

### 파싱 규칙

제목에서 `제?(\d{3,4})회` 를 추출하고, 같은 제목에 '연금'이 있으면 `pension`, '로또'가 있으면 `lotto` 로 판정한다. **둘 다 없거나 둘 다 있으면 `unknown` 으로 두고 관련 콘텐츠를 붙이지 않는다** — 틀린 회차를 붙이는 것보다 안 붙이는 편이 낫다.

`round_no` 에 FK 를 걸지 않는 이유는 DDL 주석에 적었다(추첨 전 회차 예고 영상 + 게임별 회차 번호 충돌).

### 페이지 구성 (프론트 계약)

| 순서 | 블록 | 출처 |
|---|---|---|
| 1 | 임베드 플레이어 | — |
| 2 | 그 회차 당첨번호 (볼 6 + 보너스, 추첨일) | `lotto_draw` |
| 3 | 그 회차 당첨 정보 (1등 당첨금·당첨자 수·총 판매액) | `lotto_draw` |
| 4 | 그 회차 번호 구성 (합계·홀짝·구간 분포·연속번호) | 백엔드 계산 |
| 5 | **광고** | — |
| 6 | 관련 뉴스 (같은 회차 언급) | `lotto_news` |
| 7 | 인접 회차 영상 | `lotto_video` |
| 8 | 가이드·FAQ | 정적 |

광고가 중간에 오면 플레이어와 자연히 떨어지고 위아래를 실제 콘텐츠가 감싼다. 오클릭 우려도 함께 해소된다.

`game_cd='unknown'` 이거나 `round_no IS NULL` 인 영상은 2~4·6·7 블록을 **생략한다.** 그런 영상만 있는 페이지는 애초에 독립적 가치가 없으므로, 그 경우 광고도 노출하지 않는 것이 안전하다.

### 하지 않는 것

- **자동 생성 문장을 찍어내지 않는다.** "이 영상은 제1238회 추첨을 다루고 있습니다…" 같은 템플릿 문단이 영상마다 복제되면 애드센스가 낮은 가치 콘텐츠로 분류한다. 구조화된 사실 데이터를 표와 볼로 보여준다 — 통계 페이지가 이미 그 방식이다
- **"이 영상의 예측이 맞았는지" 류를 만들지 않는다.** 예상번호 채널을 제외한 결정과 같은 이유이고 금지 표현 정책에 정면으로 걸린다

## 다른 세션에 넘길 계약

### 백엔드

1. `lotto_video` 읽기 전용. **마이그레이션 후 `pg_default_acl` 로 `app_reader` 권한을 확인할 것** — db-schema 의 "새 테이블이 생기면 백엔드가 죽는다" 함정이 여기 걸린다
2. **필수 WHERE 절** — `privacy_status_cd='public' AND embeddable_cd='yes' AND made_for_kids_cd='no'`. 워커가 이미 걸렀지만 갱신 주기(25일) 사이에 상태가 바뀐 행이 있을 수 있다. 백엔드가 다시 건다
3. 엔드포인트 — `GET /api/videos?kind=normal|shorts&page=&size=`. 페이지네이션 봉투 규약 그대로. `kind=shorts` → `'likely'`, `normal` → `'unlikely'`, **`'unknown'` 은 어느 목록에도 넣지 않는다**
4. **응답 캐시 TTL 상한 24시간.** 30일 정책 때문이다. 백엔드가 오래 캐시하면 **백엔드가 정책 위반의 주체가 된다**
5. 매핑 — `id ← video_id` · `video_key ← provider_video_key` · `title ← title_nm` · `channel ← channel_nm` · `thumbnail ← thumbnail_url` · `published_at ← published_dttm` · `duration_sec ← duration_sec` · `views ← view_cnt` · `shorts_hint ← shorts_estimate_cd` · `round ← round_no` · `game ← game_cd` · `keywords ← keyword_list`
6. **`shorts_estimate_cd` 를 `is_shorts` boolean 으로 바꾸지 않는다** — 추정이 확정으로 둔갑한다
7. `made_for_kids_cd`·`embeddable_cd`·`privacy_status_cd` 는 **응답에 내보내지 않는다.** WHERE 절 재료일 뿐이다
8. 정렬 안정성 — `ORDER BY published_dttm DESC NULLS LAST, video_id DESC`
9. **회차 연결** — `GET /api/videos/{id}` 는 `round_no`·`game_cd` 가 있으면 그 회차의 당첨 정보를 함께 담거나, 프론트가 기존 회차 API 를 따로 부르게 한다(둘 중 어느 쪽이든 백엔드 판단). **`game_cd='lotto'` 일 때만 `lotto_draw` 와 조인한다** — 연금복권 330회를 로또 330회로 조인하면 조용히 틀린 당첨번호가 화면에 뜬다. `round_no` 가 아직 추첨 전 회차일 수 있으므로 조인 결과가 없는 경우를 정상 경로로 다룬다(404 가 아니다)

### 프론트

1. **iframe 임베드는 전용 페이지에서만.** `youtube-nocookie.com` 도메인을 쓴다
2. **YouTube 브랜드 표시 의무(III.F.2)** — 썸네일을 쓰는 **모든 곳**에 YouTube 로고 또는 "YouTube에서 보기" 링크. 홈 카드·"다음 추첨" 카드 포함
3. **썸네일은 `thumbnail_url` 을 핫링크한다.** 내려받아 자체 서버에 두지 않는다
4. **제목을 원문 그대로 표시한다.** 말줄임은 되지만 낱말을 바꾸지 않는다 — 제목 변조는 정책 위반이다
5. 홈·"다음 추첨" 카드는 썸네일 3개, 클릭 → 전용 페이지. **자동재생 금지**, 최소 200×200px
6. **광고는 플레이어와 겹치지 않게 둔다.** 약관이 금지하는 것은 플레이어 "위 또는 그 안"(III.G.1.c)과 플레이어 앞의 오버레이·프레임(RMF)이다. **플레이어 하단의 별도 영역 배치는 금지 대상이 아니다.** 다만 재생 컨트롤이나 "다음 영상" 버튼처럼 보이지 않도록 여백과 구분선을 둔다 — 오클릭 유도는 `forbidden-expressions.md` 의 광고 배치 규칙에도 걸린다. YouTube 플레이어의 자체 광고를 막거나 가리지 않는다
7. **전용 페이지에 자체 콘텐츠를 함께 둔다** — III.G.1.d 의 "독립적 가치" 요건. 뉴스 페이지의 `GuideSection`+`Faq` 패턴을 따른다
8. 면책 — "외부 채널의 콘텐츠이며 본 사이트의 견해가 아닙니다"
9. **영상 상세 페이지를 만들지 않는다.** 뉴스가 그랬던 것과 같은 이유 — 남의 영상에 우리 URL 을 붙이지 않는다
10. 쇼츠 라벨은 표시해도 되나 **정렬·필터의 근거로만 쓰고 사실 주장으로 쓰지 않는다**

### 쿼터 0 으로 검증되는 것 (로직 대부분)

1. **순수 함수 단위 테스트** — `_is_on_topic`·`_has_forbidden_expression`·`_is_fresh`·`_estimate_shorts`·`_is_displayable`·`_parse_iso8601_duration`. 특히 duration 파서는 `PT1M30S`·`PT2H`·`P1DT2H3M4S`·`PT0S`·파싱 실패를 전부 커버한다
2. **픽스처 테스트** — 실제 응답을 1 unit 으로 딱 한 번 받아 JSON 파일로 저장하고 무한 반복 테스트
3. **키 없이 수동 트리거** — `POST /internal/jobs/video_search/run` → `failed` + "키가 없다". 크론에 등록되지 않았음이 기동 로그에 남는다
4. **DDL 대조** — `002_lotto_video.sql` 과 `0002_lotto_video.py` 를 눈으로 diff. `alembic upgrade head --sql` 로 나갈 DDL 확인 후 **사용자 승인**
5. **권한** — `pg_default_acl` 조회 + `app_reader` 로 SELECT 성공 / INSERT 실패
6. **삭제 경로** — 존재하지 않는 무작위 키를 DB 에 직접 넣고 `video_refresh` 실행. 실제 삭제된 영상을 기다릴 필요가 없다 (1 unit)
7. **갱신 대상 선정** — `UPDATE lotto_video SET refreshed_dttm = now() - interval '26 days'` 로 인위적으로 늙힌다
8. **`YOUTUBE_DRY_RUN=true`** — DB 를 건드리지 않고 각 필터 단계의 통과·제외 건수만 로그로 남긴다. 뉴스 제외어를 332건에 드라이런해 검증한 그 절차를 코드로 갖는 것이다

## 남는 리스크

### 1. 쇼츠 판별의 부정확성 — 가장 큰 리스크

Data API 가 원본 화면비를 주지 않아 **"3분 이하 가로 영상"이 전부 쇼츠로 오분류된다.** 로또 도메인에서 흔한 경우다 — 90초짜리 당첨번호 요약 영상이 그렇다. 오분류율을 사전에 추정할 수 없다.

- **완화**: `shorts_estimate_cd` + `shorts_basis_desc` 로 추정임이 스키마에 남는다
- **측정**: 첫 100건을 사람이 확인해 오분류율을 재고 위키에 실측치로 기록
- **폐기한 대안**: `/shorts/{id}` HEAD 리다이렉트(III.E.6 회색지대), oEmbed 의 width/height(플레이어 크기이지 원본 화면비가 아니라 무의미). **두 판단 모두 문서에 남긴다** — 나중에 같은 제안이 다시 나왔을 때 답이 있어야 한다
- **재검토 트리거**: 오분류율 30% 초과 시 RSS 의 `/shorts/` 링크를 보조 신호로 쓰는 안을 다시 검토하거나, 목록을 나누지 않고 재생시간만 표시한다. 스키마는 그대로 두면 된다 — 이 컬럼이 "추정"으로 설계된 덕이다

### 2. 30일 정책 해석 — ⚠ 사용자 확인 필요

III.E.4 는 "삭제 또는 갱신"이라 하는데 **"갱신"의 정확한 정의가 없다.** 우리 해석은 "`videos.list` 로 재조회해 값을 덮으면 그 시점부터 30일이 다시 시작한다"이다. 이 해석이 옳으면 무제한 보관이 되는데, 정책의 취지(오래된 데이터가 원본과 어긋나는 것을 막는다)를 보면 무제한 보관 자체가 의도가 아닐 가능성이 있다.

- **주 완화책 `YOUTUBE_RETAIN_DAYS=60`** — 게시 60일이 지난 영상은 갱신하지 않고 지운다. 로또는 주 1회 추첨이고 목록 노출 기준이 7일이라 60일 지난 영상은 어차피 화면에 없다. **대부분의 행이 60일 안에 사라져 해석 논쟁이 실질적으로 무력화된다**
- 보조: 하드 삭제가 API 장애와 무관하게 먼저 돈다

**법적 판단은 사용자 몫이다.** 이 문서는 조항 문언과 우리 해석을 밝힐 뿐이다.

### 3. 애드센스와의 관계 — ⚠ 사용자 판단 필요

임베드 자체는 위반이 아니다. 실제 위험은 셋이다.

1. **썸네일 이미지 안의 글자는 필터로 걸러지지 않는다.** 제목에 금지 표현이 없어도 썸네일에 "1등 예측"이 대문짝만하게 박혀 있을 수 있다. **이것이 남는 구멍이다.** 완화 — 화이트리스트 채널 위주로 노출(`discovery_cd='channel'` 우선 정렬), 검색 유래는 하단으로
2. **"낮은 가치 콘텐츠"로 읽히는 것** — 남의 영상 임베드만 있는 페이지가 그렇게 분류된다. 완화 — 전용 페이지에 회차 정보·통계 요약·면책을 함께 배치
3. **광고 밀도** — 플레이어 하나를 광고가 둘러싸는 배치는 "광고가 콘텐츠보다 많다"로 읽힌다. 하단 1개 수준은 일반적인 배치이고 문제되지 않는다

### 4. 화이트리스트 채널의 변질

오늘 통계 해설 채널이 내일 예상번호 채널이 되고, **채널이 팔려 전혀 다른 콘텐츠가 되기도 한다**(조사에서 6건 실제 확인). 금지 표현 필터가 화이트리스트 경로에도 걸리고, 채널명 대조로 개명을 감시한다. `discovery_cd='channel'` 인 행의 금지 표현 제외 건수를 별도 로그로 남겨, 그 수가 늘면 화이트리스트에서 빼고 BLOCK 으로 옮긴다.

### 5. `search.list` 100회 상한의 경직성

일일 카운터가 추정이라 재시도 초과분을 못 센다. 수동 트리거를 몇 번 누르면 그날 검색이 죽는다. **검색이 죽어도 화이트리스트 경로는 살아 있다**는 것이 잡을 나눈 실질적 이득이고 최선의 완화다.

### 6. 명명 표준 확장이 승인되지 않을 위험

`_key`·`_sec` 는 계약 변경이라 승인이 선행되어야 한다. 대안 B(`video_url` 정규화)를 함께 제시했다.
