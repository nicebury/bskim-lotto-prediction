# 금지 표현과 서비스 포지셔닝

이 페이지는 **전 세션 구속력**을 갖는다. UI 문구, 코드 주석, 변수명, API 응답 필드명, 메타 태그, 커밋 메시지 어디에도 아래 표현을 쓰지 않는다.

---

## 이 서비스가 무엇인가

**이것이다**: 복권 정보 제공 사이트. 당첨결과 확인. 번호 통계 분석. 복권 뉴스 큐레이션. 재미용 번호 추천 시뮬레이터. 꿈해몽 기반 재미용 번호 생성.

**이것이 아니다**: 당첨 예측 사이트. 고확률 번호 제공. 당첨 보장. 유료 번호 판매. 복권 구매 대행. 온라인 복권 판매. 사행성 조장.

경계는 한 문장으로 요약된다.

> 과거 당첨번호 통계와 랜덤 알고리즘을 활용한 참고용·재미용 시뮬레이션이며, 당첨을 보장하지 않는다.

---

## 왜 이것이 기술적 제약인가

세 가지가 걸려 있다.

**애드센스.** 복권 콘텐츠는 광고 제한 주제로 분류될 수 있다. 심사자는 사이트를 사람이 본다. "1등 예측 번호" 라는 버튼이 하나 있으면 나머지가 아무리 정보형이어도 도박 조장으로 읽힌다. 승인이 거절되면 재신청은 훨씬 어렵다.

**법적 포지션.** 국내에서 복권 판매는 기획재정부 복권위원회가 지정한 동행복권(dhlottery.co.kr)이 유일한 합법 채널이다. 사칭 사이트가 늘고 있어 이용자와 규제기관 모두 민감하다 ([[trademark-check]]). "구매하기" 버튼 하나가 판매 대행으로 오인될 수 있다.

**사실.** 로또 번호는 무작위로 추첨된다. 과거 통계는 다음 회차 당첨 확률을 바꾸지 않는다. 확률을 제시하는 것은 정책 위반 이전에 **거짓말**이다.

---

## 금지 표현 목록

| 금지 | 대신 |
|------|------|
| 당첨 확률, 예상 적중률, 적중 확률 | 조합 성향, 통계 참고 요소 |
| 고확률 번호, 검증된 번호, 추천 적중 | 추천 기준, 랜덤 보정 |
| 1등 가능성, 1등 예측, 당첨 보장 | 재미용 시뮬레이션 |
| 당첨 확률 상승, 확률을 높이는 | (대체 표현 없음. 이 개념 자체를 쓰지 않는다) |
| 필승, 비법, 명당 번호 | (쓰지 않는다) |
| 구매하기, 결제, 번호 구입 | (버튼 자체를 만들지 않는다) |

### 코드 식별자에도 적용된다

응답 필드명, 변수명, 함수명, DB 컬럼명에 아래를 쓰지 않는다.

```
probability   win_rate   accuracy   confidence
hit_rate      expected_value   success_rate
```

`confidence` 가 목록에 있는 이유는 미묘하다. 개발자에게는 "모델의 내부 확신도" 지만, JSON 응답을 본 사용자에게는 "이 번호가 맞을 확신" 으로 읽힌다. 실제로 기존 `CLAUDE.md` 는 `confidence` 를 "조합의 6개 번호가 유효 조합에서 평균적으로 등장한 비율" 로 정의한다고 적었으나 — **코드에는 그런 필드가 없었다.** 문서가 존재하지 않는 확률 개념을 발명한 것이다. 자세한 경위는 [[prediction-algorithm]] 참조.

대신 관찰된 **사실**을 반환한다. `hot_count: 2` 는 "최근 20회 HOT 번호가 2개 포함됐다" 는 검증 가능한 사실이다. `probability: 0.13` 은 주장이다. 필드 스펙은 [[api-contract]] 의 표현 규약 절에 있다.

## UI 라벨 규칙 (002 개편)

금지 표현은 아니지만, 002 개편으로 확정한 **사용자 노출 문구 규칙**이다.

### "COLD" → "안 나오던 번호"

화면에 노출되는 문구에서 **"COLD" 를 쓰지 않는다.** 영어 약어라 40대+ 사용자에게 직관적이지 않고, "HOT/COLD" 대비는 도박적 인상을 준다. 통계 탭·설명·차트 라벨·전략명("COLD 번호 부활" → "안 나오던 번호 되짚기") 전부 한국어 "안 나오던 번호" 로 쓴다.

**내부 데이터 필드(`cold`, `overdue`)와 API 필드명은 그대로 둔다** — 표현 규약이 금지하는 것은 `probability` 류의 확률 주장 필드이지 `cold` 가 아니다. 바꾸는 것은 사람이 읽는 라벨뿐이다. 잔존 위치(개편 전 기준): `HowRecommendWorks`(전략명), `lotto/page`, `lotto/stat/hot-cold` 페이지.

### "AI" 표현

002 는 추천 버튼을 "AI …" 로 부르길 원한다. 'AI' 자체는 금지 표현이 아니다(추천은 앙상블·몬테카를로 계산을 쓴다). 다만 **예측을 암시하는 조합은 피한다**:

- 권장: **"AI 번호 조합 추천"** — 사이트가 이미 쓰는 '조합/조합 성향' 언어와 정합하고, "번호를 조합해 제안" 이라는 사실에 충실하다.
- 지양: "AI 로또번호 **예측**", "AI 당첨번호", "AI 1등 번호" 처럼 예측·당첨을 암시하는 문구(위 금지 목록과 직접 충돌).

'AI' 를 쓰는 화면에도 재미용 면책은 그대로 붙는다.

## 면책 고지를 붙여야 하는 곳

1. **번호 추천 결과가 표시되는 모든 화면.** 초안 6.1·8.3.
2. **꿈해몽 결과 화면.** 꿈과 당첨 사이에 인과관계를 주장하지 않는다. "돼지꿈이면 로또 당첨" 처럼 확정적으로 쓰지 않는다.
3. **모든 통계 페이지.** "로또 번호는 무작위로 추첨되므로 과거 통계가 향후 당첨을 보장하지 않습니다. 본 통계는 과거 회차의 분포를 이해하기 위한 참고 정보입니다."
4. **`/disclaimer` 전용 페이지.**
5. **API 응답 자체.** `/api/lotto/recommend` 는 `disclaimer` 필드를 반환한다. 프론트가 잊지 못하게 한다.

## ★ 외부에서 들어온 텍스트 — 유튜브 영상 제목

2026-08-28 신설. 지금까지 이 페이지는 **우리가 쓰는 문구**만 다뤘다. 유튜브 영상 수집이 붙으면서 **남이 쓴 문구가 우리 화면에 뜨는** 경우가 처음 생긴다.

### 왜 뉴스보다 위험한가

뉴스 제목이 통과할 수 있었던 것은 언론사 기사 제목에 이런 표현이 거의 없기 때문이지, "외부 텍스트는 예외"라는 규정이 있어서가 아니다. **그런 예외는 이 계약 어디에도 없다.**

로또 유튜브는 다르다. 2026-08-27 채널 조사에서 활동 중인 로또 채널 대부분이 예상번호 제공 채널이었고, 제목이 이런 식이었다.

```
1238회 전문 분석가 15명이 추천하는 최종 고정5수 자료
(1239회 로또 예상번호) 목요일 패턴분석
1238회,예상번호!로또연구22년째
```

**이 페이지의 금지 낱말이 그대로 박혀 있다.** 이런 제목이 영상 카드에 뜨면 "1등 예측 번호" 버튼이 하나 있는 것과 같은 효과다 — 나머지가 아무리 정보형이어도 심사자는 그것을 본다.

### 방어선은 수집 단계다

**워커가 INSERT 전에 버린다.** `YOUTUBE_FORBIDDEN_KEYWORDS`(env 주입) + `gpt-5-nano` 보조 판정 2단이고, 제목뿐 아니라 **채널명도 함께 검사한다**("로또 예상번호 연구소" 같은 채널이 제목만 무해하게 짓는 경우).

DB 에 넣고 표시할 때 거르지 않는 이유는 `lotto_video` 의 UNIQUE 제약 때문이다 — 한 번 들어간 영상은 재수집 시 `DO NOTHING` 으로 죽어 **다시 판단할 기회가 없다.**

### ★ 표시할 때 제목을 고치지 않는다

**금지 표현이 화면에 남았다면 프론트가 제목을 손볼 일이 아니라 수집 필터를 고칠 일이다.**

영상 제목 변조는 YouTube 정책 위반이다(III.F.2 의 귀속 표시 방해 금지와 같은 취지). 우리 정책을 지키려고 남의 제목을 바꾸면 **두 정책을 동시에 어긴다.** 말줄임(`…`)은 되지만 낱말을 바꾸거나 지우지 않는다.

### 자가 점검의 사각지대 두 곳

아래 `grep` 은 **소스코드만** 훑는다. 다음 둘은 잡지 못한다.

1. **DB 에 저장된 영상 제목** — 정규식이 통과해도 화면에는 금지 표현이 떠 있을 수 있다. 그래서 아래 SQL 을 함께 돌린다
2. **썸네일 이미지 안의 글자** — 제목이 무해해도 썸네일에 "1등 예측"이 박혀 있을 수 있다. **현재 막을 방법이 없다.** 완화책은 화이트리스트 채널(`discovery_cd='channel'`)을 우선 노출하고 검색 유래를 하단에 두는 것뿐이다

```sql
-- 수집된 영상 제목에 금지 표현이 남아 있는지. 항상 0이어야 한다.
SELECT video_id, channel_nm, title_nm FROM lotto_video
 WHERE title_nm ~ '당첨 ?확률|고확률|예상 ?적중|적중률|1등 ?예측|당첨 ?보장|필승|명당|예상번호|추천번호|고정수';
```

0이 아니면 **필터를 고치고 그 행을 지운다.** 표시 단에서 감추는 것으로 끝내지 않는다 — 다음 수집에서 또 들어온다.

## 자가 점검

커밋 전에 다음을 돌린다. 정규식이 걸리면 그 문맥이 "금지 목록을 서술하는 곳" 인지 "실제로 쓰는 곳" 인지 확인한다.

```bash
grep -rnE '당첨 ?확률|고확률|예상 ?적중|적중률|1등 예측|당첨 ?보장|필승|명당' \
  --include='*.tsx' --include='*.ts' --include='*.py' --include='*.md' .

grep -rnE '\b(probability|win_rate|accuracy|confidence|hit_rate)\b' \
  --include='*.tsx' --include='*.ts' --include='*.py' .
```

이 검사를 스킬로 만들어 자동화하는 것이 좋다 — 사람의 리뷰보다 정규식이 성실하다.

## 어투 규칙 — 금지 표현을 피하려다 방어적으로 쓰지 않는다 (2026-09-02)

금지 목록을 지키려다 보면 문장이 **부정문으로만** 채워지는 일이 생긴다. 2026-09-02 에 사용자가 사이트 전체를 두고 지적했다.

> "전반적으로 모든 문구들이 약간 네거티브야. 책임지지 않습니다. 보장하지 않습니다. 약속하지 않습니다. … 너무 방어적이야."
> "과학적으로 확인된 관계도 아닙니다. 이런게 있으면 꿈해몽을 해보고 싶은 마음도 없어질 거 같아."

실제로 꿈해몽 안내 절 하나에 부정문이 **일곱 개**였다(관계가 없습니다 · 확인할 방법은 없습니다 · 뜻은 아니며 · 관계도 아닙니다 · 달라지지 않고 · 나빠지지도 않습니다 · 뜻하지 않습니다). 추천 화면은 **"어느 쪽으로 뽑아도 결과는 달라지지 않습니다" 를 세 번** 반복했다.

### 다섯 가지 규칙

1. **사실은 하나도 빼지 않는다.** 무작위 추첨, 인과관계 없음, 과학이 아님 전부 그대로 남긴다. 바꾸는 것은 **말하는 방식**이지 내용이 아니다.
2. **같은 사실을 한 화면에서 반복하지 않는다.** 한 번 분명히 말하고 끝낸다. 세 번 말하면 경고문이 된다.
3. **부정문을 서술문으로 바꾼다.** 같은 사실을 긍정형으로 쓸 수 있다.
4. **무엇인지 먼저 말하고 한계는 뒤에 붙인다.** 한계로 문단을 시작하지 않는다.
5. **면책 고지는 그대로 둔다.** `DISCLAIMER` 넷과 정책 페이지(약관·개인정보·면책·책임 있는 구매)는 법적 장치다. **본문을 부드럽게 쓸 수 있는 근거가 바로 그 고지에 있다.**

### 바꾼 예

| 전 | 후 |
|---|---|
| 어느 풀이가 맞는지 확인할 방법은 없습니다 | 정답이 하나로 정해진 분야라기보다 여러 이야기가 나란히 전해지는 쪽에 가깝습니다 |
| 과학적으로 확인된 관계도 아닙니다 | 과학이 밝혀낸 관계라기보다 사람들이 오래 나눠 온 이야기에 가깝습니다 |
| 어느 쪽으로 뽑아도 결과는 달라지지 않습니다 | 추첨은 매 회차 새로 진행됩니다. 기준은 재료를 고르는 방식일 뿐입니다 |
| 그 이상을 약속하지 않습니다 | 딱 거기까지가 이 도구의 몫입니다 |
| 어떤 예측도 섞여 있지 않습니다 | 지금 이 조합에 대한 사실만 담겨 있습니다 |
| 오래 나오지 않았다고 나올 차례가 된 것은 아닙니다 | 마지막으로 나온 뒤 몇 회차가 지났는지를 셉니다 |
| '나올 때가 됐다' 는 건 없습니다 (제목) | '나올 때가 됐다' 는 느낌에 대하여 |

### 그대로 두는 부정

**질문에 답하는 부정**과 **법적 사실**은 자연스럽다. 걷어내면 오히려 뜻이 흐려진다.

- "자동과 수동, 당첨 판정에는 아무 차이가 없습니다" (질문에 대한 답)
- "19세 미만은 복권을 구매할 수 없습니다" (법)
- "기한을 넘기면 당첨금을 받을 수 없습니다" (중요한 경고)
- 도박사의 오류 설명 전체 (교육적이고 재미있다)

판정 기준: **읽는 사람에게 필요한 정보인가, 우리가 책임을 면하려는 말인가.**

## "AI" 라는 말을 어디에 쓸 수 있는가 (2026-09-02)

사용자가 물었다. *"AI번호추천, 6가지 추천에도 AI라는 단어를 내가 쓰고 있는데 그래도 될까? 진짜 AI가 아니라면… 다른 이름을 붙여야 할까?"*

조사해 보니 **기능마다 답이 달랐다.**

| 기능 | 실제로 돌리는 것 | AI 라 부를 근거 |
|---|---|---|
| 번호추천 | 빈도·주기·흐름·패턴의 **가중 선형합** → 몬테카를로 확률 추출 → 패턴 필터 | **없다** |
| 꿈해몽 | kiwipiepy 형태소 분석 → **SentenceTransformer**(`upskyy/kf-deberta-multitask`, 768차원) 임베딩 → ChromaDB 벡터 검색 | **있다** |

[[prediction-algorithm]] 첫 문단이 이미 못박아 두었다.

> **머신러닝이 아니다.** 과거 당첨번호의 분포를 요약해 가중치를 만들고, 그 가중치로 조합을 뽑은 뒤, 역사적으로 흔한 패턴을 벗어난 조합을 버린다.

**문서가 "아니다" 라고 적어 둔 것을 화면이 "AI" 라고 부르고 있었다.** 계약과 코드가 다르면 코드가 틀린 것이라는 규칙이 화면 문구에도 그대로 적용된다.

### 결정

- **번호추천에서 "AI" 를 뺀다.** `AI 번호추천` → **`정밀 분석 추천`**, 배지는 `7단계 · 몬테카를로`. 하단 탭바는 `AI추천` → `분석추천`.
- **꿈해몽의 "AI" 는 유지한다.** 신경망 언어모델을 실제로 돌리므로 근거가 있다.
- 사이트 소개 문구도 `통계와 AI 기반 번호추천` → **`통계 기반 번호추천과 AI 꿈해몽`** 으로 나눴다.

### 규칙

> **하는 일과 다른 이름을 붙이지 않는다.** 있어 보이려고 붙인 말은 그 순간 과장이 된다.

반대로 **실제로 쓰는 기법의 이름은 당당히 쓴다.** "가상 추첨 횟수" 아래 `몬테카를로 시뮬레이션` 을 적은 것이 그 예다 — 백엔드가 실제로 `montecarlo.simulate()` 를 돌리므로 정확한 서술이고, 사용자에게는 값을 고르는 근거가 된다.
