# 금지 표현과 서비스 포지셔닝

이 페이지는 **전 세션 구속력**을 갖는다. UI 문구, 코드 주석, 변수명, API 응답 필드명, 메타 태그, 커밋 메시지 어디에도 아래 표현을 쓰지 않는다.

---

## 이 서비스가 무엇인가

**이것이다**: 복권 정보 제공 사이트. 당첨결과 확인. 번호 통계 분석. 복권 뉴스 큐레이션. 재미용 번호 추천 시뮬레이터. 꿈해몽 기반 재미용 번호 생성.

**이것이 아니다**: 당첨 예측 사이트. 고확률 번호 제공. 당첨 보장. 유료 번호 판매. 복권 구매 대행. 온라인 복권 판매. 사행성 조장.

경계는 한 문장으로 요약된다.

> 과거 당첨번호 통계와 랜덤 알고리즘을 활용한 참고용·재미용 시뮬레이션이며, 당첨을 보장하지 않는다.

---

## 왜 이것이 기술적 제약인가

세 가지가 걸려 있다.

**애드센스.** 복권 콘텐츠는 광고 제한 주제로 분류될 수 있다. 심사자는 사이트를 사람이 본다. "1등 예측 번호" 라는 버튼이 하나 있으면 나머지가 아무리 정보형이어도 도박 조장으로 읽힌다. 승인이 거절되면 재신청은 훨씬 어렵다.

**법적 포지션.** 국내에서 복권 판매는 기획재정부 복권위원회가 지정한 동행복권(dhlottery.co.kr)이 유일한 합법 채널이다. 사칭 사이트가 늘고 있어 이용자와 규제기관 모두 민감하다 ([[trademark-check]]). "구매하기" 버튼 하나가 판매 대행으로 오인될 수 있다.

**사실.** 로또 번호는 무작위로 추첨된다. 과거 통계는 다음 회차 당첨 확률을 바꾸지 않는다. 확률을 제시하는 것은 정책 위반 이전에 **거짓말**이다.

---

## 금지 표현 목록

| 금지 | 대신 |
|------|------|
| 당첨 확률, 예상 적중률, 적중 확률 | 조합 성향, 통계 참고 요소 |
| 고확률 번호, 검증된 번호, 추천 적중 | 추천 기준, 랜덤 보정 |
| 1등 가능성, 1등 예측, 당첨 보장 | 재미용 시뮬레이션 |
| 당첨 확률 상승, 확률을 높이는 | (대체 표현 없음. 이 개념 자체를 쓰지 않는다) |
| 필승, 비법, 명당 번호 | (쓰지 않는다) |
| 구매하기, 결제, 번호 구입 | (버튼 자체를 만들지 않는다) |

### 코드 식별자에도 적용된다

응답 필드명, 변수명, 함수명, DB 컬럼명에 아래를 쓰지 않는다.

```
probability   win_rate   accuracy   confidence
hit_rate      expected_value   success_rate
```

`confidence` 가 목록에 있는 이유는 미묘하다. 개발자에게는 "모델의 내부 확신도" 지만, JSON 응답을 본 사용자에게는 "이 번호가 맞을 확신" 으로 읽힌다. 실제로 기존 `CLAUDE.md` 는 `confidence` 를 "조합의 6개 번호가 유효 조합에서 평균적으로 등장한 비율" 로 정의한다고 적었으나 — **코드에는 그런 필드가 없었다.** 문서가 존재하지 않는 확률 개념을 발명한 것이다. 자세한 경위는 [[prediction-algorithm]] 참조.

대신 관찰된 **사실**을 반환한다. `hot_count: 2` 는 "최근 20회 HOT 번호가 2개 포함됐다" 는 검증 가능한 사실이다. `probability: 0.13` 은 주장이다. 필드 스펙은 [[api-contract]] 의 표현 규약 절에 있다.

## 권장 표현

- 조합 성향, 추천 기준, 통계 참고 요소, 랜덤 보정
- 재미용 시뮬레이션, 참고용 통계
- 공식 당첨결과 확인, 회차별 데이터 정리
- 건전한 복권 이용 안내, 19세 미만 구매 불가

## UI 라벨 규칙 (002 개편)

금지 표현은 아니지만, 002 개편으로 확정한 **사용자 노출 문구 규칙**이다.

### "COLD" → "안 나오던 번호"

화면에 노출되는 문구에서 **"COLD" 를 쓰지 않는다.** 영어 약어라 40대+ 사용자에게 직관적이지 않고, "HOT/COLD" 대비는 도박적 인상을 준다. 통계 탭·설명·차트 라벨·전략명("COLD 번호 부활" → "안 나오던 번호 되짚기") 전부 한국어 "안 나오던 번호" 로 쓴다.

**내부 데이터 필드(`cold`, `overdue`)와 API 필드명은 그대로 둔다** — 표현 규약이 금지하는 것은 `probability` 류의 확률 주장 필드이지 `cold` 가 아니다. 바꾸는 것은 사람이 읽는 라벨뿐이다. 잔존 위치(개편 전 기준): `HowRecommendWorks`(전략명), `lotto/page`, `lotto/stat/hot-cold` 페이지.

### "AI" 표현

002 는 추천 버튼을 "AI …" 로 부르길 원한다. 'AI' 자체는 금지 표현이 아니다(추천은 앙상블·몬테카를로 계산을 쓴다). 다만 **예측을 암시하는 조합은 피한다**:

- 권장: **"AI 번호 조합 추천"** — 사이트가 이미 쓰는 '조합/조합 성향' 언어와 정합하고, "번호를 조합해 제안" 이라는 사실에 충실하다.
- 지양: "AI 로또번호 **예측**", "AI 당첨번호", "AI 1등 번호" 처럼 예측·당첨을 암시하는 문구(위 금지 목록과 직접 충돌).

'AI' 를 쓰는 화면에도 재미용 면책은 그대로 붙는다.

## 면책 고지를 붙여야 하는 곳

1. **번호 추천 결과가 표시되는 모든 화면.** 초안 6.1·8.3.
2. **꿈해몽 결과 화면.** 꿈과 당첨 사이에 인과관계를 주장하지 않는다. "돼지꿈이면 로또 당첨" 처럼 확정적으로 쓰지 않는다.
3. **모든 통계 페이지.** "로또 번호는 무작위로 추첨되므로 과거 통계가 향후 당첨을 보장하지 않습니다. 본 통계는 과거 회차의 분포를 이해하기 위한 참고 정보입니다."
4. **`/disclaimer` 전용 페이지.**
5. **API 응답 자체.** `/api/lotto/recommend` 는 `disclaimer` 필드를 반환한다. 프론트가 잊지 못하게 한다.

## 광고와 UI 배치 규칙

초안 11.4 에서 옮긴다.

- 광고가 콘텐츠를 가리지 않는다.
- 광고가 내비게이션이나 액션 버튼처럼 보이지 않는다.
- **"다시 생성" 버튼 주변에 광고를 배치하지 않는다.** 오클릭을 유도하는 배치로 읽힌다.
- 광고가 콘텐츠보다 많아 보이지 않는다.
- "준비 중" 페이지(연금복권·스피또)에는 광고를 렌더링하지 않는다.

자세한 것은 [[adsense-readiness]].

## 자가 점검

커밋 전에 다음을 돌린다. 정규식이 걸리면 그 문맥이 "금지 목록을 서술하는 곳" 인지 "실제로 쓰는 곳" 인지 확인한다.

```bash
grep -rnE '당첨 ?확률|고확률|예상 ?적중|적중률|1등 예측|당첨 ?보장|필승|명당' \
  --include='*.tsx' --include='*.ts' --include='*.py' --include='*.md' .

grep -rnE '\b(probability|win_rate|accuracy|confidence|hit_rate)\b' \
  --include='*.tsx' --include='*.ts' --include='*.py' .
```

이 검사를 스킬로 만들어 자동화하는 것이 좋다 — 사람의 리뷰보다 정규식이 성실하다.
