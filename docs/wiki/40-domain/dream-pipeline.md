# 꿈해몽 → 번호 파이프라인

원래 `bskim-money-tellme-lotto`(reg_lotto) 프로젝트의 기능이다. 핵심 로직만 이 저장소로 이식됐고, 신규 백엔드는 그것을 **그대로** 다시 이식한다.

꿈과 당첨 사이에 인과관계는 없다. 재미용 콘텐츠이고, 롱테일 SEO(`돼지꿈 로또번호`, `돈꿈 로또번호`) 유입 경로다. 화면에는 반드시 면책 고지를 붙인다 ([[forbidden-expressions]]).

---

## 전체 흐름

```
꿈 텍스트
  → analyzer.py    형태소 분석 → 후보 단어 목록
  → searcher.py    ChromaDB 벡터 유사도 → 매칭 단어 + 번호 + gubun(1/2/3)
  → generator.py   gubun 누적 tier 별로 조합 생성
  → 번호 세트
```

## 1. 형태소 분석 (`analyzer.py`)

**konlpy 가 아니라 kiwipiepy 를 쓴다.** Java 런타임이 필요 없고 훨씬 빠르다. 원본 프로젝트에서 바꾼 부분이다.

유지하는 품사 (`analyzer.py:20-25`):

```python
_KEEP_TAGS = {"NNG", "NNP", "NNB", "NR", "SL", "VV", "VA", "VA-I", "VV-I", "XR"}
```

일반명사·고유명사·의존명사·수사·외국어, 그리고 동사·형용사(불규칙 포함)와 어근이다. 동사와 형용사를 남기는 이유는 "쫓기다", "빠지다" 같은 꿈 서술어가 해몽 사전의 표제어이기 때문이다.

추출은 3단계다 (`analyzer.py:83-187`).

1. 원문 어절을 사전에 직접 매핑하고 **유의어로 확장한다.**
2. kiwipiepy 토큰을 매핑하거나, 어간을 명사로 되돌린다 (`_stem_to_noun`).
3. 원문 어절 자체를 후보에 추가한다.

한 글자 단어는 **화이트리스트에 있을 때만** 받아들이고, 스톱워드는 뺀다 (`analyzer.py:142-145`). 한 글자를 다 받으면 "이", "그", "수" 같은 것들이 벡터 검색을 오염시킨다.

### ⚠ 함정: `dream_word` 는 사용자가 적은 단어가 아니다

1단계의 **유의어 확장** 때문에, 응답의 `matched_words[].dream_word` 에는 원문에 없는 단어가 섞인다. 2단계의 어간 → 명사 되돌리기(`_stem_to_noun`)는 **말이 아닌 것**을 만들어 내기도 한다.

실측 (2026-08-27, 입력 `"큰 돼지가 집으로 들어오는 꿈을 꿨어요"`):

| `dream_word` | 원문에 있나 | 정체 |
|---|---|---|
| `돼지` `집` | ○ | 실제로 적은 단어 |
| `집안` `건물` | ✕ | `집` 의 유의어 확장 |
| `크함` `꾸음` | ✕ | `큰` · `꿨어요` 의 어간 되돌리기 실패 |

`건물` 은 사전 표제어와 **정확히 일치**하므로 `gubun=1` 로 내려온다. 화면에 그대로 나열하면 "내가 건물을 적었나?" 가 된다(실제 지적).

**프론트의 대응**(2026-08-27): `result.text` 에 실제로 들어 있는 `dream_word` 만 "적어 주신 상징" 으로 세우고, 나머지는 *"꿈 내용에서 넓혀 본 단어"* 로 접어 둔 채 번호에는 반영된다고 밝힌다. 판정은 단순 문자열 포함이다 — 프론트가 형태소를 다시 분석하지는 않는다.

### ✅ 처리 완료 (2026-08-28) — 비단어 필터와 `from_text`

프론트 세션이 남긴 요청 둘을 구현했다. 계약은 [[api-contract]] 의 '2026-08-28 계약 변경' 절에 있다.

**① `_stem_to_noun` 이 만든 문자열은 정확 일치가 있을 때만 쓴다.**

`크함`·`꾸음` 처럼 사전에도 없고 뜻도 없는 문자열이 벡터 검색에 들어가면 유사도만으로 엉뚱한 표제어를 끌어온다 — 실측으로 `크함` 이 `큰북`·`큰방`·`대형` 을 데려와 번호 3개를 보태고 있었다. 사용자는 "큰" 이라고 썼을 뿐이라 그 번호의 출처를 설명할 방법이 없다.

**통째로 막지 않은 이유**: 규칙이 우연히 맞아 실재하는 표제어를 만들어 내는 경우가 있다. 그때는 `gubun=1` 정확 일치가 생기므로, 그것을 조건으로 삼으면 멀쩡한 단어를 잃지 않는다.

실측: `"큰 돼지가 나왔어요"` → 종전 `크함`·`돼지`·`나오음` 셋이 매칭되던 것이 **`돼지` 하나만** 남는다. `matched_words` 에서 항목이 사라질 뿐 **응답 필드는 그대로**다.

**② `matched_words[].from_text: boolean` 추가.**

판정은 원문에 대한 **단순 문자열 포함**이다 — 프론트가 이미 하던 규칙을 그대로 서버로 옮긴 것이라 화면의 분류가 조용히 달라지지 않는다. 프론트는 자기 쪽 포함 판정을 걷어내면 된다.

구현은 `DreamAnalyzer.analyze_detailed()` 가 후보마다 `Candidate(word, from_text, derived)` 를 돌려주는 방식이고, 기존 `analyze()` 는 그 위의 얇은 래퍼로 남겼다 — **두 함수가 다른 규칙으로 갈라지지 않게 한 쪽만 구현한다.**

### ✅ 처리 완료 (2026-08-28) — 제외 번호 `exclude`

`POST /api/dream/recommend` 가 `exclude: number[]`(선택, 기본 `[]`, **최대 39**)를 받는다. 프론트는 3배수 선수신과 필터링을 걷어내면 된다.

- 번호는 **풀에서도 채움에서도** 빠지고, 응답의 `tiers.tierN.pool` 에서도 빠진다. 풀에서만 빼면 "뺐는데 또 나온다" 가 되고 제외 스위치가 고장 난 것으로 읽힌다. `pool` 에서도 빼야 프론트의 `pool` ↔ `numbers` 대조가 계속 성립한다.
- 어떤 tier 의 풀이 **통째로** 제외되면 그 tier 는 `null` 이다(빈 풀과 같게 다룬다).
- 상한이 39인 이유: 6개를 만들려면 6개가 남아야 한다(45 − 39 = 6). 40개 이상과 1~45 밖은 `422` 다 — 조용히 무시하면 사용자는 뺐다고 믿는데 그 번호가 계속 나온다.
- `seed` 재현성은 그대로다.

실측(`돼지`, `exclude=[7,8]`): tier1 풀 `[7,8,12]` → `[12]` 로 줄고 조합에 7·8 이 없다.

## 2. 벡터 검색 (`searcher.py`)

| 항목 | 값 | 줄 |
|------|-----|----|
| ChromaDB 컬렉션 | `lotto_word` | 20 |
| 임베딩 모델 | `upskyy/kf-deberta-multitask` (SentenceTransformer) | 21 |
| 조회 개수 | `n_results=100` | 83, 96 |
| 결과 컷 | `TOP_CONTAINING=3`, `TOP_SIMILAR=3` | 25-26 |
| 거리 상한 | `DISTANCE_THRESHOLD=500` | 23 |

### 거리 → 점수

```python
score = 1.0 / (1.0 + max(0.0, distance))     # searcher.py:91-94
```

L2 거리를 0~1 점수로 뒤집는다. 가까울수록 1에 가깝다. **이 값은 UI 표시용이다.** 확률이 아니다.

### `gubun` — 매칭 종류

| 값 | 조건 |
|----|------|
| 1 | 문서 == 검색어 (정확 일치) |
| 2 | 검색어가 문서에 포함됨 |
| 3 | 그 외 (벡터 유사) |

`DISTANCE_THRESHOLD` 를 넘는 결과는 버린다 (`searcher.py:113`).

### 함정: 유사 단어 오염 방지

**증상.** 관련 없는 단어("곡괭이", "꽈리", "꽈배기")가 유사 결과 상위에 반복해서 뜬다.

**원인.** 임베딩 공간에서 이 단어들이 여러 질의의 근처에 놓여 있다. 벡터 검색의 고질적 허브(hub) 문제다.

**해법.** `EXCLUDE_WORDS` 목록을 두고, 유사(gubun 3) 상위 3개 중 **2개 이상**이 목록에 걸리면 유사 결과 전체를 버린다 (`searcher.py:143-145`). 개별 단어만 빼는 게 아니라 전부 버리는 이유는, 그 정도로 허브가 끼어들었다면 나머지 결과도 신뢰할 수 없기 때문이다.

## 3. 번호 생성 (`generator.py`)

`build_tier_sets` (`generator.py:58-98`). 번호 풀을 gubun 별로 **누적**한다.

| tier | 번호 풀 |
|------|---------|
| 1 | gubun 1 (정확 일치)만 |
| 2 | gubun 1 + 2 |
| 3 | gubun 1 + 2 + 3 |

tier 마다 `sets_per_tier`(기본 **10**)개의 고유 조합을 만든다. 풀이 6개 미만이면 **모자란 자리를 번호별 통계 점수에 비례해 채운다** (`_generate_combo`).

### 부족분 채우기 — 무작위가 아니라 통계다 (2026-08-27)

종전에는 `1~45 무작위`였다. 화면이 "모자란 번호는 통계로 채웠습니다" 라고 안내하려면 그 말이 사실이어야 해서 채우는 방법만 바꿨다. **응답 스키마는 그대로다.**

쓰는 점수는 `/api/lotto/recommend` 의 `ensemble` 이 쓰는 것과 **같다** — 분석기 4종(빈도·지연·핫콜드·패턴)을 `ensemble.score` 로 가중 합산한다(`app/domain/number_scores.py`). 같은 사이트의 두 화면이 "눈여겨볼 번호" 를 다르게 계산하면 사용자는 어느 쪽도 믿지 않는다.

**몬테카를로는 타지 않는다.** 그 5만 회는 점수를 만든 *뒤* 조합을 고르는 단계이고, 2.5초짜리에 동시 실행을 막는 게이트까지 걸려 있다([[0012-serialize-monte-carlo]]). 여기서 필요한 것은 번호별 점수뿐이고, 태웠다면 꿈해몽이 추천과 같은 대기열에 들어가 서로를 굶겼을 것이다.

| 항목 | 실측 (1,238회차, 2026-08-27) |
|------|------|
| 분석기 4종 + 합산 | **24.9ms** — 캐시 미스일 때 1회만 |
| `all_draws` 조회 | 4.8ms — 캐시 미스일 때만 |
| `latest_round` 조회 | 0.9ms — 매 요청 (캐시 키 확인용) |
| 조합 생성 3 tier × 30세트 | **4.4ms** (종전 균등 1.0ms) |
| 꿈해몽 warm 요청 전체 | 0.07~0.08초 |

점수는 **최신 회차를 키로 캐시**한다. 주 1회만 바뀌므로 매 요청 1,200여 행을 다시 집계할 이유가 없다.

**가중은 온건하다.** 실측 점수 범위가 0.318~0.718 로 최대 2.3배이고, 채움 3,000회에서 상위 5개 번호가 하위 5개보다 **1.75배** 자주 나왔다(431회 vs 247회). 무작위와 구분되지만 특정 번호로 쏠리지도 않는다.

⚠ **꿈에서 나온 번호에는 가중치를 적용하지 않는다.** 통계가 채우는 것은 빈자리뿐이다. 풀 안에서의 선택까지 통계가 흔들면 그 조합은 더 이상 "꿈에서 나온 번호" 가 아니고, 프론트의 `pool` ↔ `numbers` 대조도 뜻을 잃는다.

⚠ **채움이 아예 없는 tier 가 흔하다.** 풀이 6개 이상이면 채울 자리가 없다. 실측(`돼지꿈`, `sets_per_tier=5`): tier1 은 3자리 채움, tier2 는 1자리, **tier3 은 0자리**. 안내 문구를 tier 단위로 무조건 띄우면 채움이 없는 tier 에서 거짓이 된다 — 지금처럼 `pool` 과 대조해 실제로 채워진 번호가 있을 때만 말한다.

⚠ **가중 추출은 균등보다 같은 조합을 자주 만든다.** `generate_unique_combos` 는 중복을 버리고 최대 1,000회만 시도하므로 이론상 요청 개수를 못 채울 수 있다. 가장 좁은 조건(풀 5개 = 빈자리 1개 = 만들 수 있는 조합 40개)에서 30세트를 요청해도 전부 채워지는 것을 확인했고 테스트로 고정해 두었다(`backend/tests/test_dream_fill.py`).

#### 통계로 채우지 못하는 경우

두 가지뿐이고, 그때는 **조용히 균등 무작위로 되돌아간다.** 채움 방식 하나 때문에 멀쩡히 동작하던 화면을 500 으로 만드는 것이 사용자에게 더 나쁘기 때문이다. 대신 서버 로그에 시끄럽게 남긴다.

| 경우 | 로그 | 언제 |
|------|------|------|
| 회차 50개 미만 | `WARNING … 통계로 채울 수 없습니다` | 빈 DB·개발 초기. 운영에서는 1,238회차라 도달하지 않는다 |
| DB 조회 실패 | `ERROR … 준비하지 못했습니다` | Postgres 장애. 이때는 사이트의 다른 화면도 이미 500 이다 |

> **프론트 세션에게 (요청 완료).** 안내 문구를 "통계로 채웠습니다" 로 바꿔도 된다. 위 두 경우에는 문구와 실제가 어긋나지만 둘 다 운영 정상 상태에서는 발생하지 않는다. **응답만 보고는 구분할 수 없다** — 구분하려면 필드가 필요한데, 늘리지 않기로 한 요청을 지켰다. 구분이 필요해지면 그때 계약을 함께 연다.

tier 1 은 좁고 확신 있는 풀, tier 3 은 넓고 느슨한 풀이다. 사용자에게는 "정확히 일치한 단어만", "비슷한 단어까지" 정도로 설명한다.

> **문서-코드 불일치.** 기존 `CLAUDE.md` 는 이 모듈을 "3-세트 조합 생성" 이라고 적었다. 실제로는 **3개 tier × tier당 10세트 = 30세트**다. UI 가 몇 세트를 보여줄지는 프론트의 결정이지만, 백엔드가 3개만 준다고 가정하지 않는다.

번호 생성 로직은 **백엔드에 있다.** 원본 프로젝트는 TypeScript 프론트에서 만들었다. 옮긴 이유는 프론트가 비즈니스 계산을 하지 않는다는 경계 때문이다 ([[api-contract]]).

## 3-1. 사전에 단어를 더할 때 (2026-08-27)

`data/chroma_words/` 는 `.gitignore` 되어 **git 에 없고**, 이 임베딩을 만든 원본 데이터도 남아 있지 않다. 사전은 **복제할 수 없는 자산**이다. 그래서 직접 넣지 않는다.

| 무엇 | 어디 |
|------|------|
| 무엇을 더할 것인가 | `backend/data/custom_words.json` — **git 에 들어간다** |
| 그것을 사전에 반영 | `backend/scripts/add_custom_words.py` |

```bash
cd backend
uv run python scripts/add_custom_words.py            # 무엇이 바뀔지만 본다 (쓰지 않는다)
uv run python scripts/add_custom_words.py --apply    # 실제로 반영
```

`upsert` 라 두 번 돌려도 결과가 같다. 사전 파일을 잃어도 원본만 다시 구하면 이 스크립트로 복구된다.

**전체 재임베딩은 하지 않는다.** 기존 4,802개의 벡터는 그대로 두고 새 단어만 같은 모델(`upskyy/kf-deberta-multitask`, 768차원)로 인코딩한다. 같은 공간에 놓이므로 거리 비교가 성립한다. 모델을 바꾸는 경우에만 전부 다시 만들어야 하고, 그건 이 스크립트의 일이 아니다.

⚠ **실행 전에 백엔드 서버를 멈춘다.** ChromaDB 는 HNSW 인덱스를 `data_level0.bin` 등 별도 파일로 들고 있고 단어를 더하면 그 파일들을 다시 쓴다. 서버가 떠 있으면 그 프로세스(정확히는 `PersistentClient` 를 든 multiprocessing 자식)가 같은 파일을 열어 둔 채라 **복구할 수 없는 자산이 상할 수 있다.** 스크립트가 `lsof` 로 점유 프로세스를 감지하면 실행을 거부한다.

⚠ **메타데이터는 문자열로 넣는다.** 원본 4,802건이 전부 문자열이고(`{'lotto_number': '[5, 33, 39]', 'importance': '4'}`), `searcher._parse_lotto_number` 가 그 형식을 전제로 판다. 타입이 섞이면 **그 단어만 조용히 번호 없이** 매칭된다.

⚠ **kiwipiepy 가 그 단어를 뽑아내는지 먼저 본다.** 사전에 넣어도 형태소 분석에서 안 나오면 검색에 도달하지 못한다. `DreamAnalyzer.analyze("...")` 로 확인한다 — 고유명사는 `NNP` 로 잡혀야 하고, `_KEEP_TAGS` 에 없는 품사면 넣어도 소용없다.

### 지금까지 더한 단어

| 단어 | 번호 | 날짜 | 비고 |
|------|------|------|------|
| 이재명 | 1, 32 | 2026-08-27 | 사용자 지정. 원본에 `문재인 → [1, 32]` 이 이미 있어 값·관례가 일치한다. 원본의 인물·직위 표제어는 `대통령`(1,3) · `문재인`(1,32) · `김대중대통령휘호`(37) · `국회의원`(18) · `선거`(23,39) 이고 다른 정치인 이름은 없다 |

> **정치적 중립.** 원본 사전에 특정 정치인 이름이 하나(`문재인`) 들어 있고 거기에 하나를 더한 상태다. 표제어를 늘릴수록 "누구는 있고 누구는 없다" 가 눈에 띈다 — 넣고 빼는 판단은 사용자 몫이고, 백엔드는 `custom_words.json` 에 적힌 대로만 반영한다.

## 4. 싱글톤 로딩 (`state.py`)

`threading.Lock` + double-checked locking 으로 `DreamAnalyzer` 와 `DreamSearcher` 를 각각 한 번만 만든다 (`state.py:14-40`).

### 함정: 첫 요청이 20초 걸린다

**증상.** 서버를 띄우고 처음 `/api/dream/recommend` 를 부르면 20초쯤 응답이 없다. 이후 요청은 즉시 온다. 헬스체크는 정상이다.

**원인.** SentenceTransformer 모델(`upskyy/kf-deberta-multitask`)과 ChromaDB 클라이언트가 **lazy** 로 로드된다. 첫 요청이 그 비용을 전부 낸다.

**해법.** 두 가지 중 하나를 고른다.

- 프론트가 이 요청에 로딩 상태를 반드시 표시한다. 진행 표시 없는 20초는 고장으로 읽힌다.
- 또는 백엔드 lifespan 에서 워밍업한다. 그러면 기동이 20초 느려지지만 첫 사용자가 기다리지 않는다. 컨테이너 헬스체크의 `start_period` 를 그만큼 늘려야 한다.

lazy 를 eager 로 바꾸면 **꿈해몽을 안 쓰는 배포에서도** 20초와 수백 MB 를 낸다. 지금은 lazy 를 유지하고 프론트가 로딩을 표시한다.

`chroma_path` 가 없으면 `FileNotFoundError` 를 던진다. 조용히 빈 결과를 주지 않는다.

## ChromaDB 를 pgvector 로 옮기지 않는다

`backend/data/chroma_words/` 를 파일 그대로 쓴다. 근거는 [[0006-keep-chromadb-not-pgvector]].

백엔드 컨테이너는 이 디렉토리를 **읽기 전용**으로 마운트한다. 쓰기가 필요한 순간은 없다 — 단어 사전은 정적이다.

## 무거운 의존성

`sentence-transformers` → `transformers` → `torch`. 수백 MB 이고, 백엔드가 Python 3.13 을 쓸 수 있느냐를 결정하는 유일한 요인이다. [[0008-python-313-torch-pin]] 참조.

워커에는 이 의존성이 없다. 그것이 워커를 분리한 실질적 이득 중 하나다.

## 임베딩 데이터

기존 `CLAUDE.md` 는 `chroma_words` 가 "4,802 단어 × 768-dim" 이라고 적었다. **2026-07-09 실측 결과 단어 수는 맞다** — `lotto_word` 컬렉션의 `count()` 가 정확히 4,802 다. 차원 수는 아직 확인하지 않았다.

컬렉션의 각 문서는 단어 자체이고(`ids` 와 `documents` 가 같다), 메타데이터는 `lotto_number`(`"[5, 33, 39]"` 형태의 **문자열**)와 `importance`(문자열 숫자)다. `searcher.py` 의 `_parse_lotto_number` 가 그 문자열을 파싱하는 이유가 이것이다.

**단어 목록만 필요하면 `DreamSearcher` 를 거치지 않는다.** `chromadb.PersistentClient(...).get_collection(...).get()` 은 임베딩을 만들지 않으므로 SentenceTransformer 를 로드하지 않는다. `/api/dream/keywords` 가 20초 함정을 피하는 방법이다 (`backend/app/dream/keywords.py`).
