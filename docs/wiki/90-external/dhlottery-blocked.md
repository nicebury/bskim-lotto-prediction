# 동행복권 공식 API 차단과 네이버 위젯 대체

로또 회차 데이터를 어디서 가져오는지에 대한 함정 기록이다. 뉴스 수집(`[[naver-search-api]]`)과는 다른 소스다.

## ⚠ 수집 정책이 미결이다 — 확장 전에 읽는다 (2026-07-09)

**`search.naver.com/robots.txt` 는 `User-agent: * / Disallow: /` 로 전면 금지다.** 지금의 위젯 파싱이 여기에 해당한다. 이 사실을 확인한 뒤 **과거 회차 백필을 중단했고, 수집 범위 확장(등위별·판매점)은 보류했다.**

역설이 있다. **정당한 원본(`dhlottery.co.kr`)의 robots.txt 는 `/resources/` 와 `/winImages/` 만 금지해 나머지를 허용하는데, 그 사이트가 접근을 차단하고 있다.** 접근 가능한 경유지(네이버)는 전면 금지고, 허용된 원본은 닫혀 있다.

### 사람이 판단해야 할 것

이것은 기술 문제가 아니라 정책·법률 문제다. **개발자가 아니라 사용자가 결정한다.**

- **네이버 이용약관·`robots.txt` 위반 여부**와 그 위험 수준. 국내 관련 판례: 잡코리아 v 사람인(크롤링에 대한 데이터베이스제작자 권리 침해 인정), 야놀자 v 여기어때(형사).
- **저작권법상 데이터베이스제작자의 권리**(제91~98조). 개별 사실(당첨번호·금액)은 저작물이 아니지만, **상당한 투자로 구축한 DB 의 "상당한 부분"** 을 복제·전송하면 창작성과 무관하게 침해가 된다. 회차 하나를 보는 것과 전 회차 + 등위 + 판매점을 통째로 적재하는 것은 이 기준에서 다르다.
- **판매점 상호·주소**는 개인정보는 아니나 특정 업소의 영업에 직접 닿는다. 광고 수익이 붙는 서비스라면 위험도가 다르다.
- **동행복권에 데이터 이용을 정식 문의**하는 선택지. 가장 안전하고, 공식 API 복구 여부도 함께 확인된다.

"공개된 정보이므로 자유롭게 이용할 수 있다" 는 **성립하지 않는다.** 공개 여부와 이용 권리는 별개다.

### 결정 전까지

- 신규 회차 수집(`lotto` 잡)은 회차당 요청 1~2회로 **유지한다.**
- **과거 회차 대량 백필을 재개하지 않는다.**
- **등위별(`lotto_prize`)·판매점 수집을 시작하지 않는다.** 소스에 데이터가 있다는 것과 담아도 된다는 것은 다르다.

## 증상

동행복권 공식 API(`https://www.dhlottery.co.kr/common.do`)를 호출하면 데이터가 오지 않는다. 모든 `.do` 경로가 `/errorPage`(사실상 메인 페이지)로 302 리다이렉트된다. 특정 클라이언트만이 아니라 **전 클라이언트 대상**이다. (2026-04 확인.)

## 원인

동행복권이 공식 API 를 전면 차단한 상태다. `common.do?method=getLottoNumber` 같은 기존 JSON 엔드포인트가 더 이상 응답하지 않는다. 복구 여부는 모니터링 중이나 재개 시점은 미정이다.

## 해법 — 네이버 검색 위젯 HTML 파싱

공식 API 대신 **네이버 검색 위젯의 HTML 을 정규식으로 파싱**한다. 구현은 `backend/app/naver_source.py`(향후 `worker/` 로 이동).

### 요청

```
GET https://search.naver.com/search.naver?query=로또 {N}회
follow_redirects=True
```

`{N}` 은 회차 번호. 브라우저 유사 `User-Agent` / `Accept-Language: ko-KR` / `Referer` 헤더를 붙인다.

### 파싱 규칙

- **당첨번호 7개**: `class="ball type\d"` 패턴에서 숫자를 추출한다. 앞 6개가 당첨번호, 7번째가 보너스다.
- **미추첨 판정**: 추출된 balls 가 **7개 미만이면 `None` 반환**(아직 추첨되지 않은 회차). 크롤러는 `None` 을 받으면 증분 수집을 정상 종료한다.
- **회차+날짜 컨텍스트 검증**: 추첨일은 요청한 회차 번호와 같은 컨텍스트에서 `{N}회차 (YYYY.MM.DD)` 형태로 매칭한다. 회차 컨텍스트에서 날짜를 못 찾으면 위젯에 그 회차가 없는 것으로 보고 `None` 을 반환한다. 엉뚱한 회차의 날짜를 주워 담지 않기 위한 방어다.
- **1등 당첨금(1인당)**: `1등 당첨금 ... N원` 패턴.
- **1등 당첨자 수**: `1등 당첨자는 (총|모두) N명` 또는 `당첨 복권수 N개` 대체 패턴.

### 위젯이 실제로 제공하는 것 — 기존 기록이 틀렸다 ★

이 페이지는 오랫동안 "등위별(2~5등) 정보가 위젯에 없다" 고 적어 왔고, `[[db-schema]]` 의 `lotto_prize` 가 "당분간 비어 있다" 는 근거도 그것이었다. **틀렸다.** 1230회차 위젯 HTML 을 직접 파싱해 확인했다 (2026-07-09).

위젯에 **있는** 것:

| 항목 | 실측 예시 (1230회) |
|------|------------------|
| 당첨번호 6 + 보너스 | `3 8 9 22 28 42` + `45` |
| 1등 당첨금·당첨게임 수 | `1,771,357,196원` / `16개` |
| **등위별 1~5등** 총 당첨금·당첨게임 수·1개당 당첨금 | 2등 `52,484,658원` / `90개` … |
| **자동/수동/반자동 분포** | 자동 15, 수동 1, 반자동 0 |
| **1·2등 배출점** 상호·주소·당첨게임 수 | `나누리로또` / `경북 경산시 성암로15길 4 1층` / 1개 |
| 출처 표기 | `제공 동행복권` |

위젯에 **없는** 것 — 여전히 항상 NULL 이다.

- `total_sell_amt` (총 판매금액)
- `first_accum_prize_amt` (1등 누적 상금)

UI 에서는 이 둘을 `-` 로 표시한다.

**즉 `lotto_prize` 가 비어 있는 이유는 이제 "소스가 없어서" 가 아니라 "수집 정책이 미결이어서" 다.** 위의 미결 절을 본다. `[[db-schema]]` 의 해당 서술도 정정했다.

용어 주의: 위젯과 동행복권은 **"당첨게임 수"** 를 쓴다. `lotto_prize.winner_cnt`(당첨자수)와 엄밀히 같은 개념이 아니다 — 한 사람이 여러 게임을 살 수 있다. 수집을 시작한다면 이 차이를 컬럼 코멘트에 반영해야 한다.

1등 당첨금·당첨자 수는 위젯에 있지만, SQLite 시절 과거 회차를 수집할 때 긁지 않아 비어 있다 — 아래 백필 절.


### 봇 감지 완화

네이버에 부담을 주지 않도록:

- 요청 간 **2.0초 + 0~0.8초 지터** 대기.
- 실패 시 **최대 3회 재시도**, 재시도 간격 **3초**.

이 값들은 `config.py`(`CRAWL_DELAY_SEC`, `CRAWL_MAX_RETRY`, `CRAWL_RETRY_DELAY_SEC` 등)에서 온다. 코드에 박지 않는다.

## 과거 회차 1등 정보 백필 (enrich)

**공식 API 를 기다릴 필요가 없는 부분이 있다.** `first_prize_amt` 와 `first_winner_cnt` 는 위젯이 지금도 준다. 이관된 과거 회차에 이 둘이 비어 있는 것은 소스의 한계가 아니라 **당시 수집 코드가 긁지 않았기 때문**이다.

이관 직후 실측 (2026-07-09):

| 연도 | 회차 | `first_prize_amt` NULL | `first_winner_cnt` NULL |
|------|-----|---------------------|----------------------|
| 2026 | 27 | 0 | 1 |
| 2025 | 52 | 52 | 52 |
| 2024 이전 | … | 전부 | 전부 |

→ 회차를 하나씩 다시 조회해 **NULL 인 컬럼만** 채우는 **1회성 작업**으로 시도했다.

## ⚠ 백필은 중단되었다 (2026-07-09)

**253/1,231회차까지 채운 상태에서 중단했다.** 위의 robots.txt 사실을 확인했기 때문이다. 마지막으로 도달한 회차는 908회다.

작업은 **멱등**이므로(NULL 인 컬럼만 `COALESCE` 로 채운다) 정책이 정해지면 같은 방식으로 이어서 돌릴 수 있다. 재개하지 않기로 하면 나머지 회차의 1등 정보는 `-` 로 표시한다.

스크립트는 **저장소에 남기지 않았다.** `worker/scripts/` 에 두면 반복 실행 가능한 자산으로 보이고, 크론에 올릴 유혹이 생긴다. 1회성 작업은 1회성으로 남긴다.

**이것은 잡이 아니다.** 과거 데이터의 구멍을 메우는 일이지 반복 수집이 아니다. 앞으로 들어오는 회차는 `lotto` 잡이 처음부터 1등 정보를 함께 저장한다.

### 규칙

- **이미 값이 있으면 덮지 않는다.** `COALESCE` 로 NULL 만 채운다. 중단 후 재실행해도 안전하다(멱등).
- **당첨번호로 회차를 대조한 뒤에만 UPDATE 한다.** 위젯이 엉뚱한 회차를 주면 1234회 행에 1233회의 당첨금이 박힌다. 번호 6개와 보너스가 DB 와 모두 일치할 때만 쓰고, 어긋나면 건너뛰며 경고한다. **이 방어가 없으면 조용히 오염된다** — 당첨금은 사람이 눈으로 틀렸는지 알 수 없는 값이다.
- `updated_dttm` 을 갱신한다. 무엇이 언제 보강됐는지 남긴다.
- 실패한 회차는 건너뛰고 계속한다. 한 회차 때문에 전체를 멈추지 않는다.

### 요청 간격 — 배치는 배치의 간격을 갖는다

증분 수집은 보통 한두 회차만 긁지만 백필은 **수백 회차를 연속으로** 긁는다. `lotto` 잡의 간격(2.0초 + 지터)을 그대로 쓰면 트래픽 양상이 완전히 달라져 봇으로 보인다.

중단 전까지 실제로 쓴 값. 재개한다면 이 값을 그대로 쓴다.

| 항목 | 값 | 이유 |
|------|-----|------|
| 요청 간격 | 4.0초 + 0~3.0초 지터 | 평균 5.5초. 규칙적인 간격은 사람으로 보이지 않는다 |
| 묶음 휴식 | 40회차마다 45~90초 | 사람은 쉬지 않고 수백 번 클릭하지 않는다 |
| 연속 실패 중단 | 5회 | 차단당했는데 계속 두드리지 않는다 |
| `429`/`403` | 즉시 중단 | 속도 제한·차단 신호를 무시하지 않는다 |
| 회차당 재시도 | 2회 (간격 8초) | 실패하면 건너뛰고 계속한다 |

**끝내는 속도보다 차단당하지 않는 것이 중요하다** — 차단되면 `lotto` 잡의 주간 수집까지 함께 죽는다.

253회차를 처리하는 동안 `429`·`403`·연속 실패는 **0건**이었고 당첨번호 불일치도 **0건**이었다. 즉 중단은 기술적 실패가 아니라 **정책 판단**에 따른 것이다.

### 번호 대조 방어가 실제로 값을 지킨다

백필된 253회차의 1등 당첨금은 7.4억 ~ 62.6억(평균 22.5억), 당첨자 3~24명으로 실제 로또 분포와 부합했다. 이상치 0건. **당첨금은 사람이 눈으로 틀렸는지 알 수 없는 값**이므로 번호 대조 없이는 이 확인이 불가능하다.

## 공식 API 복구 시

동행복권 API 가 복구되면 위젯에 없던 필드를 되살릴 수 있다.

- `total_sell_amt` / `first_accum_prize_amt` 를 채우는 **enrich 스크립트**를 추가한다(기존 회차 백필).
- 등위별 데이터로 `lotto_prize` 를 채운다.

단, 회차 번호·당첨번호 자체는 위젯 파싱으로 이미 확보되므로 소스 전환은 enrich 성격이지 재수집이 아니다.
