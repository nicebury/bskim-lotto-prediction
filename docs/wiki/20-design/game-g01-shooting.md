# G01 · 오리 사격장

**이 문서와 [[playground-game-contract]] 만 읽고 구현한다.** 다른 게임의 코드를 읽지 않는다.
소유 범위는 `frontend/src/games/g01-shooting/` **뿐이다.**

| 항목 | 값 |
|------|-----|
| slug | `shooting` |
| stage | 360 × 440 (논리 좌표) · 2026-09-16 에 560 에서 줄였다 |
| 유형 | **은닉형** — `pool.awardHidden()` |
| 목표 시간 | 75초 |
| accent | `reco` |
| 예상 규모 | 약 450줄 |

## 한 문장

컨베이어 위를 지나는 오리 여섯 마리를 조준해 맞히면, 오리가 물고 온 번호가 공개된다.

## 화면 구성

- **상단 20%** — 천막 차양(반원 arc 8개, `--svc-reco` 와 흰색 교대) + 전구 줄(원 12개,
  `timeMs` 로 순차 점멸). 맞힌 오리가 올라가는 **트로피 선반**도 여기.
- **중앙 60%** — 컨베이어 3줄(y = 165 / 237 / 309, 간격 72). 각 줄은 사다리꼴 벨트 + 대각선
  줄무늬가 `beltOffset` 만큼 흐른다. ⚠ 원안은 175 / 255 / 335(간격 80)였고 무대 축소로
  내렸다 — 아래 개정 절 참조.
- **하단 20%** — 나무 결 카운터 + 조준 정보. 발사 버튼은 호스트가 캔버스 밖 DOM 으로 그린다.

## 번호 획득

명중 판정이 성립한 **그 프레임에** `pool.awardHidden()` 을 부른다.
오리가 뒤집혀 튀어오르며(0.5초, `easeOutCubic`) 트로피 선반으로 날아가고, 도착 시
`mysteryBall` → `ball(n)` 로 0.3초 페이드 교체한다.

**은닉형이라 중복이 구조적으로 불가능하다.** 사용자는 오리의 번호를 미리 알 수 없으므로
호스트가 남은 풀에서 뽑아도 아무 모순이 없다. 재투 처리를 구현할 필요가 없다.

## 물리와 수치

- 오리 히트박스 타원 `rx=22, ry=15`.
- 레인 속도 `[46, 62, 78] px/s`. 방향은 레인별 교대(→, ←, →). 간격 120px,
  화면 밖 40px 에서 재진입한다. **오리 배열 6마리를 재사용**한다(GC 방지).
- **조준** — 포인터 위치가 곧 십자선. `x ∈ [24, 336]`, `y ∈ [150, 390]` 로 클램프.
  키보드는 방향 action 홀드로 260 px/s 이동.
- **발사** — `action primary down`. 쿨다운 0.35초.
  **히트스캔이다(탄속 없음).** 모바일에서 리드샷을 요구하면 난이도가 폭발한다.
  오리가 움직이므로 "누르는 타이밍" 자체가 실력이 된다.
- **명중 판정** — `ellipseHit(탄착점, duck.x, duckHitY(d), 22, 15)`.
  조준 관용(aim assist)을 주지 않는다. ⚠ 2026-09-17 부터 탄착점은 조준점 **중심이 아니라**
  산포 원 안의 임의 지점이다(아래 개정 절).
- **실탄 12발.** `emit({type:'attempt', used, total:12})` 로 HUD 에 표시.
  소진 시 **무제한 재장전 버튼**(1.0초 애니메이션). 탄약으로 게임을 끝내지 않는다.
- 빗나가면 그 레인 속도 ×1.06(놀란 오리). 상한은 초기값의 1.5배.

## 난이도 곡선

명중할 때마다 전체 레인 속도 ×1.05, 상한 1.45배. 여섯 번째 오리는 초기 대비 약 28% 빠르다.

## 아트 디렉션 (코드로 그린다)

**오리** — 몸통 타원(`rx22 / ry15`, `--svc-reco` 계열) + 머리 원(`r10`, 중심에서 `+14, −12`)
+ 부리 삼각형(주황, 3점) + 눈 점(`r2`, 흰 하이라이트 `r0.8`) + 날개 아크(2차 베지어 1개)
+ 꼬리 삼각형. 명중하면 눈을 `×` 로 바꾸고 회전각을 준다.

**컨베이어** — 사다리꼴 + 톱니 원 2개(회전).

**배경** — 야시장 실루엣(사각형 5개 + 천막 삼각형 3개, α0.18) 패럴랙스.
정적이므로 **오프스크린 캔버스에 한 번 그려 캐시**한다.

시각 언어 4대 규칙(배경 3층 · 접지 그림자 · 좌상단 광원 림라이트 · 숫자는 `ball()` 로만)을
지킨다.

## 실패·재시도

**실패 개념이 없다.** 탄약이 떨어져도 재장전하면 그만이고, 모은 번호는 잃지 않는다.
"12발 안에 6마리" 배지만 성취 표시로 남긴다.

## 완료 기준

[[playground-game-contract]] 의 공통 완료 기준에 더해:
- 키보드(방향키 조준 + 스페이스 발사)만으로 6마리 완주 가능.
- 세 레인의 오리가 화면 밖에서 겹치지 않고 순환한다.
- 명중 연출 중에도 다른 오리가 계속 움직인다(연출이 게임을 멈추지 않는다).

## ★ 2026-09-16 개정 — 무대를 560 → 440 으로 줄였다

계약이 *"`stage.height` 는 420~450 안에서 끝낸다"* 를 정한 뒤로 **이 무대만 560 으로 남아
있었다.** 다른 다섯은 이미 430 이다. 그 규칙은 취향이 아니라 **세로가 길수록 모바일에서
가로가 좁아지기 때문**이다 — 호스트가 높이를 먼저 제한하고 남은 높이에 `aspect-ratio` 를
곱해 폭을 정한다.

조준 게임에서 화면 폭은 곧 조작 정밀도다. 히트박스(가로 반경 22px)와 흔들림(±4.5px)이
논리 좌표로 고정돼 있으므로, 화면이 좁을수록 **같은 22px 을 더 적은 실제 픽셀로 겨눠야**
한다. 여섯 중 조준이 가장 정밀한 게임이 가장 좁은 화면을 쓰고 있었다.

### 120px 을 어디서 뺐는가

| 부위 | 전 | 후 |
|---|---|---|
| 레인 간격 | 80 | **72** (2칸 = 16px) |
| 카운터 높이 | 112 | **80** (32px) |
| 벨트 두께(`BELT_DY`+`BELT_H`) | 20 + 14 | **17 + 12** (레인당 5px) |
| 차양·전구·선반 | 44 / 56 / 86 | **36 / 48 / 76** (10px 위로) |
| 조준 범위 y | 142~390 | **130~348** |

**오리 크기·점프 높이·레인 속도·쿨다운·탄약·꽝 개수는 한 값도 건드리지 않았다.** 그것들을
만지면 난이도가 함께 바뀌어 "무대만 줄였다" 가 아니게 된다. 실측으로 맞춰 둔 완주율이
그대로여야 한다.

⚠ **레인 간격 72 는 점프 높이 24 에서 나온 하한이다.** 아래 레인 오리가 뛰어오른 상단과 위
레인 벨트 하단 사이가 정확히 **1px** 이다(165+17+12 = 194 vs 237−3−24−15 = 195). 간격을 더
줄이거나 점프를 더 높이면 **뛰는 오리가 위 벨트를 뚫고 올라간다.** 둘 중 하나를 바꾸려면
나머지 하나를 함께 계산한다.

⚠ **배경 실루엣 높이도 지평선과 함께 내려야 한다.** 처음에 건물 높이(60~138)를 그대로 두었더니
지평선이 448 → 360 으로 올라온 만큼 **실루엣이 컨베이어 한가운데까지 치솟아** 오리·벨트와
겹쳐 화면이 어지러웠다. 축소 비율(0.79)을 곱해 46~108 로 낮췄다. 배경은 뒤로 물러나 있어야
조준 대상이 먼저 읽힌다.

## ⚠ 테마 전환이 캔버스 무대에 반영되지 않던 것을 고쳤다 (2026-09-16)

`ctx.palette` 는 **`create()` 시점의 스냅샷이다.** 호스트(`GameCanvas`)가 `watchPalette` 로
갱신하는 것은 자기 지역 변수뿐이고, 이미 만들어 넘긴 컨텍스트 객체는 옛 색을 계속 가리킨다.
매 프레임 `ctx.palette` 를 다시 읽어도 소용이 없다 — **같은 객체다.**

`DrawKit` 만은 `() => palette` 클로저라 최신 색을 본다. 그래서 **볼만 테마를 따라가고 무대
(배경·차양·컨베이어·카운터)는 옛 테마로 남았다.** G04 가 먼저 부딪혀 [[playground]] 에 적어
둔 결함이고 고치는 쪽은 호스트지만, 그때까지 게임이 스스로 막는다 — `readPalette()` 를
**1초에 한 번** 직접 읽는다.

- ⚠ 폴링인 이유: 테마 변경을 게임에 전달하는 통로가 계약에 없다(`GameInstance` 에
  `onPalette` 가 없다). `types.ts` 는 동결이라 넣을 수도 없다.
- ⚠ 1초면 충분하다. `readPalette()` 는 `getComputedStyle` 로 20여 개 변수를 읽는다 — 매
  프레임 부르면 그 자체가 프레임 예산을 먹는다. 테마 전환은 사람이 누르는 일이다.
- **검증**: 플레이 중 `data-theme` 을 바꾸고 캔버스 픽셀을 직접 읽었다. 카운터
  `253,239,216 → 54,43,28`, 하늘 `249,250,252 → 18,22,32`. **폴링을 끄면 두 값이 그대로**여서
  (반증) 결함이 실재했고 이 수정이 그것을 고친 것임이 확인된다.

## 눈으로 보고 잡은 시각 결함 둘 (2026-09-16)

무대 축소와는 별개로, 넓어진 화면에서 드러난 것들이다.

1. **선반 빈 칸 여섯 개가 라이트에서 보이지 않았다.** `surface2` 는 라이트에서 흰색에 가까워
   **흰 배경 위에 흰 원**을 그린 꼴이었고, "여섯 칸을 채운다" 는 목표가 화면에서 사라졌다.
   글자색 α0.07 로 바꾸니 라이트에서는 옅은 회색, 다크에서는 옅은 밝은 판이 되어 양쪽에서
   같은 정도로 읽힌다.
2. **차양이 "주황 블록 네 개" 로 보였다.** 스캘럽 여덟 개가 `--svc-reco` 와 흰색 교대인데
   흰 쪽이 배경에 묻힌다. α0.35 테두리 한 줄로는 부족했다 — 아주 옅은 주황(α0.1)을 덧칠해
   **연주황 ↔ 진주황 교대**로 만들었다.

## 계약 정합 정리 (2026-09-16)

`failed` 팝업에서 **제목을 보내던 것을 뗐다.** 호스트 `defaultCopy()` 가 여섯 게임 공통
제목을 갖고, 게임이 채우는 것은 *게임마다 달라야 하는 것* 뿐이다(계약 2026-09-16 정본).
몇 개를 모았는지는 이 판에서만 아는 값이라 `text` 로만 덮는다.

## ★ 2026-09-17 개정 — 조준이 끝나야 발사된다 (사용자 요청)

### 왜 바꿨나 — 그리고 한 번 더 바꿨나

**"단순 클릭을 해도 총이 발사된다."** 줌이 순수 시각 효과였기 때문에 누르자마자 떼는 것이
언제나 최적이었다 — 기다리면 오리만 멀어질 뿐 정확도는 그대로였으므로, **조준이라는 행위가
게임에서 통째로 빠져 있었다.**

**처음에는 원을 *산포 범위*로 만들었다.** 덜 좁힌 채 쏘면 탄이 원 안 어딘가로 흩어지게 한
것이다. 그런데 **같은 지적이 다시 돌아왔다** — *"여전히 그냥 클릭해도 바로 발사된다."*

이유가 분명하다. **탄이 나가기는 하기 때문이다.** 흩어져서 빗나간 것과 애초에 안 나간 것은
손끝에서 전혀 다르게 느껴진다. 전자는 *"운이 나빴다"* 로 읽혀 **조작을 바꿀 이유가 되지
못한다** — 사용자는 같은 방식으로 계속 누르고, 결과만 나빠진다.

**그래서 확률을 조절하는 대신 조건을 걸었다.** 조준이 끝나기 전에 떼면 **발사 자체가
실패한다.** 규칙이 "확률이 나빠진다" 가 아니라 "아직 못 쏜다" 이면 배울 것이 하나뿐이다 —
**기다렸다 뗀다.**

> **교훈:** 조작을 바꾸게 하려면 **결과를 나쁘게 만드는 것으로는 부족하다.** 그 조작이
> 아예 성립하지 않아야 한다. 확률로 벌을 주면 사용자는 운을 탓하지 자기 조작을 보지 않는다.

### 무엇이 바뀌었나

| | 개정 전 | 개정 후 |
|---|---|---|
| 줌의 의미 | 순수 장식 | **발사 조건**. 다 좁혀져야 쏠 수 있다 |
| 조준 전에 떼면 | 그대로 발사 | **발사되지 않는다.** 탄약도 줄지 않는다 |
| 십자 크기 | 3.4배로 커졌다 좁혀짐 | **고정.** 좁혀지는 것은 바깥 원뿐 |
| 조준 중 색 | 빨강 | **흐린 보조색** — 준비되지 않았다는 신호 |
| 조준 완료 | (표시 없음) | **빨강으로 바뀌고 링이 한 번 번쩍인다** |
| 좁혀지는 곡선 | `easeOutCubic` | **선형** |
| 키보드 | 스페이스 누르면 즉시 발사 | **누른 채 조준 → 떼면 발사**(포인터와 같은 규칙) |

- ⚠ **실패에 탄약을 물리지 않는다.** 실패는 "아직 못 쏜다" 이지 벌칙이 아니다. 여기서 탄이
  줄면 규칙을 모르는 첫 판에 12발을 빈손으로 날리게 되고, 그건 **배우기 전에 지는 것**이다.
  쿨다운도 걸지 않아 바로 다시 조준할 수 있다.
- ⚠ **이것은 조준 관용(aim assist)이 아니다.** 관용은 빗나간 탄을 몰래 맞게 해 주는 것이고,
  이쪽은 조건을 채우기 전에 쏘지 못하게 하는 것이다. 맞고 안 맞고는 **여전히 겨눈 자리로만**
  갈린다 — 산포도 보정도 없다.
- ⚠ **십자는 크기를 고정한다.** 십자까지 함께 커지면 "조준점이 크다" 로만 읽히고 *무엇이*
  줄어드는지가 보이지 않는다. 십자는 겨눈 한 점, 원은 남은 시간 — **역할이 다른 둘을 한
  덩어리로 키우면 둘 다 뜻을 잃는다.**
- ⚠ **색만으로 전하지 않는다**(계약). 조준 중↔완료는 색(보조색↔빨강)뿐 아니라 **형태**로도
  갈린다 — 점선 원이 사라지고 중심 점이 굵어진다.
- ⚠ **`easeOutCubic` 을 쓰지 않는다.** 초반이 빨라 0.25초 만에 원이 34 → 9px 로 줄어 **거의
  다 된 것처럼 보이는데 실제로는 아직 못 쏘는 상태**가 된다. 선형이면 남은 거리가 곧 남은
  시간이다.
- ⚠ **키보드도 같은 규칙이다.** 포인터만 기다리게 하고 키보드는 즉시 쏘게 두면 규칙이 둘이
  되고 그쪽이 더 쉬워진다. 방향키는 조준점 이동(원 없음), 스페이스 홀드가 조준이다.
  ⚠ 방향키로 미세 조정하는 동안 `aimZoom` 을 건드리면 **겨냥을 고칠수록 못 쏘게 되는**
  모순이 되므로, 스페이스를 누르고 있는 중에는 방향키가 조준을 되돌리지 않는다.
- ⚠ **`pointer up` 에서 판정을 먼저 하고 리셋한다.** 순서를 뒤집으면 `aimZoom` 이 1로 돌아간
  뒤 `shoot()` 이 불려 **언제 떼도 발사되어 이 규칙 전체가 무력해진다.**
- ⚠ 시작 버튼의 `up` 으로 **판이 시작하자마자 한 발 나가지 않도록** `keyHold` 를 확인한다.

### 검증

조준 시간 0.7초 기준, 누른 시간을 바꿔 가며 탄약이 실제로 줄었는지 쟀다.

| 누른 시간 | 0.00 | 0.10 | 0.30 | 0.50 | 0.69 | 0.71 | 1.00 | 1.50 |
|---|---|---|---|---|---|---|---|---|
| 포인터 | ✕ | ✕ | ✕ | ✕ | ✕ | **발사** | **발사** | **발사** |
| 키보드 | ✕ | ✕ | ✕ | ✕ | ✕ | **발사** | **발사** | **발사** |

경계가 정확히 0.7초에서 갈리고 **포인터와 키보드가 같다.** 실패 시 `status` 로
"아직 조준 중입니다. 조준점이 좁혀진 뒤에 손을 떼세요." 가 나간다.

### 흔들림이 느려서 "딜레이" 로 느껴졌다

주파수가 `sin(t*1.7)` 이라 **한 번 왕복에 3.7초**였다. 0.7초짜리 조준 구간에서는 위상이
1.2 rad 밖에 안 흘러 "떨린다" 가 아니라 "천천히 밀린다" 로 보였고, 그래서 *"줌인이 끝나야
흔들리기 시작한다"* 는 인상을 줬다(2026-09-17 사용자 보고). 실제로는 누르는 순간부터
흔들리고 있었고 **진폭도 그때가 가장 컸다.**

`4.7 / 7.3`(x) · `3.9 / 6.1`(y) 로 올렸다 — 주기 0.86~1.6초. 누르는 순간부터 떨림이 보인다.
⚠ 서로 배수가 아닌 값을 유지한다. 배수면 규칙적으로 왕복해 주기를 외울 수 있다.

### 조준 실패는 캔버스 안에서 말한다

캔버스 아래 `hint` 줄에도 같은 말이 있지만 **그때 눈은 오리와 조준점에 있다** — 화면 밖
글자는 읽히지 않는다. 조준했던 자리 옆에 1.1초짜리 말풍선을 띄운다.

⚠ **"탄약은 그대로" 를 함께 말한다.** 그 말이 없으면 "한 발 손해 봤다" 고 오해하고, 그
오해가 다음에도 급하게 쏘게 만든다.

### 시작 팝업에 조작법을 적는다

캔버스 아래 "조작 방법" 목록이 이미 있지만, **시작 버튼을 누르는 사람의 눈은 팝업에 있다.**
거기 없으면 읽지 않은 채 판이 시작되고, 그러면 누르자마자 떼는 조작이 굳어 버린다.
⚠ 두 문장을 넘기지 않는다 — 팝업이 캔버스를 덮으므로 길어지면 게임 화면을 가린다.

`catalog.ts` 의 `howTo` 둘째 줄에도 산포 규칙을 넣었다. 규칙이 안내에 없으면 사용자는
기다릴 이유를 모른 채 연타한다.

## ⚠ 오리가 간간이 깜빡이던 것을 고쳤다 (2026-09-17)

화면 밖에서 되돌아올 때(`WRAP`) **`d.x` 만 옮기고 `d.prevX` 를 두고 갔다.** 그리기는
`lerp(prevX, x, alpha)` 로 두 값을 보간하므로, 그 프레임에 **399 → −40 을 잇는 선분 위
어딘가**가 나온다 — 오리가 화면 한가운데 한 프레임 나타났다 사라진다.

레인당 4~8초에 한 번, 여섯 마리면 대략 1초에 한 번 꼴이라 *"보였다 안 보였다"* 로 보였다.

**순간이동은 위치를 두 값 다 옮겨야 보간에도 순간이동으로 남는다.**

⚠ **보간을 쓰는 다른 게임도 같은 지점을 본다.** 좌표를 감싸거나(wrap) 순간이동시키는 코드가
있으면 `prev` 를 함께 옮겼는지 확인한다. 이 결함은 **`alpha`(보간 계수)가 1일 때는 드러나지
않는다** — 검증에서 `alpha` 를 0.5 로 줘야 잡힌다.

**검증**: 90초 · `alpha` 0.5 로 실제 모듈을 돌려 프레임당 이동량을 쟀다. 수정 후 최대
**1.65px**(허용 6px)에 튀는 프레임 **0건**, 되돌리면 **190건 · 최대 219px** 이다.

## ⚠ 2026-09-16 개정 — 누른 채 조준, 떼면 발사 (사용자 요청)

### 조준 방식을 모바일 기준으로 다시 짰다

**누르는 순간 발사하던 것을 "누른 채 조준 → 떼면 발사" 로 바꿨다.** 작은 화면에서 누르는
순간 쏘면 손가락이 처음 닿은 지점으로 나가 조준이라는 것이 성립하지 않는다.

| | 개정 전 | 개정 후 |
|---|---|---|
| 조준점 | 항상 떠 있음 | **누르는 동안에만** 보인다 |
| 발사 | `pointerdown` | **`pointerup`** |
| 누른 직후 | — | 조준점이 3.4배로 나타나 **0.7초에 걸쳐 원래 크기로 좁혀진다** |
| `pointercancel` | — | **발사하지 않는다** |

- 평소에 조준점을 숨기는 이유: 모바일에서는 **손가락이 곧 조준점**이라 항상 떠 있는 십자선이
  오히려 방해가 된다. 키보드 사용자에게는 손가락이 없으므로 키를 한 번이라도 누르면 계속 보인다.
- ~~⚠ **줌인은 순수 시각 효과다.** 히트박스는 언제나 조준점의 중심 한 점이고, 다 좁혀지기
  전에 떼도 불이익이 없다.~~ → **2026-09-17 에 뒤집혔다.** 바로 그 이유로 조준이라는 행위가
  통째로 생략됐다(누르자마자 떼는 것이 최적이 된다). 이제 **바깥 원이 곧 산포 범위**이고
  덜 좁힌 채 쏘면 실제로 흩어진다 — 아래 [조준 원은 탄이 갈 수 있는 범위다] 절이 정본이다.
- ⚠ **취소는 발사하지 않는다.** `pointercancel` 은 iOS 스와이프·통화 알림처럼 사용자가

- ⚠ 캔버스 `pointerdown` 은 `pointer down` 과 `action primary down` 을 **둘 다** 보낸다
  (계약: 입력 절). 그래서 `action primary down` 은 **키보드 발신만** 발사로 처리한다 —
  안 그러면 한 번 누를 때 두 발이 나간다.

### 조준점이 흔들린다 (2026-09-16 추가)

스코프를 든 손은 멈추지 않는다. 조준점이 못처럼 박혀 있으면 "겨눈다" 는 행위가 사라지고 남는
것은 오리가 지나가기를 기다리는 일뿐이다. 조금 흔들리면 **언제 쏘느냐**가 다시 실력이 된다.

- 주파수가 서로 배수가 아닌 사인 둘을 겹친다. 하나만 쓰면 규칙적으로 왕복해 기계처럼 보이고
  사용자가 주기를 외워 버린다.
- 누른 직후(줌이 좁혀지는 동안) **더 크게 흔들리고 점점 가라앉는다** — 스코프가 자리를 잡는
  느낌이다. 이것은 **눈에 보이는** 차이지 숨은 명중 보정이 아니다. 급하게 쏘고 싶으면 그래도 된다.
- ⚠ **흔들림은 판정에도 그대로 적용된다.** 보이는 자리와 맞는 자리가 다르면 그것은 숨은 확률이고,
  사용자는 조작당했다고 느낀다. 조준점이 있는 곳이 곧 탄이 가는 곳이다.
- ⚠ 진폭이 **이 게임의 주 난이도 손잡이**다(`SWAY_X` **11px** · `SWAY_Y` **7px**).
  3.2 → 4.5 → 5.4 → **11** 로 세 번 올렸고, 마지막 전까지 계속 *"흔들리는 게 별로 영향이
  없어 보인다"* 는 말을 들었다. **값이 작아서만이 아니라 두 가지가 실효 이탈을 깎고 있었다.**

  ① **발사 시점의 `amp` 는 언제나 1이다.** `SWAY_SETTLE` 이 조준 중 진폭을 키우지만,
     **조준이 끝나야 발사되므로** 증폭이 걸린 상태로는 애초에 쏠 수가 없다. 그 배수는
     판정에 단 한 번도 관여하지 않는다 — 순수한 시각 효과다.
  ② **사인 둘이 서로 상쇄한다.** `0.6·sin a + 0.4·sin b` 의 최댓값은 1이지만 전형값(RMS)은
     **0.51** — 화면에서 실제로 보는 이탈은 대개 **진폭의 절반**이다.

  그래서 5.4px 일 때 전형 이탈이 2.8px, 히트박스 가로 반경 22px 의 **12%** 밖에 되지 않았다.
  겨냥이 조금 어긋나도 그대로 맞으니 흔들림이 없는 것과 다르지 않았다.

- ⚠ **조정할 때는 "진폭 ÷ 2 가 실효값" 으로 어림한다.** 진폭 그대로를 히트박스와 비교하면
  매번 과대평가하게 되고, 그것이 세 번이나 모자라게 잡은 원인이다.
- ⚠ **정확히 겨누면 여전히 맞는다.** 최대 이탈(11·7)이 히트박스(22·15)보다 작다. 어려워진
  것은 *대충 겨누는 것*이지 *제대로 겨누는 것*이 아니다. 진폭이 히트박스를 넘으면 그때부터는
  제대로 겨눠도 빗나가므로 **22/15 가 사실상 상한**이다.
- ⚠ 더 올릴 때는 **클램프 밖으로 새지 않는지** 함께 본다. 흔들림은 클램프된 `cross` 위에
  얹히므로, 조준 중 최대 진폭까지 더한 값이 조준 범위를 넘으면 조준점이 화면 밖이나 선반·
  카운터 위로 올라간다. 진폭을 11로 올리면서 `SWAY_SETTLE` 을 **1.2 → 0.6 으로 낮춘** 것이
  그 때문이다 — 판정에 무관한 시각 효과가 조준점을 밀어내면 그쪽이 더 큰 손해다.
- **실측**(40초 · 클램프 네 귀퉁이 + 가운데): 조준점이 닿은 범위 **x 13.0~347.4 · y
  123.0~357.0** 으로 화면(0~360)·선반 판자(103)·카운터(360) 어디도 침범하지 않는다.
  발사 가능 상태의 이탈은 **x 전형 4.7px(21%) 최대 11px(50%) · y 전형 3.0px(20%) 최대 7px(47%)**.
- 조준점 **십자선의 팔**(중심에서 20px)은 하한에서 카운터에 걸친다. 무대를 440 으로 줄이며
  생긴 것이고 그대로 둔다 — 조준점은 맨 마지막에 그려져 가려지지 않고, 겹침을 없애려면
  하한을 331 까지 올려야 해서 맨 아랫줄 오리 아래를 겨눌 여유가 사라진다.

### 맞은 오리가 다시 들어와야 하는 이유

**꽝을 넣는 순간 "오리 6마리를 없앤다" 는 구조가 무너진다.** 오리가 여섯인데 꽝이 두 번
나오면 번호는 최대 넷뿐이라 6개를 채우는 것이 **수학적으로 불가능**해진다. 그래서 맞은
오리는 날아간 뒤 레인 입구로 되돌아온다. 화면이 비어 가던 종전 문제도 함께 사라졌다.

### 꽝을 확률로 굴리지 않는 이유

매번 확률로 굴리면 운 나쁜 판에서 꽝만 다섯 번 나올 수 있고, 그때 사용자는 조작당했다고
느낀다([[0014-number-playground]] 가 크레인에서 확률형 실패를 금지한 것과 같은 이유).
**꽝 두 장을 넣은 봉투를 섞어** 뽑으면 최대 꽝 수가 보장된다 — 열두 발을 다 맞히면 번호
열 개를 얻으므로 6개는 반드시 채워진다.

### 빗나감 벌칙을 낮춘 이유

사양서의 ×1.06 은 **무제한 재장전이던 시절의 값**이다. 실패가 생기자 그것이 하향 나선이
됐다 — 못 맞히는 사람일수록 오리가 빨라져 더 못 맞힌다. 실측에서 네 판 중 세 판이
"하나 모자라서 실패" 로 끝났다. ×1.02 · 상한 1.32 로 낮추자 여섯 판 중 세 판 완주가 됐다.

### 꽝은 크고 오래 남아야 한다 (2026-09-10)

처음에는 날아가는 오리 위에 16px 짜리 "꽝" 을 0.5초 띄웠다. 결과는 **"꽝인지 뭔지 확인이
안 된다"** 였다 — 눈이 오리를 쫓는 동안 글자는 이미 사라져 있다. 셋을 함께 준다.

1. **충격파 링**(0.3초) — 터졌다는 사실을 주변시로도 알린다
2. **만화식 폭발 별 + 큰 "꽝"**(46px) — 튀어나왔다 자리를 잡는다
3. **"번호를 얻지 못했어요"** 한 줄 — "꽝" 만으로는 *무엇을 잃었는지* 알 수 없다

지속 시간은 **1.35초**이고, 마지막 18% 구간에서만 흐려진다. 그 전에는 또렷하게 남아 읽을
시간을 준다. 진동도 빗나감(10ms)보다 세게(40ms) 울린다 — 같은 세기면 손끝으로 구분되지 않는다.

⚠ **별을 `--color-warning` 으로 칠하지 않는다.** 그 토큰은 *연한 배경 위 경고 글자용*이라
라이트에서 어두운 갈색이다. 실제로 그렇게 칠했더니 별이 갈색 덩어리가 되고 그 위 어두운
글자가 통째로 묻혔다. 바깥은 `--svc-reco`(주황), 안쪽은 **공식 볼 1구간 노랑**으로 칠하고
글자는 `ballFgDark` 를 쓴다 — 사이트가 *그 노랑 위에는 그 글자색* 을 쓰도록 이미 정해 두어
대비가 라이트·다크 양쪽에서 보장된다.

⚠ **꽝은 가장 마지막에 그린다.** 파티클·조준선 아래에 두면 연기와 십자선이 글자를 가린다 —
실제로 조준선이 별 한가운데를 지나갔다.

### 시작·실패·완료 버튼은 캔버스가 아니라 DOM 이다

게임은 `emit({type:'phase'})` 로 단계만 알리고 호스트가 캔버스 위에 DOM 오버레이를 그린다.
캔버스에 그린 버튼은 스크린리더에 보이지 않고 탭으로 닿지도 않으며, 페이지 스크롤("번호보기")
과 인스턴스 교체("다시하기")는 애초에 캔버스가 할 수 없는 일이다.
규약은 [[playground-game-contract]] "진행 단계와 오버레이" 절에 있다.

### 소개글을 한 줄로 줄였다

상세 페이지는 제목·소개글이 캔버스 **위**에 얹히는 구조라, 네 줄짜리 소개가 모바일에서
게임을 화면 밖으로 밀어냈다 — 스크롤하지 않으면 플레이할 수 없었다. `intro` 를 한 문장으로
줄여 390×760 에서 "시작" 버튼까지 스크롤 없이 보인다.

## 구현 메모 (2026-09-08 · 구현 완료)

`frontend/src/games/g01-shooting/` 세 파일 1,231줄. 사양서의 수치는 그대로 옮겼고, 아래
넷은 사양서가 정하지 않았거나 **그대로 두면 모순이 생기는** 지점이라 판단해 결정했다.

### 오리 여섯 마리는 맞히면 사라진다 (재등장하지 않는다)

사양서의 "오리 배열 6마리를 재사용한다" 와 "여섯 마리를 맞히면 번호 6개가 모입니다" 를
그대로 읽으면, **화면의 오리 여섯 마리가 곧 번호 여섯 개**다. 레인당 두 마리씩 120px 간격,
맞으면 선반으로 날아가 목록에서 빠진다. 뒤로 갈수록 표적이 줄어 조준이 어려워지는 것이
난이도 곡선(명중마다 전 레인 ×1.05)과 같은 방향이라 따로 손대지 않았다.

세션 복원으로 이미 모은 번호가 있으면 **그만큼 오리를 줄여** 시작한다(`pool.slotsLeft`).
여섯 마리를 그려 놓고 셋만 맞을 수 있게 하면 화면이 거짓말이 된다.

### 재장전은 발사 버튼을 다시 누르는 것

사양서는 "무제한 재장전 버튼" 을 적었지만 계약이 보장하는 캔버스 밖 버튼은 `action primary`
하나뿐이다. 두 번째 버튼을 요구하면 호스트가 게임마다 다른 버튼 세트를 그려야 한다.
**탄이 0일 때 같은 버튼을 누르면 재장전**으로 해석하고, 그 사실을 `hint` 로 문장으로 알린다.

### 속도 상한은 1.5배 하나

사양서는 빗나감 1.5배·명중 1.45배로 따로 적었다. 그러나 명중은 최대 다섯 번뿐이라
`1.05⁵ = 1.28` 로 1.45 에 닿지 않고, 상한이 나뉘어 있으면 빗나감으로 1.5까지 오른 레인이
**명중하는 순간 1.45로 깎인다** — 맞혔는데 느려진다. 합쳐도 결과가 같아 하나로 뒀다.

### 패럴랙스의 기준은 조준선이다

사격장에는 스크롤하는 카메라가 없어 "패럴랙스 2겹" 의 기준이 없다. 조준선이 중심에서
벗어난 만큼 실루엣을 **반대로** 민다(먼 층 ×0.02, 가까운 층 ×0.045). 조준할 때만 배경이
아주 조금 움직여 깊이가 생기고, 움직임 최소화에서는 0 으로 고정된다.

### 실측

| 항목 | 결과 |
|---|---|
| 완주율 | 사람에 가까운 조준(반응 지연 200ms · ±9px 오차)으로 **여섯 판 중 세 판 완주**, 나머지도 4~5개. "이길 수 있지만 방심하면 실패" 를 목표로 맞춘 값이다 |
| 완주 시간 | 12발 × 쿨다운 0.35초 + 조준 시간. `paceSeconds` 를 75 → **60** 으로 낮췄다 |
| 중복 | 은닉형이라 **구조적으로 불가능**. 완주 6판에서 0건 |
| 검증 게이트 | 브라우저 표준 난수 · 화면배율 직접참조 · hex 리터럴 · 금지 식별자 · 루프 내 `shadowBlur` · `core` 외 import **전부 0건** |
| 다크모드 | 캔버스 안까지 따라간다. 볼 5구간 색은 불변 |
| 움직임 최소화 | 파티클 0 · 패럴랙스 정지 · 회전/포물선 없음. **물리와 이동은 그대로** |
| 키보드 | ← → ↑ ↓ 조준(대각선 정규화) + 스페이스 발사로 완주 가능 |

⚠ **`catalog.ts` 의 `keyGuide` 가 `↑ ↓` 를 빠뜨렸다.** 컨베이어가 세 줄이라 좌우만으로는
다른 두 줄에 닿을 수 없다. 게임이 `hint` 로 보완했지만 `keyGuide` 자체를 고치는 것이 맞다 —
호스트 소유 파일이라 손대지 않았다([[playground-game-contract]] 파일 소유 경계).
