# ★ 2026-09-17 전면 개편 — 사용자 지시 여섯 건

이 아래가 **현재 규칙이다.** 그 전(6개 통과 = 6개 수집 · 목숨 무제한)은 폐기됐고, 옛 규칙
시절의 실측치는 이 문서 맨 아래에 **무효 표기와 함께** 남겨 두었다.

사용자가 실제로 플레이해 보고 준 지적은 세 가지였다 — **어렵다 · 떨어지고 나면 바로 시작해서
또 떨어진다 · 안 눌렀을 때 낙하가 너무 빠르다.** 여기에 기회 9번 · 비행 거리 표시 ·
20개 배치 · 완주 후 계속 비행이 더해졌다.

## 기회 9번

**충돌 1회 = 기회 1 소모.** 파이프에 부딪히든 바닥에 닿든 같다.

- 기회가 남아 있으면 → `crashed` 상태로 **대기**(아래 [이어날기](#이어날기--자동-재개-폐지)).
- 9번을 다 쓰면 판이 끝난다.
  - 번호 6개를 다 모았으면 → `cleared`
  - 못 모았으면 → `failed`. `text` 만 `"n개를 모았습니다. 다시 도전해 보세요."` 로 덮는다
    (G01 선례. 제목은 호스트 기본값 `"6개 번호 모으기 실패"`).

⚠ **그래도 모은 번호는 잃지 않는다.** 개편 전 이탈 방지 장치 ②의 핵심이었고, 기회 제한이
생겨도 그 부분은 그대로다. 기회가 줄어드는 것은 **다시 날 수 있는 횟수**이지 전리품이 아니다.

⚠ `emit({type:'attempt', used, total:9})` 를 보내되 **캔버스 상단에도 직접 그린다** —
계약대로 호스트 HUD 가 아직 `attempt` 를 쓰지 않는다. 동시에 `status` 로도 알린다
(캔버스 글자는 보조기술에 투명하다).

## 비행 거리

**13px = 1m.** 전진 속도 130px/s 가 곧 **10m/s** 가 되고, 파이프 간격 260px 는 **20m** 다.
사람이 암산으로 옮길 수 있는 비율을 골랐다 — 화면의 거리감과 숫자가 어긋나면 표시가
장식이 된다.

- 캔버스 상단 HUD 에 `123m` 로 정수 표시.
- **충돌해도 거리는 리셋하지 않는다.** 한 판 전체의 누적 비행 거리다. 그래야
  [완주 후 계속 비행](#완주-후--계속-날건지-묻는다)이 노릴 대상이 된다.
- 최종 거리는 판이 끝날 때 `status` 로 한 번 말한다.

## 이어날기 — 자동 재개 폐지

개편 전에는 충돌 1.2초 뒤 **자동으로** 다시 날았다. 사용자가 그대로 지적했다 —
*"떨어지고 나면 바로 시작하는데 새가 바로 떨어지네."* 화면을 다시 읽기도 전에 중력이
걸려 있으니 연쇄 충돌이 났다.

이제 충돌 뒤 상태가 셋으로 나뉜다.

```
충돌 → crashed (세계 정지, "이어날기" 안내)
        ↓ 탭 / 스페이스
      hover   (중력 0. 새가 제자리에서 부유한다 — ready 와 같은 상태)
        ↓ 탭 / 스페이스
      flying  (그 탭이 곧 첫 날갯짓)
```

⚠ **`hover` 가 이 수정의 핵심이다.** "이어날기" 를 누른 순간 곧바로 중력이 걸리면 버튼만
하나 늘고 문제는 그대로다. 부유 상태를 한 단계 두어 **사용자가 파이프 위치를 보고 준비된
다음에** 날기 시작하게 한다. 시작 지점의 `ready` 와 완전히 같은 취급이다.

⚠ `crashed` 는 **탭할 곳을 가리지 않는다.** 화면 아무 데나 눌러도 되고 스페이스도 된다.
캔버스 안 버튼 그림은 "눌러야 한다" 는 신호이지 히트박스가 아니다 — 작은 화면에서 좁은
버튼을 맞히게 하는 것이 또 하나의 마찰이다.

⚠ 여전히 **부딪힌 파이프는 치우고** 재개하고, 재개 높이는 **다음 파이프의 간극 중심**에
맞춘다. 치우지 않으면 재개하자마자 같은 파이프에 다시 부딪힌다.

## 번호 획득 — 20개 중 여섯 개만 번호 링

개편 전에는 **링 = 번호**였다. 여섯 번 통과하면 그대로 끝나서, 사용자 표현으로
*"6개를 통과하면 무조건 6개를 모으게"* 되는 구조였다. 이제 링 대부분은 **꽝 링**이고
정해진 순번에서만 번호가 나온다.

**번호 링은 2 · 6 · 9 · 13 · 16 · 20 번째 링이다.** 난수가 아니라 **고정 배치**다.

| 왜 고정인가 | |
|---|---|
| 확률로 뽑으면 | 30% 확률로 6개를 채우는 데 운 나쁘면 40개를 넘긴다. 사용자가 *"잘 배치해야 할거 같아"* 라고 한 것이 바로 이 분산이다 |
| 첫 번호를 2번째에 | 첫 성공을 빨리 줘야 "이 게임이 뭘 주는지" 를 안다. 3~4개 간격은 그 뒤부터다 |
| 마지막이 20번째 | 지시대로 "20개정도는 통과해야 다 모으는" 값이다 |

- **꽝 링** — `reserve()` 하지 않는다. 무채색 링 + 빈 원. 통과하면 거리와 통과 수만 오른다.
- **번호 링** — 기존과 같다. 생성 시 `reserve()`, 구간 **색만** 보이고, 우측 끝을 지난
  프레임에 `commit` 하며 그때 볼이 깨져 번호가 드러난다(색 힌트형 계약).
- 통과하지 못하고 흘러간 번호 링은 `release` 한다.

⚠ **꽝 링과 번호 링은 생김새가 다르다.** 색 힌트형 계약이 숨기라고 한 것은 *번호*이지
*어느 링이 번호 링인지*가 아니다. 오히려 색 링이 다가오는 것이 보여야 긴장이 생긴다 —
꽝만 스무 개 지나가는 동안 아무 일도 없으면 그것이 지루함이다.

⚠ 6개를 다 모은 뒤(계속 비행 중)에는 **모든 링이 꽝 링이다.** 풀에 남은 번호를 예약할
이유가 없다.

## 완주 후 — 계속 날건지 묻는다

번호 6개를 채워도 **바로 끝내지 않는다.** 기회가 남아 있으면 캔버스에 두 갈래를 띄운다.

| 선택 | 결과 |
|---|---|
| **계속 날기** | 그대로 비행. 이후 링은 전부 꽝이고 **거리만 쌓인다** |
| **번호 확인** | `cleared` 를 보낸다. 호스트가 "다시하기 · 번호확인" 오버레이를 덮는다 |

⚠ **기회가 0이면 묻지 않는다.** 선택지가 하나뿐인 질문은 질문이 아니다. 곧바로 `cleared`.

⚠ **`cleared` 를 미루는 것이 이 절의 전부다.** 호스트는 `phase !== 'playing'` 인 동안 내내
캔버스를 오버레이로 덮으므로, 6개를 모은 순간 `cleared` 를 보내면 계속 날 방법 자체가 없다.
그래서 선택하는 동안 `phase` 는 `playing` 을 유지하고 **캔버스가 직접 묻는다.**

⚠ **계속 날 이유는 거리다.** 번호를 다 모은 뒤에 더 얻을 것이 없으면 아무도 "계속" 을
누르지 않는다. 지시 2(거리 표시)와 지시 6(계속 비행)은 한 쌍이다.

**선택 입력** — 캔버스 안 두 버튼이라 히트박스가 필요하다.

- 포인터: `pointer down` 좌표로 어느 버튼인지 정하고, 뒤이어 오는 `action primary` 에서 확정한다.
  ⚠ 호스트 `input.ts` 는 탭 한 번에 `pointer down` **과** `action primary down` 을 순서대로
  보낸다. 둘 다 처리하면 한 번의 탭이 두 번 먹는다.
- 키보드: `←` `→` 로 커서를 옮기고 스페이스로 확정. `keyGuide` 에 적는다.

## 물리와 수치

- 새 x 고정 110. 반지름 14, **충돌 판정은 `r=12` 로 관대하게.**
- 중력 **900** px/s², 날갯짓 임펄스 `vy = **−360** px/s`, 최대 낙하 **480** px/s.
  ⚠ 2026-09-17 에 1500 / −430 / 800 에서 낮췄다. 사용자 지적 — *"안 눌렀을때 떨어지는
  속도가 너무 빨라 게임이 너무 어려워."* 최대 낙하를 800 에서 480 으로 내린 것이 가장 크다.
  간극(175)의 절반을 떨어지는 데 0.36초 → **0.46초**가 되어 반응할 시간이 생긴다.
  ⚠ 임펄스도 함께 낮췄다(−430 → −360). 중력만 낮추면 한 번의 탭으로 천장까지 솟아
  이번에는 **위쪽이 어려워진다** — 상승 정점 높이는 62px → 72px 로 조금 늘어난 정도다.
- **전진 속도 130 px/s 고정.** 가속하지 않는다 —
  원본 플래피의 이탈 원인 1위가 후반 체감 가속이다.
- 파이프 폭 56, 수평 간격 260px → **2.0초에 하나**(= 20m).
- 수직 간극 `gap = 178 − 1.2k` (k = 통과 수) → 178 → **최소 160**.
  ⚠ 개편 전 `175 − 5k` 는 **여섯 개까지만 가는 판**의 계수였다. 이제 20개 이상을 지나므로
  같은 계수를 쓰면 8번째 링에서 이미 하한이고 뒤로 갈수록 벌 받는 느낌이 된다. 기울기를
  1/4 로 눕히고 하한을 160 으로 올렸다 — 새 지름 28 대비 **5.7~6.4배**다(원본 약 3.2배).
- 간극 중심은 **간극 크기에서 유도한다** — `min = gap/2 + 32` · `max = groundY − gap/2 − 32`.
  이전 중심 대비 변화량 **±90px 로 클램프**(연속 극단 배치 방지).
  ⚠ 원안의 고정 범위 `y ∈ [130, stage.h − 170]` 은 **무대 560 을 전제로 쓴 값**이다.
  계약이 무대 세로를 420~450 으로 못 박은 뒤로는 그대로 쓰면 하단 파이프가 지면 아래로
  내려간다. 위 식은 무대 560·간극 195 에서 `[127.5, 392.5]` 를 내어 **원안과 사실상 같다** —
  수치를 바꾼 것이 아니라 다시 유도한 것이다.
- **천장은 충돌이 아니라 클램프.** 바닥(`y = h − 40`)만 충돌.

## ★ 이탈 방지 — 개편 후

1. **첫 파이프는 3.0초 뒤**에 오고 간극 195px. 사실상 튜토리얼 구간이다.
2. **충돌해도 번호를 잃지 않는다.** 기회만 줄어든다.
3. **자동 재개가 없다.** 준비됐을 때 스스로 이어 난다(위 [이어날기](#이어날기--자동-재개-폐지)).
4. 첫 충돌 시 **1회만** 힌트 — "가볍게 여러 번 탭하세요".
5. 2회 연속 충돌하면 다음 파이프 간극을 **+20px** 보정(상한 +40).
   눈치채지 못할 정도의 은근한 도움이다.
6. **남은 기회를 항상 보이게** 둔다. 몇 번 남았는지 모르는 채 끝나는 것이 가장 나쁘다.

`reducedMotion` 일 때 배경 패럴랙스와 흔들림은 멈추되 **파이프 이동은 유지**한다
(계약의 4항목 규약).

## 아트 디렉션 (코드로 그린다)

**새** — **로또볼 캐릭터**다. `draw.ball()` 로 그린 볼 + 눈 2개 + 날개 2장(각속도에 따라
각도 변화) + 아래로 늘어진 짧은 다리. 날갯짓 시 −0.25 rad 기울고 낙하 시 +0.35 rad.

**파이프** — 둥근 사각 + 끝단 캡 + 세로 하이라이트 띠(`--svc-lotto` 계열 2단 그라디언트).

**번호 링** — 이중 원(외곽 볼 구간색 6px, 내부 흰색 α0.15) + 중앙 **무지 볼**.
`timeMs` 로 미세 맥동. ⚠ 통과 전에는 숫자가 없다. 통과한 순간부터 `draw.ball()` 로 번호를
그리며 확대·페이드한다 — 그 연출이 곧 "볼이 깨지며 번호가 드러나는" 장면이다.

**꽝 링** — 같은 이중 원이되 **무채색**(`border`)이고 가운데가 **비어 있다**(가는 테두리 원만).
맥동하지 않는다. 한눈에 "여기엔 없다" 를 읽히게 하는 것이 목적이다.

**HUD** — 캔버스 좌상단에 `123m`, 우상단에 남은 기회를 **점 9개**로. 숫자를 두 개 늘어놓는
것보다 점이 빠르게 읽히고, 줄어드는 것이 눈에 들어온다.

**배경** — 하늘 그라디언트 + 구름 2겹 + 하단 도시 실루엣(패럴랙스 0.3배). 오프스크린 캐시.

## 구현 결정 — 사양서에 없어 구현 세션이 정한 것

계약([[playground-game-contract]])이 *"계약에 없는 것이 필요하면 임의로 정하지 말고 멈춰서
보고한다"* 고 못 박았다. 아래는 **멈추는 대신 여기에 적고 진행한 것들**이다(사용자 지시,
2026-09-08). 전부 이 게임 폴더 안에서 닫히고 다른 게임에 영향을 주지 않는다.

| 결정 | 근거 |
|------|------|
| **시작 대기 상태(`ready`)를 둔다.** 첫 입력 전에는 중력을 걸지 않고 새가 제자리에서 부유한다 | 사양서의 "첫 파이프 3초" 를 **시작 지점까지 연장**한 것이다. 화면을 인식하기도 전에 새가 바닥으로 떨어지면 "무엇을 해야 하는지 모른 채 실패" 하게 된다 |

| **획득 시 게임이 `status` 를 보내지 않는다** | 호스트(`GameCanvas` 의 `onAward`)가 이미 "세 번째 번호 17번을 모았습니다" 를 보낸다. 게임이 또 보내면 `aria-live` 가 같은 내용을 **두 번 읽는다** |

| **연속 충돌 보정에 상한(+40)을 둔다** | 무한정 넓히면 파이프가 없는 것과 같아진다. 은근한 도움이라야 모아 온 번호가 시시해지지 않는다 |
| **새 몸통에 직전에 모은 번호를 새긴다**(하나도 없으면 `mysteryBall`) | 사양서는 "`draw.ball()` 로 그린 볼" 이라고만 했고 어떤 번호인지는 정하지 않았다. 획득 순간 몸통이 바뀌어 **캔버스만 보는 사용자에게 즉각적인 피드백**이 되고, 시각 언어 규칙 4(숫자는 `ball()` 로만)도 지켜진다 |

### 2026-09-17 — 개편을 구현하며 정한 것

사양서에 없어 구현 세션이 정했고, 전부 이 게임 폴더 안에서 닫힌다.

| 결정 | 근거 |
|------|------|
| ★ **번호 링을 순번이 아니라 `pool.awarded.length` 로 고른다** — `order >= NUMBER_RING_ORDER[모은 수]` | `NUMBER_RING_ORDER.includes(order)` 로 짰더니 **놓친 번호 링의 순번이 영영 사라졌다.** 2번째 링에 부딪혀 지나치면 그 링은 `release` 되는데 순번은 이미 지나가, 20개를 다 통과해도 다섯 개뿐이다. **충돌이 잦은 사용자일수록 덜 모으는** 구조라 이 게임이 가장 피해야 할 형태다. 모은 수를 기준으로 하면 놓쳐도 다음 링이 곧 번호 링이 되어 **저절로 복구된다** |
| **번호 링 예약은 한 번에 하나로 막는다** | 아직 지나지 않은 예약 링이 화면에 있으면 새로 세우지 않는다. 안 막으면 둘 다 통과했을 때 목표 순번을 건너뛰어 **20개보다 훨씬 일찍 끝난다** |
| **번호 링인데 예약이 `null` 이면 꽝 링으로 강등해 세운다** | 개편 전에는 파이프를 아예 세우지 않았다. 이제는 6개를 모은 뒤에도 계속 날 수 있으므로 파이프가 사라지면 **날 곳 자체가 없어진다** |
| **`fillPipes` 가 `pool.complete` 에서도 계속 세운다** | 같은 이유다. 개편 전에는 여기서 곧바로 돌아갔다 |
| **`crashed` 는 화면 아무 곳이나 눌러도 이어 난다** | 버튼 그림은 "눌러야 한다" 는 신호이지 히트박스가 아니다. 작은 화면에서 좁은 버튼을 맞히게 하는 것이 또 하나의 마찰이고, 이 게임의 조작은 원래 아무 데나 탭이다. ⚠ 반대로 **완주 선택은 히트박스가 필요하다** — 선택지가 둘이라 어디를 눌렀는지가 곧 답이다 |
| **`CRASH_HOLD_SEC` 의 뜻을 바꿨다**(1.2 → 0.6) | 전에는 "이 시간이 지나면 자동 재개" 였고 이제는 **입력 잠금**이다. 충돌하는 순간 누르고 있던 손가락이 곧바로 이어날기를 눌러 버리면 무슨 일이 났는지 볼 새가 없다. 자동 재개가 없어졌으므로 "볼 시간" 을 강제할 이유는 사라졌다 — 길면 오히려 눌러도 안 먹는 구간이 된다 |
| **`hover` 는 기준 높이에 사인파를 더한다**(`y += sin(...)` 이 아니라) | `y` 에 직접 더하면 진폭이 0.13px 로 뭉개져 멈춘 것처럼 보이고, 반올림 오차가 쌓여 새가 조금씩 흘러내린다. `ready` 와 같은 식을 쓴다 |
| **안내 패널을 `cy = 50` → `58`** | HUD(8~30)가 생기면서 패널(24~76)이 **기회 점 위에 겹쳤다.** 58 이면 32부터라 2px 이 남고, 아래 끝 84 는 여전히 링 위쪽 끝(100)보다 위다 |
| **꽝 링 통과에 `blank` 를 보내고 진동은 보내지 않는다** | `blank` 는 계약이 *"맞았지만 소득이 없다"* 에 배정한 소리다. 소리가 없으면 통과 여부를 화면으로만 알 수 있다. 진동은 뺐다 — 20개를 지나는 동안 매번 울리면 그것만으로 성가시다 |
| **실패 문구에 비행 거리를 넣는다** | `text` 만 덮고 제목은 호스트 기본값을 쓴다(G01 선례). 번호를 못 채운 판에서 **남는 것이 거리뿐**이다 |
| **`choice` 동안 세계를 멈춘다** | 뒤에서 판이 굴러가면 고를 수가 없다. 새도 멈춘다 |

### ⚠ `ctx.palette` 스냅샷 — 다른 게임 세션이 먼저 찾은 문제

호스트가 `create()` 에 팔레트를 **값으로** 넘기고 테마 변경 시 자기 지역 변수만 갈아 끼운다.
`DrawKit` 은 클로저로 최신 색을 보지만 게임이 쥔 `ctx.palette` 는 처음 객체 그대로다 —
볼은 다크로 바뀌는데 게임이 직접 칠한 하늘·파이프·패널은 옛 색으로 남아 **화면이 반씩 갈린다**
(G03·G04 세션이 [[log]] 에 먼저 남겼다).

G06 은 호스트가 전달 경로를 만들 때까지 **`readPalette()` 를 1초에 한 번 직접 읽고**, 색이
실제로 달라졌을 때만 구워 둔 스프라이트와 그라디언트를 버린다. 매 프레임 읽지 않는 이유는
읽는 값이 아니라 **다시 굽는 비용**이 문제이기 때문이다.

⚠ 다시 구울 때 **빌딩 모양이 달라지면 안 된다.** 배치 난수를 시드로 붙들어 두고 같은
스트림을 다시 뽑는다 — 안 그러면 다크모드로 토글하는 순간 도시가 통째로 다른 도시가 된다.

### ⚠ 여섯 게임 공통 함정 — `DrawKit` 의 그라디언트 캐시

`draw.bgGradient` 의 내부 캐시는 **키가 `크기 + 색` 뿐이라 어느 컨텍스트에서 만들어졌는지를
기억하지 않는다.** `CanvasGradient` 는 만든 컨텍스트에 종속이므로, **오프스크린 캔버스에서
한 번이라도 부르면** 그 객체가 캐시에 남아 이후 메인 캔버스가 남의 컨텍스트 객체를 쓴다.

배경을 오프스크린에 캐시하는 것은 시각 언어 규칙 1이 **요구하는** 일이라, 다른 게임 세션도
같은 자리를 밟을 수 있다. G06 은 오프스크린에서 `bgGradient` 를 부르지 않고 자체
그라디언트를 만든다.

⚠ **이 시간은 "화면을 전혀 보지 않는 플레이어" 의 값이다.** 조준 없이 400~750ms 무작위
간격으로 스페이스만 누르는 봇이라, 링 높이를 보고 조작하는 사람보다 훨씬 못한다. 즉
**75.3초는 사람 성적의 상한(더 나쁠 수 없는 쪽)** 이고, 완료 기준인 "숙련되지 않은 사용자가
90초 안에" 는 이 값만으로도 만족된다. 무실수 코스는 `3초 + 2초 × 5 = 13초`로 사양서가 적은
"무실수 12초" 와 맞는다.

⚠ **여덟 판 모두 6개를 채웠다는 사실이 시간보다 중요하다.** 충돌해도 번호를 잃지 않으므로
**실패라는 결말이 구조적으로 없다.** 이 게임에서 막아야 할 것은 실패가 아니라 지루함이다.
