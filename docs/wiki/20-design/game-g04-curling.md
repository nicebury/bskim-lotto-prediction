| 항목 | 값 |

## ★ 2026-09-17 전면 개편 — 보드형에서 은닉형으로

**사용자 지시로 게임의 뼈대가 바뀌었다.** 이 절이 현재 사양의 정본이고, 아래 "지나온 길"
은 왜 이 수치가 되었는지의 기록이다.

| 무엇 | 전 (2026-09-08 ~ 09-16) | 후 (2026-09-17) |
|---|---|---|
| 칸 | 번호가 **적혀 있다** (아래 1~5, 위 41~45) | **전부 뒷면**. 멈춘 칸만 뒤집힌다 |
| API | `pool.board()` → `claimExact(n)` | **`pool.awardHidden()`** |
| 중복 | 가능 → **재투**(기회 소모 없음) | **구조적으로 불가능** |
| 이미 얻은 칸 | 체크 표시(그냥 지나간다) | **장애물 — 스톤이 튕긴다** |
| 기회 | 무제한 | **9번**. 다 쓰면 `failed` |
| 꽝 | 없음 | **45칸 중 9칸** |
| 칸 판정 | 보드 안이면 무조건 획득 | **가운데에 세워야 열린다** (사방 2px 여유) |
| 각도 한계 | ±26° | **±45°** (벽을 쓸 수 있게) |
| 최대 당김 | 140px | **80px** (손가락이 화면 밖으로 안 나가게) |
| 시작 화면 | 조준선만 | **당겼다 놓는 동작을 시연** |

### 왜 번호를 감췄나

계약이 2026-09-10 에 *"여섯 게임 전부, 번호는 손에 넣는 순간 처음 드러난다"* 고 정했는데
**G04 만 예외로 남아 있었다.** 이번에 그것을 맞췄다.

**잃은 것을 분명히 적어 둔다.** 종전 게임의 유일한 조작 감각은 *"41번을 원하면 세게 친다"*
였고, 그 대응이 곧 난이도 곡선이었다. 번호를 감추면 그 근거가 사라진다 — 어느 칸이든
기댓값이 같으므로 세기는 "번호를 고르는" 문제가 아니라 **"보드 안에 넣는"** 문제가 된다.

대신 난이도를 만드는 것이 셋 생겼다.

1. **꽝** — 피할 수 없는 운. 어디가 꽝인지는 뒤집어 봐야 안다
2. **장애물** — 모을수록 지형이 복잡해진다. 후반일수록 원하는 자리에 넣기 어렵다
3. **9번이라는 한계** — 헛투구가 그냥 넘어가지 않는다

### 꽝 — 45칸 중 9칸

**시작할 때 자리를 정해 두고 숨긴다.** 멈춘 뒤에 그때그때 굴리지 않는다 — 그러면 같은 칸이
한 번은 꽝, 한 번은 번호가 되어 **판이 기억을 갖지 않고**, 화면에서 읽은 정보가 다음 투구에
쓸모없어진다.

> **왜 9칸인가.** 기회 9번, 목표 6개다. 20% 면 9번 던져 기대 꽝이 1.8회이고 여유가 3번이므로,
> **기대치 안에서는 완주하고 운이 나쁘면 실패한다.** 실패가 의미를 갖되 억울하지 않은 지점이다.

⚠ **공개된 꽝 칸을 장애물로 만들지 않는다.** 장애물로 두면 화면에 남은 위험이 하나씩 사라져
판이 갈수록 쉬워진다. 꽝은 피해야 할 자리로 **계속 거기 있어야** 긴장이 산다. 다시 멈추면
또 꽝이고 기회를 잃는다.

### 얻은 칸은 장애물이다 — 재투를 대신한다

종전에는 이미 모은 번호 칸에 멈추면 **그 투구를 없던 것으로** 되돌렸다. 일이 벌어진 뒤에
무르는 방식이라, 스톤은 거기 멈춰 있는데 결과는 없는 어정쩡한 순간이 남았다.

지금은 아예 **물리적으로 들어가지 못한다.** 무를 일이 없으니 "이 투구는 없던 것" 이라는
설명도, 그 설명을 못 읽는 사용자를 위한 배려도 필요 없어졌다.

⚠ **장애물의 물리 반지름은 11 로, 보이는 볼(10)보다 1px 크다.** 장난이 아니라 불변식을
지키는 장치다. 칸은 40×23 이라 중심에서 모서리까지가 23.07px 인데, 스톤(13) + 볼(10) = 23
이면 **모서리에 스톤 중심이 겨우 들어가** 이미 얻은 칸에 멈추는 일이 드물게 일어난다.
13 + 11 = 24 > 23.07 이면 **기하학적으로 불가능**해지고 예외 규칙이 사라진다.

### 칸 가운데에 세워야 열린다 — 실패가 나오게 만든 장치

**처음 만들었을 때는 실패가 거의 나오지 않았다.** 실패 경로가 꽝(20%)과 아웃뿐이라, 보드
안에만 넣으면 사실상 획득이었다 — 9번 던져 6개를 모을 확률이 **85%** 였다.

그래서 **칸 경계에서 사방 2px 안쪽에 스톤 중심이 들어와야** 그 칸을 얻는다. 걸치면
아무것도 열리지 않고 기회만 준다.

| 마진 (가로, 세로) | 판정 통과 | 투구당 획득 | **완주율** |
|---|---|---|---|
| 없음 (종전) | 100% | 0.76 | **85%** |
| **(2, 2) ← 채택** | 74% | 0.565 | **약 40%** |
| (3, 2) | 70% | 0.53 | 32% |
| (2, 1) | 82% | 0.625 | 54% |

*보드 진입률 0.95 · 꽝 9칸 가정. 두세 판에 한 번 완주하는 폭이 90초짜리 미니게임에 맞다.*

> **난이도를 조절할 때 가장 먼저 만질 값이 이 마진이다.** 위 표에서 고르면 된다.

⚠ **세로가 병목이다.** 칸 높이가 23px 이고 한 행이 당김 5~7px 에 대응하므로, 세로 여유
1px 을 더 주고 덜 주고가 가로보다 훨씬 크게 작용한다.

⚠ **꽝·획득 판정보다 먼저 본다.** 순서를 뒤집으면 선에 걸친 투구가 꽝 칸을 열어 버리거나
(그 칸의 정체가 공짜로 드러난다) 번호를 하나 소비한다. 걸친 투구는 **아무것도 열지 않고**
끝나야 다음 투구에 같은 칸을 제대로 노릴 수 있다.

⚠ **걸친 자리를 반드시 화면에 보여 준다.** 예상 궤적은 보드 진입 전까지만 그리므로, 결과를
보여 주지 않으면 사용자에게는 **아무 근거 없이 실패한 것**이 되어 조절할 방법이 없다 —
실력이 아니라 순전히 운이 된다. 걸친 칸의 테두리와 **판정 영역 점선**, 스톤이 실제로 선
자리를 함께 그려 "어느 쪽으로 얼마나" 어긋났는지가 한눈에 읽히게 한다.

### 기회를 소모하는 것과 아닌 것

| 결과 | 기회 |
|---|---|
| 번호 획득 · 꽝 · **선에 걸침** · 보드 밖 정지 · 아웃 | **소모** |
| 당김이 최소치(8px)에 못 미친 헛손질 | 소모 안 함 |

**기회는 발사하는 순간 한 번만 센다.** 결과 종류마다 따로 세면 한 군데를 빠뜨렸을 때
기회가 줄지 않는 경로가 조용히 생긴다.

⚠ **아웃까지 세는 이유.** 공짜라면 세기 조절이라는 이 게임의 조작 자체가 무의미해진다.
대신 파워 바에 "보드에 드는 구간" 눈금을 새겨 완전히 깜깜하게 두지는 않는다.

## 물리와 수치 — 실측

설계는 해석식으로 잡고 **확정은 실측으로 한다.** 실제 루프는 오일러 적분이라 해석식보다
한 스텝만큼 더 간다.

```
v0 = 194 + pull × 4.0        마찰 a = 380 px/s² (선형·쿨롱)
시작점 (180, 330)            각도 한계 ±45°     벽 반사 0.6 · 장애물 반사 0.7
```

### 당김 → 도달 (각도 0, 실제 루프와 같은 dt·같은 식)

| 당김 | 결과 | | 당김 | 결과 |
|---|---|---|---|---|
| 0 ~ 20.5 | 못 미친다 | | 48 ~ 53 | 행 4 |
| 21 ~ 28 | **행 8 (맨 아래)** | | 53.5 ~ 58 | 행 3 |
| 28.5 ~ 35 | 행 7 | | 58.5 ~ 63 | 행 2 |
| 35.5 ~ 41.5 | 행 6 | | 63.5 ~ 68 | 행 1 |
| 42 ~ 47.5 | 행 5 | | 68.5 ~ 72 | **행 0 (맨 위)** |
| | | | 73 ~ 74.9 | 보드 위 공백 |
| | | | 75 ~ 80 | **아웃** |

한 행이 당김 5~7px 에 대응한다. 좌우는 ±45° 안에서 **아홉 행 모두 다섯 열 전부** 도달한다.

### ⚠ 최대 당김이 아웃에 닿아야 한다

처음에는 `PULL_MAX` 를 72 로 뒀는데, 실측해 보니 **끝까지 당겨도 맨 위 행에 얌전히 서서
아웃이 한 번도 나지 않았다.** 그런데 화면에는 아웃 라인이 그려져 있다 — **넘을 수 없는 선을
그려 두는 것은 화면이 하는 거짓말**이고, 동시에 "끝까지 당기는 것이 언제나 안전" 이 되어
세기를 조절할 이유가 사라진다. 80 으로 올리면 보드 → 보드 밖 → 아웃 세 구간이 모두 손에
들어온다.

### ⚠ 당김이 화면을 넘어가지 않는다

당김은 시작점에서 포인터까지의 거리다. 종전(시작점 365 + 최대 140 = **505**)은 무대 430 을
75px 넘겨 **화면 밖에서 손을 떼야 최대 세기가 나왔다.** 지금은 330 + 80 = **410 < 430** 이다.

### 벽은 장식이 아니라 전략이다

각도를 45° 로 연 것은 사용자 요청("벽을 활용할 수 있게")이다. tan45° = 1 이라 **앞으로 간
만큼 옆으로도 갈 수 있어** 벽을 맞고 되꺾이는 경로가 실용적인 선택지가 된다. 26° 로는 맨 아래
행에서 좌우 54px 밖에 벌지 못해 벽(중심에서 120px)에 닿을 일이 사실상 없었다.

⚠ **90° 로 열지 않는다.** 앞으로 나가지 않는 투구가 가능해져, 아무 일도 일어나지 않는데
기회만 소모되는 판이 생긴다.

## 화면

위에서 내려다본 얼음 레인(`x 60~300`). 위쪽에 **5열 × 9행 = 45칸**(`x 80~280` · `y 24~231`),
그 아래 **남은 기회 표시**(y 252), 아래쪽에 스톤 시작점(180, 330), 왼쪽 바깥에 세로 파워
바(x 32, y 210~330).

### 조작 시연 — 첫 투구 전까지

**"시작 화면만 보면 당겨서 던지는 게임인 줄 알 수 없다"** 는 지적에서 나왔다.

⚠ **시작 오버레이 뒤에는 그릴 수 없다.** 호스트는 `phase !== 'playing'` 인 동안 캔버스를
통째로 덮으므로, 시작 화면에 그리는 것은 아무도 보지 못한다. 그래서 **"게임시작" 을 누른
직후부터 첫 투구 전까지** 보여 준다 — 사용자가 처음으로 캔버스를 마주하는 그 순간이다.

2초 주기로 아래로 당겼다가 놓는 동작을 반복한다(당기기 1.1초 · 튕김 0.25초 · 쉼 0.65초).
**쉬는 구간을 두는 이유**는 끊임없이 움직이면 조준 중인 시선을 계속 빼앗기 때문이다.
한 번 던지면 끈다.

`reducedMotion` 이면 **움직이지 않는 아래 화살표 + "당겼다 놓기"** 로 대체한다 — 연출만 끄고
정보는 남긴다(계약의 장식 넷 중 "번호 공개 연출을 페이드로" 와 같은 해석).

### 당김 표시 — 스톤은 제자리에 둔다

스톤 자체를 뒤로 물리면 조준의 기준점이 움직여, 얼마나 당겼는지를 눈이 아니라 기억으로
재야 한다. 고정된 시작점 원에서 손잡이까지의 거리가 곧 세기이고, 그 길이가 화면에 그대로
보인다.

### 남은 기회

계약은 *"캔버스 상단에 그린다"* 고 하지만 이 게임의 상단에는 자리가 없다(아웃 라인 바로
아래가 보드다). **보드와 스톤 사이**는 시선이 반드시 지나는 길이라 오히려 눈에 잘 들어온다.

⚠ **색만으로 전하지 않는다.** 남은 기회는 **채운 원**, 쓴 기회는 **빈 원**이다 — 모양이
다르므로 색각 이상이 있어도, 흑백으로 보아도 읽힌다. 화면 안 표시는 보조기술에 투명하므로
`status` 로 **숫자를 말로 함께** 준다("…남은 기회 3번").

## 아트 디렉션 (코드로 그린다)

**스톤** — 화강암 원(r13, 방사 그라디언트) + 방향을 가리키는 손잡이 + 접지 그림자.
**얼음** — 흰-하늘색 그라디언트 + 스크래치 12개(α0.06, 시드 고정) + 지나간 자리 페이드 궤적.
**뒷면 칸** — `DrawKit.mysteryBall`. 직접 그리지 않는 이유는 은닉형 셋(G01·G02·G04)이
**같은 뒷면**을 보여야 하기 때문이다.
**꽝 칸** — 회색 원 + 붉은 테두리 + **"꽝" 글자.** 글자가 정보의 본체이고 색은 거들 뿐이다.
**얻은 칸** — `ball()` + **장애물 링.** 링은 장식이 아니라 "여기는 부딪히는 자리" 라는 지형
정보다. 모르면 스톤이 왜 튀는지 알 수 없다.

⚠ **행별 구간색을 지웠다.** 전에는 행마다 볼 구간색을 α0.10 으로 깔아 "색만 봐도 번호대가
읽히게" 했다. 번호를 감춘 지금 같은 색을 깔면 **뒷면인 척하면서 번호대를 알려 주는** 셈이다.

⚠ **꽝은 볼이 아니라 글자로 키운다.** 볼 모양으로 솟아오르면 그 실루엣만으로 번호를 얻은
줄 알고, 글자를 읽고 나서야 아니라는 것을 안다 — 그 반 초가 불쾌하다.

⚠ **시연은 맨 마지막에 그린다.** 조준선·파워 바 아래에 깔리면 손 모양이 선에 가려 무엇을
흉내 내는지 알 수 없다(G01 이 꽝 연출에서 겪은 것과 같은 이유 → [[log]] 2026-09-10).

## 효과음

`shoot`(투구) · `hit`(획득) · `blank`(꽝) · `miss`(보드 밖·아웃·약한 당김) · `clear`(완주) ·
`fail`(기회 소진). **꽝과 빗나감을 다른 소리로 낸다** — 같은 소리면 귀로 원인을 구분할 수 없다.

⚠ 벽과 장애물도 **진동으로 가른다**(벽 10ms · 장애물 20ms). 벽은 활용하는 것이고 장애물은
막힌 것이라, 같은 신호로 알리면 손끝으로 구분되지 않는다.

## 완료 기준

- 당김 21~72 가 보드 아홉 행에 대응하고, 75 이상이 아웃이다 ✅ 실측
- ±45° 안에서 아홉 행 다섯 열에 **전부** 도달한다 ✅ 실측
- 이미 얻은 칸에 **멈출 수 없다**(기하학적으로) ✅ 24 > 23.07
- 최대로 당겨도 손가락이 화면 밖으로 나가지 않는다 ✅ 410 < 430
- 기회 9번을 다 쓰면 `failed`, 6개를 모으면 `cleared`
- **완주율이 85% 가 아니다** — 칸 가운데 판정으로 약 40% (계산값, 플레이 검증 필요)
- 선에 걸치면 **판정 영역이 화면에 표시된다** — 다음 투구에 쓸 근거가 남는다
- 획득·꽝이 **색 외 수단**(글자·모양)으로 구분된다
- 키보드(방향키 + 스페이스)만으로 완주 가능
- 검증 게이트 0건 ✅ 브라우저 표준 난수 · 화면 배율 참조 · hex 리터럴 · 금지 식별자 · 번호 리터럴

⚠ **실제 플레이 검증은 사용자가 한다**(2026-09-17 지시). 위 ✅ 는 수치·기하 실측과 정적
검사만이고, 체감 난이도(꽝 9칸이 적당한가, 장애물이 후반을 너무 막지 않는가)는 플레이로만
알 수 있다.

## ⚠ 경계를 넘은 수정 1건 — 호스트 `GameCanvas.tsx`

**스페이스를 누르면 페이지가 스크롤된다**는 제보에서 나왔다. `input.ts` 는 `keydown` 을
**캔버스에만** 걸고 거기서 `preventDefault` 하므로, 막히는 것은 **캔버스에 포커스가 있을
때뿐**이다. 그런데 가장 흔한 진입 경로인 오버레이의 "게임시작" 버튼은 눌리자마자
**언마운트되어 포커스가 `body` 로 떨어진다.**

게임은 DOM 에 접근할 수 없으므로(계약: 게임은 순수 함수 덩어리) **G04 폴더 안에서 고칠 수
없다.** `phase: 'playing'` 이 올 때 캔버스에 `focus({ preventScroll: true })` 하는 한 줄을
호스트에 넣었다. **여섯 게임 공통 이득**이고, 특정 게임의 사정이 아니라 호스트의 입력 경로
문제다.

⚠ `preventScroll: true` 가 반드시 필요하다. 없으면 브라우저가 캔버스를 보이게 하려고
스크롤해서 `GameStage.scrollTo()` 가 잡아 둔 위치를 흐트러뜨린다 — 고치려는 증상을 스스로
다시 만드는 셈이다.

## 지나온 길 — 수치의 근거

### 무대를 620 → 430 으로 줄였다 (2026-09-16)

호스트가 무대 높이를 `clamp(260px, calc(100svh − --pg-chrome), 660px)` 로 정하고 캔버스가 그
박스를 **꽉 채우는데**, `loop.ts` 는 **가로 기준으로만** 확대한다. 세로로 긴 무대일수록 아래가
잘린다. 620 일 때 375×667 에서 **394까지만** 보였고 **스톤이 화면 밖이라 던질 수가 없었다.**

430 으로 줄인 뒤 390×760 과 1280×900 에서 **잘림이 사라졌고**, 375×667 에서 잘리는 36px 은
레인 하단 장식뿐이다. 그 대가로 칸 높이 30→23, 볼 반지름 11→10 이 됐다.

⚠ **무대를 줄이면 좌우 도달 범위도 함께 줄어든다.** 발사점과 표적이 가까워져 같은 각도로도
덜 벌어지기 때문이다. 그때 각도를 ±20°→±26° 로 넓혀야 맨 아래 행 양끝 칸에 닿았다
(2026-09-17 에 ±45° 로 다시 넓혔다).

### 마찰 260 → 300 → 380 (2026-09-08 · 09-16)

사양서 초안(a=260, 시작 y=560)은 pull 30~94 의 이동 폭이 269.6px 인데 보드 높이가 270px 이라
**여유가 0.4px** 였다 — 시작점을 어디에 두어도 양 끝 중 하나가 보드를 벗어난다.

### 파워 바를 하단 가로 → 좌측 세로 (2026-09-08)

가로 바를 스톤 아래 두면 **드래그하는 손가락이 정확히 그 위를 덮는다.** 세기가 이 게임의
전부인데 그 표시가 가리면 소용이 없다.

### 예상 궤적은 보드 진입 전까지만 (2026-09-08)

정지 지점까지 그리면 어느 칸에 멈출지가 화면에 적혀 있는 셈이라, 첫 투구부터 원하는 칸을
맞힌다. 방향은 보여 주고 거리는 파워 바로 가늠하게 한다.

### 위에 벽을 두지 않는다 (2026-09-08)

백보드를 두면 세게 친 스톤이 튕겨 돌아와 보드에 멈출 수 있고, 그러면 "세게 칠수록 위" 라는
단조 관계가 깨진다.

### 계약 재반영 4건 (2026-09-16)

`phase` 이벤트 · **시작 입력 삼키기**(오버레이의 "게임시작" 이 `primary` 로 오므로 거르지
않으면 그 입력이 첫 투구가 된다) · **이미 끝난 판**(30분 복원 시 `ready` 없이 `cleared`) ·
`sfx` 연결.

### 위키 재대조 3건 (2026-09-16)

계약 표의 무대 높이가 620 인 채였던 것 · `intro` 가 세 문장이던 것 · 첫 진입에서 `attempt`
를 보내지 않던 것.

## ⚠ 남은 것 — 호스트가 고쳐야 한다

**캔버스가 박스를 꽉 채우느라 비율이 깨지는 문제는 그대로다.** 무대를 430 으로 줄여 G04 는
실용적으로 비켜섰지만 원인이 사라진 것은 아니다.

- **세로 잘림** — 375×667 에서는 여전히 430 중 394 까지만 보인다
- **포인터 좌표 어긋남** — 비율이 어긋난 만큼 `pointerScaleY` 가 되돌린다. 비율이 맞는
  해상도(390×760 · 1280×900)에서는 이 값이 1 이라 아무 일도 하지 않는다
- **팔레트 스냅샷** — `ctx.palette` 가 `create()` 시점 그대로라 `readPalette()` 를 직접 읽는다

근거와 해법(레터박스)은 [[playground]] 에 적었다. 호스트가 고치면 **G04 쪽 방어 코드는
저절로 무해해진다** — 지우지 않아도 된다.
