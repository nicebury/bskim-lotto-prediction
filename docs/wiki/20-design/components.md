# 컴포넌트 사양

홈 화면을 이루는 재사용 컴포넌트의 사양이다. 색·크기 값은 토큰([[design-tokens]])에서 가져오고, 단별 배치는 [[responsive-rules]] 를 따르며, 접근성 요구는 [[accessibility]] 에 상세하다. 이 페이지는 각 컴포넌트가 **무엇을 받고(props) 어떤 상태를 갖고 어떻게 마크업되는지**를 정한다.

신규 프론트는 Next.js 지만 기존 `frontend/src/components/LottoBall.jsx` 의 구간 매핑 로직은 그대로 유효하다.

---

## LottoBall — 번호 볼

한 개의 로또 번호를 원형 볼로 렌더링한다. 색은 동행복권 공식 5구간을 따른다(시안 색 아님 — 근거 [[0009-official-ball-colors-over-mockup]]).

시그니처:

```tsx
<LottoBall number={13} />                 // 일반
<LottoBall number={16} bonus />           // 보너스 변형
<LottoBall number={7} size="sm" />        // 크기 변형
```

- `number: number` (1~45) — 필수. 이 값이 색 구간과 표시 숫자를 동시에 결정한다.
- `bonus?: boolean` — 보너스 변형. 볼 우상단에 `+` 배지를 얹는다.
- `size?: 'sm' | 'md' | 'lg'` — 크기 변형. 기본 `md`. 모바일에서도 최소 지름 36px + 44px 히트 영역([[responsive-rules]]).

구간→색 매핑은 순수 함수다:

```ts
function ballRange(n: number): 1|2|3|4|5 {
  if (n <= 10) return 1;   // 1~10  노랑 --ball-1-10
  if (n <= 20) return 2;   // 11~20 파랑 --ball-11-20
  if (n <= 30) return 3;   // 21~30 빨강 --ball-21-30
  if (n <= 40) return 4;   // 31~40 회색 --ball-31-40
  return 5;                // 41~45 초록 --ball-41-45
}
```

**색은 정보의 유일한 전달자가 아니다(WCAG 1.4.1).** 볼에는 항상 숫자가 있고, 스크린리더용 `aria-label` 에 구간을 명시한다. 형식은 정확히 다음이다:

```tsx
aria-label={`${number}번, ${lo}~${hi} 구간`}   // 예: "13번, 11~20 구간"
```

보너스는 `"16번, 11~20 구간, 보너스"` 로 붙인다. 밝은 볼(노랑·초록) 위 숫자는 `--ball-fg-dark` 를 써 대비를 확보한다([[accessibility]]). 상태는 없다(순수 표시 컴포넌트).

## Card — 카드

콘텐츠 컨테이너의 기본 골격. 최신 회차 결과·D-day·뉴스·통계·가이드가 모두 이 위에 선다.

- 배경 `--color-surface`, 테두리 `--color-border`, 모서리 `--radius-card`(16px), 그림자 `--shadow-card`.
- 호버 시 `--shadow-card-hover` + 미세한 상승(`translateY(-2px)`). `prefers-reduced-motion` 에서 이동을 끈다.
- 시맨틱: 독립적으로 이해되는 카드는 `<article>`, 페이지 구획은 `<section>` + 제목(`<h2>`/`<h3>`)으로 감싼다([[accessibility]] 헤딩 계층).

props 는 얇게: `title`, `action`(더보기 링크 등), `children`. 상태를 갖지 않는다.

## Header — 헤더

로고 + 내비게이션 + 검색 + 다크 토글. 데스크톱과 모바일에서 형태가 갈린다([[responsive-rules]] 헤더 전환).

- **데스크톱**: 가로 `<nav>` (로또 · 번호통계 · 번호추천 · 꿈해몽 · 뉴스 · 가이드) + 검색 입력 + 테마 토글 버튼.
- **모바일**: nav → 햄버거 버튼이 여는 **드로어**. 검색 → 아이콘이 여는 **전체화면 오버레이**.

**헤더의 검색은 사이트 전체 검색이 아니라 회차 번호 이동이다.** 입력한 번호로 `/lotto/round/{n}` 에 간다. 전체 검색 페이지(`/search`)는 URL 구조(초안 5.1)에 없고, 동작하지 않는 검색창을 만들지 않기 위한 선택이다. 그래서 JSON-LD `WebSite` 에 `potentialAction`(sitelinks searchbox)을 넣지 않는다 — 화면에 없는 기능을 마크업에 넣지 않는다([[structured-data]]).

시그니처(상태를 가진 클라이언트 컴포넌트):

```tsx
<Header />
// 내부 상태
//   drawerOpen: boolean   — 햄버거 드로어 열림
//   searchOpen: boolean   — 검색 오버레이 열림
//   theme: 'light'|'dark'|'system'  — 다크 토글 (localStorage 지속)
```

드로어·오버레이는 열릴 때 포커스를 안으로 가두고(focus trap), `Esc` 로 닫히며, 현재 페이지 링크에 `aria-current="page"` 를 준다. 햄버거·검색 버튼은 `aria-expanded` 와 `aria-controls` 를 갖는다. `type="button"` 을 명시한다. 상세는 [[accessibility]].

다크 토글은 `prefers-color-scheme` 을 기본값으로 읽고, 사용자가 누르면 `data-theme` 를 `<html>` 에 박아 자동값을 덮는다([[design-tokens]] 다크 세트).

**내비 타이포 (002 R5·R6).** 40대+ 가독성을 위해 데스크톱 nav 링크 글자를 **약 2pt 키운다**(현행 `--fs-body` ≈ 0.95rem 기준 한 단계 상향). `--fs-body` 를 직접 바꾸면 전역에 파급되므로 **nav 전용 규칙에서만** 상향한다. **현재 페이지 링크(`aria-current="page"`)는 볼드(`--fw-bold` 700)** 로 강조한다(종전 semibold 600 → 700).

## RecommendCarousel — 추천번호 캐러셀

"오늘의 추천 번호" 5장(완전 랜덤 · 최근 HOT · **안 나오던 번호** · 홀짝 균형 · 번호대 균형)을 넘긴다. 각 카드는 6개 볼 + "다시 생성" 버튼. (전략명 "COLD" 표기는 002 개편으로 "안 나오던 번호" 로 바꾼다 — [[forbidden-expressions]] 의 라벨 규칙.)

- 데스크톱(1024px~): 여러 장 노출 + 좌우 화살표(가로 캐러셀).
- **모바일(~1023px): 가로 스크롤을 쓰지 않고 세로로 쌓는다(1열 스택).** 002 R12 — 40대+ 사용자에게 옆으로 숨은 카드는 발견성이 낮다. 옆으로 스와이프해 찾게 하지 않고 아래로 죽 잇는다.

```css
/* mobile-first: 기본 = 세로 스택 (가로 스크롤 없음) */
.carousel-track {
  display: flex;
  flex-direction: column;
  gap: var(--space-4);
}
.carousel-item { width: 100%; }

@media (min-width: 1024px) {   /* 데스크톱에서만 가로 캐러셀 */
  .carousel-track {
    flex-direction: row;
    overflow-x: auto;
    scroll-snap-type: x mandatory;
  }
  .carousel-item { scroll-snap-align: start; flex: 0 0 auto; width: auto; }
}
```

**좌우 화살표는 데스크톱에서만 렌더한다** — 세로 스택에는 넘길 방향이 없다. 이 전환은 [[responsive-rules]] 의 캐러셀 항목과 함께 본다.

시그니처:

```tsx
<RecommendCarousel items={cards} onRegenerate={(mode) => …} />
```

- `items` — 5개 추천 세트. 각 항목은 `mode`, `label`, `numbers: number[]`.
- `onRegenerate(mode)` — "다시 생성" 콜백. 결과는 매번 달라진다.

상태: 현재 인덱스, 각 카드의 재생성 로딩 여부. 자동 재생을 넣는다면 `prefers-reduced-motion: reduce` 에서 타이머를 걸지 않는다([[responsive-rules]]). 좌우 화살표·"다시 생성"은 44px 히트 영역. 번호 볼은 LottoBall 을 그대로 쓴다.

문구 주의: 이 컴포넌트 어디에도 "당첨 확률 / 고확률 / 예상 적중률" 을 쓰지 않는다. "재미용 시뮬레이션 · 당첨을 보장하지 않습니다" 고지를 캐러셀 하단에 둔다.

## Modal — 대화상자

화면 중앙에 뜬다. 포커스를 안으로 가두고, 닫으면 포커스를 연 버튼으로 되돌리며, 배경 스크롤을 잠근다. 이 동작은 헤더의 드로어·검색 오버레이와 공유한다(`useModalBehavior`).

**`Esc` 는 어떤 경우에도 막지 않는다.** "닫기 버튼으로만 닫힌다" 는 요구가 있어도 마찬가지다 — 키보드 사용자가 대화상자에 갇히면 안 된다. 막을 수 있는 것은 **배경 클릭**이고, 그것이 `dismissible={false}` 다.

`onClose` 를 주지 않으면 닫기 버튼을 그리지 않는다. 진행 중 대화상자가 그 경우다.

### 생성 진행 대화상자

"다시 생성" 을 누르면 진행 대화상자가 뜬다. 단계 문구는 시간표대로 넘어간다(0s 준비 → 1s 시작 → 2s 조합 → 3s 완료 → 3.5s 닫힘).

**백엔드가 그보다 빨리 답해도 단계를 건너뛰지 않고, 늦게 답하면 완료 단계에서 기다린다.** 진행 표시가 거짓말을 하면 안 된다 — 아직 번호가 없는데 "생성되었습니다" 를 띄우는 일은 없다. 실패하면 대화상자에 사유를 보여주고 그때만 닫을 수 있게 한다.

### 추천 방식 설명 대화상자

"오늘의 추천 번호" 옆의 **글자 pill 버튼**이 연다. 002 개편으로 라벨은 `5가지 방식이란? (전략 설명)` 이다(사용자 시안 `docs/raw/설명버튼예시.png`). 카드에 `완전 랜덤` 이라 써 놓고 그 아래에 `홀짝 1:5 · 합계 153` 을 붙이면 **랜덤이 그 값을 맞추려고 뽑은 것처럼 읽힌다.** 실제로는 뽑은 뒤에 센 값이다. 실제 사용자가 이 오해를 했고, 그래서 설명을 만들었다.

같은 이유로 캐러셀 카드의 성향 숫자 위에 `조합 성향` 라벨을 붙인다. 라벨 하나가 "이것은 결과다" 라고 말해 준다.

**문구 톤 (002 R11).** 이 대화상자의 본문은 **친절한 어조**로 쓴다. 의도(완전 랜덤을 맨 앞에 둔 이유, 통계 조합과 랜덤이 결과적으로 구분되지 않는다는 사실)는 유지하되, "없습니다"·"유일한 정직함"·"감추지 않는" 처럼 **단정적·훈계조** 표현을 쓰지 않는다. 40대+ 사용자가 "가르치려 든다"·"무섭다" 고 느끼지 않게, "함께 즐기는 도구" 의 어조로 설명한다. 전략명 "COLD 번호 부활" 은 "안 나오던 번호 되짚기" 처럼 [[forbidden-expressions]] 라벨 규칙을 따른다. 다만 **면책의 핵심 사실**(당첨을 보장하지 않는다)은 부드럽게라도 반드시 남긴다.

## NumberActions — 번호 내보내기

추천 번호를 **복사 · 이미지 저장 · 공유**한다(초안 10.3).

**자리마다 액션 수가 다르다.** 홈 캐러셀은 5장을 훑어보는 자리이고 카드 폭이 280px 이다. 여기에 버튼을 넷 두면 "다시 생성" 이 묻힌다 — 복사 하나만 아이콘으로 낸다. `/lotto/recommend` 는 번호를 가져가려고 들어오는 자리이므로 셋을 모두 낸다.

복사를 1순위에 두는 이유는 실제 사용 맥락이다. 판매점에서 용지에 옮겨 적거나 메모장에 붙여넣는 일이 가장 잦다.

**피드백은 버튼 안에서 낸다.** 복사는 화면을 바꾸지 않아 성공했는지 알 방법이 없다. `aria-live` 로 스크린리더에도 알린다. 토스트를 띄우면 시선이 화면 구석으로 끌려간다.

### 공유 — Web Share API

`navigator.share` 를 쓴다. 모바일에서 OS 공유 시트가 열려 카카오톡·문자 어디로든 간다. `navigator.canShare({files})` 가 되면 이미지도 함께 보낸다. 지원하지 않는 브라우저(대부분의 데스크톱)에서는 **클립보드 복사로 폴백**한다.

**사용자가 공유 시트를 닫은 것은 실패가 아니다**(`AbortError`). 오류를 띄우지 않는다.

카카오톡 SDK 를 쓰지 않는다. 앱키가 필요하고 외부 스크립트가 하나 더 붙으며 개인정보처리방침에 제3자 스크립트를 명시해야 한다. OS 공유 시트에 이미 카카오톡이 들어 있다.

### 이미지 — Canvas 직접 그리기

1080×1080 정사각. 카카오톡·인스타그램이 자르지 않고, 저장해 두었다가 나중에 봐도 번호가 또렷하다. 가로 이미지는 메신저에서 위아래가 잘린다.

`html2canvas` 같은 라이브러리를 쓰지 않는다 — 그리는 것이 원 6개와 글자 몇 줄뿐이다. 웹폰트가 도착하기 전에 그리면 시스템 폰트로 렌더링되므로 `document.fonts.ready` 를 기다린다. CSS 변수는 canvas 에서 읽을 수 없어 볼 5구간 색을 `share.ts` 에 한 벌 둔다.

**공유 문구와 이미지에 금지 표현을 쓰지 않는다**(초안 10.3). 둘 다 "재미용 시뮬레이션이며 당첨을 보장하지 않습니다" 를 항상 포함한다 — 링크나 이미지가 단독으로 떠돌 때 그것만 보고 판매·예측 사이트로 오해하는 것을 막는다.

## StatBoard — 주요 통계 패널 (002 개편)

002 개편으로 주요 통계는 **4개 분리 카드 → 좌측 탭 테이블 + 우측 막대차트·인사이트의 2분할 패널**로 바뀐다. 정본 레이아웃은 `docs/raw/주요통계_샘플.png`. 목적은 정보 밀도를 올려 "빈약해 보이는" 인상을 없애되(R8·R10), **과거 사실의 정리**임이 드러나 예측으로 오인되지 않게 하는 것이다.

**좌측 — 탭 테이블.** 탭 4종: `최근 N회 HOT 번호` · `안 나오던 번호` · `미출현 기간` · `동반 출현`.

- 표 열: **순위 · 번호(LottoBall) · 출현 횟수 · 출현 비율 · 최근 출현 · 추세**.
- 상위 3위는 메달, 추세는 `↑`/`↓`/`—` 를 **색과 기호를 동시에** 쓴다(색만으로 전달 금지, WCAG 1.4.1 — [[accessibility]]). 숫자는 `tabular-nums`.
- 데이터 매핑([[api-contract]] 통계 절): 출현 횟수 = `count`, 출현 비율 = `appearance_rate`(`65%` 로 표시하되 **"지난 N회 중 나온 비율"** 임이 드러나게 라벨), 최근 출현 = `last_seen_round`(예 `1182회`), 추세 = `trend`. `미출현 기간` 탭은 `hot-cold` 의 `overdue`(`rounds_since`), `동반 출현` 탭은 `GET /stats/pairs` 의 `pairs`(오름차순 번호쌍 + `count`).
- 하단에 "전체 번호 통계 보기 →" 링크(통계 상세로).

**우측 — 막대차트 + 인사이트.**

- `번호 출현 빈도 (최근 N회)` 45개 막대. **차트 위 고정 readout** 에 `23번 · 1회 나왔어요` 를 표시하고, "전체 구간 보기" 버튼을 둔다. `frequency` 응답을 쓴다.
  - 떠 있는 툴팁이 아니라 **차트 위에 자리를 예약한 한 줄**이다. 호버가 없는 터치에서도 읽히고, 값이 바뀌어도 레이아웃이 밀리지 않는다(`min-height` 예약). `aria-live="polite"` 라 키보드로 옮길 때 스크린리더가 값을 읽는다.
  - **가리키는 방법은 홈과 상세가 다르다.** 홈(`fit`)은 막대가 6~7px 이라 개별 컨트롤이 될 수 없어 **차트 전체가 하나의 조작면**이고 포인터 x 좌표로 번호를 고른다(호버·탭·좌우 방향키). 상세(`scroll`)는 막대당 24px↑ 라 **막대 하나하나가 `<button>`** 이고 Tab 으로 옮겨 다닌다. 근거는 [[accessibility]] '작은 표적이 많은 그래프' 절.
- 모바일도 45개를 그대로 그린다. **종전의 "상위 5개 축약" 규칙은 폐기됐다**(코드가 한 번도 그렇게 동작한 적이 없다 → [[responsive-rules]] 차트 축약).
- **인사이트 콜아웃** — 전구 아이콘 + 데이터 기반 **자연어 요약** 한두 문장. 예: "33번이 최근 20회 중 13회로 가장 자주 나왔어요. 10번대 후반과 30번대가 자주 보입니다." 이 문장은 **백엔드 수치로 프론트가 조립**한다(백엔드는 사실 수치만 반환 — 금지표현을 프론트에서 관리하기 쉽다). **과거 요약이지 예측이 아니다** — "다음에 나올" 같은 표현을 쓰지 않는다([[forbidden-expressions]]).

**"COLD" 표기 금지 (R9).** 이 패널 어디에도 "COLD" 를 노출하지 않는다 — 탭·설명·차트 라벨 전부 "안 나오던 번호". 내부 데이터 필드(`cold`)는 유지한다.

**반응형.** 데스크톱은 좌우 2분할. 태블릿·모바일은 세로로 — 탭 테이블 위, 차트(축약형) 아래. 표가 넘치면 자기 컨테이너에서 가로 스크롤([[responsive-rules]] body 가로 스크롤 금지).

props: `window`(20/50/100/all) · `data` · `moreHref`. 상태: 탭 선택, 로딩(스켈레톤), 빈 데이터. `window` 는 쿼리스트링으로 URL 에 싣지 않는다(중복 색인 방지 — [[metadata-strategy]]). 로딩 시 CLS 를 막기 위해 표·차트 슬롯 크기를 미리 예약한다.

## NewsThumb — 뉴스 목록 아이콘 (002 개편)

## ServiceTiles — 홈 아이콘 6타일

로또 6/45 · 번호 통계 · 번호 추천 · 꿈해몽 · 복권 뉴스 · 연금복권(준비중). 각 타일은 아이콘 + 제목 + **한 줄 설명**을 갖는다. 아이콘만 있는 홈은 저가치 페이지로 읽힌다([[adsense-readiness]]).

**아이콘은 진한 컬러 그라디언트 위의 흰 글리프다.** 파스텔 배경이 아니다 — 시안을 보라. 그라디언트는 새 hex 를 만들지 않고 `color-mix(in oklab, var(--svc) 76%, white)` 로 유도하고, 그림자도 같은 색에서 뽑아 아이콘이 자기 색의 빛을 흘리는 것처럼 보이게 한다. 타일 하나가 `--svc` 지역 변수를 정하면 배경·그림자가 그것을 읽으므로 둘이 어긋날 수 없다.

**이모지를 쓰지 않는다.** 📊 ★ ☁ 📰 ⚙ 는 OS·폰트마다 모양과 색이 달라 브랜드 색을 따르지 못하고, 안드로이드·윈도우에서는 시안과 전혀 다른 그림이 나온다. 글리프는 `currentColor` 를 쓰는 인라인 SVG 로 그린다(`frontend/src/components/icons.tsx`).

`로또 6/45` 타일의 글리프는 흰 원에서 "6/45" 를 **도려낸다**(SVG `mask`). 뚫린 자리로 타일 배경이 비친다. 글자를 흰 원 위에 얹으면 색을 하드코딩해야 하는데, 타일 색은 CSS 변수라서 SVG 안에서는 알 수 없다.

`accent` 값 하나가 `--svc-*` 토큰과 아이콘 컴포넌트를 **동시에** 고른다. 색과 그림이 따로 놀지 않는다.

데스크톱에서는 타일 사이에 얇은 세로 구분선을 긋는다(`gap: 0` + `border-left`). 모바일 3×2 에서는 긋지 않는다 — 2행 구조라 선이 격자처럼 보인다. '준비중' 배지는 타일 우상단에 고정한다(아이콘 기준 픽셀 오프셋을 주면 좁은 단에서 타일 밖으로 밀려난다).

## GuideCard — 가이드 카드

로또 가이드 5종(당첨확인 방법 · 당첨금 수령 · 통계 보는 법 · 자동 vs 수동 · 건전한 복권 이용). 파스텔 배경 + 제목 + 한 줄 설명 + "자세히 보기" 링크.

- 배경 파스텔은 서비스 색과 충돌하지 않는 중립 톤을 쓰되, 필요 시 `--svc-*-bg` 계열을 재활용한다([[design-tokens]]).

**가이드 상세페이지에서의 재사용 (002 R16).** 각 가이드 **상세페이지 맨 아래**에 홈처럼 `GuideCard` 그리드(다른 가이드로 바로가기)를 배치한다 — 현재 상세는 상단 Breadcrumb 만 공통이라 한 가이드를 다 읽고 나면 다음 갈 곳이 없다. 홈의 카드 컴포넌트를 그대로 재사용해 일관성을 지킨다(R35). 현재 항목만 빼거나 흐리게 처리한다.

**가이드 상세 레이아웃 (2026-09-17).** "글이 왼쪽으로 치우치고 정적이다"(사용자). 본문을 **780px 읽기 칼럼으로 가운데 모으고**, 1100px 이상에서는 오른쪽에 **목차 레일**(`GuideRail`, sticky · 현재 절 강조 · 읽은 비율 막대)을 둔다. 절은 박스로 감싸지 않고 **장 번호(01, 02…) + 1px 구분선**으로 나눈다 — 안쪽 카드가 '상자 속 상자' 가 되지 않게. 안내(`gd-callout`)는 틴트 바탕 + 아이콘 배지, 비교(`gd-versus`)는 흰 카드 + 모서리 색 번짐 + 색표 번호, 절차(`gd-steps`)는 640px 이상에서 가로로 나란한 큰 번호 카드. 전부 `styles/guide-doc.css`.

**가이드 상세 헤더 이미지 (002 R14·R34).** 각 상세페이지 제목 아래에 대표 일러스트 1장(브랜드 팔레트 플랫 일러스트). 파일은 `frontend/public/guide/*-hero.png`, 명세·프롬프트는 [`002-이미지제작요청서.md`](../../raw/002-이미지제작요청서.md). **남발 금지** — 페이지당 헤더 1장 + 본문 스팟 소수. `aspect-ratio` 로 자리를 예약해 CLS 를 막고([[responsive-rules]]), 다크모드를 위해 배경 투명 이미지를 쓴다. 사진(Pexels)과 일러스트를 한 페이지에 섞지 않는다. 등수 판정 시각화(R19)는 이미지가 아니라 `LottoBall` 컴포넌트로 그린다.

## AdSlot — 광고 슬롯

애드센스 승인 전에는 **아무것도 렌더링하지 않는다**(작업지시서 6.5). 클라이언트 환경변수 `NEXT_PUBLIC_ADSENSE_CLIENT` 가 비어 있으면 광고 코드도, **빈 자리도** 만들지 않는다.

```tsx
export function AdSlot({ slot }: { slot: string }) {
  const client = process.env.NEXT_PUBLIC_ADSENSE_CLIENT;
  if (!client) return null;         // 미승인·미설정 시 완전 미렌더링
  return <ins className="ad-slot" data-ad-client={client} data-ad-slot={slot} />;
}
```

- 승인 **후** 렌더링될 때는 `min-height` 로 자리를 예약해 광고가 늦게 로드돼도 레이아웃이 밀리지 않게 한다(CLS — [[responsive-rules]]).
- "준비 중" 페이지(연금복권·스피또)에는 광고를 넣지 않는다.
- 빈 상자에 "광고" 라벨을 붙이지 않는다.

> **정정 (2026-07-09).** 이 페이지는 원래 "미승인 상태에서도 `min-height` 를 예약한다" 고 적었다. **틀린 규칙이었다.** 광고가 없으면 늦게 도착할 것도 없어 CLS 가 발생하지 않는다. 남는 것은 콘텐츠 사이의 200px 짜리 빈 구멍뿐이고, 승인은 몇 달 뒤일 수 있다. 승인 시점에는 어차피 환경변수를 넣고 다시 빌드하므로 그때 자리가 생긴다. 실제로 이 예약이 홈의 "주요 통계 ↔ 오늘의 추천 번호" 사이를 벌려 놓았고, 사용자가 그것을 발견했다.

props: `slot`(광고 슬롯 ID). 상태: 렌더 여부(환경변수에 의존)만.

## GuideSection — 화면 하단 안내 절 (표본 해부)

기능 화면 아홉 곳(`/`, `/lotto`, `/lotto/latest`, `/lotto/recommend`, 통계 3종, `/dream`, `/news`)의 하단 설명이 공유하는 구조다. `components/GuideSection.tsx`.

**왜 바꿨나.** 종전에는 세 화면 모두 `.prose` 안에 `h3` 네 개와 문단 열 개가 줄글로 이어졌다. 내용은 정확했지만 모바일에서 벽처럼 읽혀 끝까지 내려가지 않았고, "쉽게 말씀드리자면 —", "동전으로 설명드리자면 —" 같은 상투구가 반복돼 기계가 쓴 글처럼 읽혔다(사용자 지적, 2026-08-21).

**원리.** 설명을 **화면에 실제로 보이는 조각에 붙인다.** 표 한 줄·추세 배지·볼 다섯 색·히트맵 칸·미니 막대를 그대로 놓고 그 아래 라벨과 한 줄 설명을 단다.

| 구성 | 역할 |
|------|------|
| `GuideSection` | 절 껍데기. `headingId` 는 기존 `aria-labelledby` 값을 그대로 받는다 |
| `SpecimenGrid` | 표본 카드 격자. 375 **1열** → 640 **2열**(홀수면 마지막만 전폭) → 1024 **3열** |
| `SpecimenCard` | 표본 하나. 조각 + 라벨/설명 목록 |
| `GuideNote` | 표본으로 설명할 수 없는 것(왜 그런 모양인지, 무엇을 뜻하지 않는지). 격자 아래 전폭 |

**규칙 셋.**

- ⚠ **클래스 접두어는 `spec-` 이다.** `.guide-card`/`.guide-grid` 는 **가이드 문서 링크 카드**(`components/GuideCard.tsx`)가 이미 쓴다. 같은 이름을 쓰면 나중에 선언된 쪽이 이겨 홈·`/guide`·`/lotto` 의 파스텔 링크 카드가 통째로 깨진다 — 실제로 깨뜨렸다가 잡았다(2026-08-21). 컴포넌트 이름도 `GuideCard` 가 아니라 `SpecimenCard` 다.
- **표본에는 '예시' 배지가 강제로 붙는다.** 숫자가 위쪽 실제 표와 다를 수밖에 없고(구간을 바꾸면 표는 바뀌지만 설명은 그대로다), 같아 보이면 오히려 오해를 만든다. `GuideCard` 가 붙이며 호출부가 끌 수 없다.
- **조각은 진짜 컴포넌트 클래스를 쓴다**(`.ball`, `.trend`). 진짜를 떼어 올 수 없는 것만 `.spec-minibar`·`.spec-heatcell` 로 흉내 내되 **같은 토큰**을 쓴다 — 여기서 새 색을 만들면 원본이 바뀔 때 설명 그림만 낡는다.
- **서버 컴포넌트다.** 상호작용이 없다. JS 를 꺼도 본문이 보여야 하고(완료 기준), 이 절이 페이지 콘텐츠 가치의 큰 몫이다([[adsense-readiness]]).

**바로가기 카드 아이콘.** `StatNav` 의 세 카드에 내용을 가리키는 아이콘을 둔다 — 순위는 내림차순 막대, 빈도는 일부 채워진 45칸 격자, 패턴은 반으로 나뉜 원(비율). ⚠ **트로피를 쓰지 않는다** — '당첨'을 암시해 심사에서 도박 조장으로 읽힐 수 있다([[forbidden-expressions]]). 달력도 쓰지 않는다 — 이 화면들은 날짜가 아니라 번호에 관한 것이다. 색은 `currentColor` 로 받아 다크 모드에서 따로 손댈 것이 없다.

### 색 — accent 순환

카드 자리가 색을 정한다. **모든 화면에서 같은 순서로 돈다.**

| 카드 | accent | 파스텔 |
|---|---|---|
| 1번째 | `news` | 파랑 |
| 2번째 | `lotto` | 초록 |
| 3번째 | `reco` | 주황 |
| 4번째 | `stats` | 보라 |

⚠ **색은 아무 뜻도 가리키지 않는다.** 순서대로 도는 팔레트일 뿐이다. 뜻을 담으려 하지 말 것 — 담는 순간 카드를 옮길 때마다 색을 다시 정해야 한다.

### ★ `--spec-ink` — 파스텔 위 제목·아이콘 색

참조 시안은 제목을 `--svc-*` **원색**으로 쓴다. **그대로 하면 안 된다** — 여섯 색 전부 AA 미달이다(reco 1.91 · lotto 2.65 · dream 2.92 · news 3.09 · pension 2.19 · stats 3.64). 그래서 `--color-text` 와 섞어 어둡게 만든 값을 카드가 지역 변수로 들고 있고, 제목과 아이콘이 그것을 공유한다.

```css
.spec-card[data-accent='reco'] { --spec-ink: color-mix(in oklab, var(--svc-reco) 50%, var(--color-text)); }
```

**한 줄이 라이트·다크를 동시에 만족한다.** `--color-text` 가 테마에 따라 `#1a1d2e` ↔ `#e6e9ef` 로 뒤집히므로, 같은 식이 라이트에서는 어둡게 다크에서는 밝게 섞인다. 테마별 값을 따로 둘 필요가 없다.

⚠ 비율은 accent 마다 다르다(50~80%). **전부 같은 값으로 통일할 수 없다** — 60%로 맞추면 라이트에서 reco 4.14 · pension 4.45 로 미달한다. ⚠ 비율을 **올리면**(원색에 가까워지면) 대비가 **떨어진다.**

### 그 밖의 규칙

- **아이콘은 흰 타일 위에.** 파스텔에 원색 글리프를 바로 얹으면 비텍스트 3:1 을 못 넘긴다. `.spec-card-icon` 이 `.stat-card-icon` 과 같은 문법이다.
- **표본 조각(`.spec-body`)은 흰 배경.** `.spec-rank` 가 `--color-text-subtle` 을 쓰는데 그 색은 중립 배경 전용이다.
- **`dl.spec-notes` 자체가 2열 grid 다.** dt/dd 를 `<div>` 로 감싸면 행마다 grid 가 따로 생겨 **라벨 칸 폭이 줄마다 달라지고** 설명 글머리가 들쑥날쑥해진다(실제로 지적받았다). 감싸지 말 것.
- 아이콘은 `components/icons.tsx` 의 **stroke 계열**(`STROKE_BASE`)에서 고른다. 트로피·달력 금지.

## Faq — 자주 묻는 질문

`components/Faq.tsx`. 아홉 화면과 가이드 3편이 공유한다.

- **`<details>/<summary>` 를 쓴다.** JS 를 꺼도 펼쳐지고(완료 기준), 키보드·스크린리더 동작을 브라우저가 준다. 직접 만든 아코디언은 `aria-expanded`·포커스를 손으로 맞춰야 하고 대개 틀린다.
- **답변은 평문 문자열만 받는다.** FAQPage 구조화 데이터는 **화면에 보이는 텍스트와 정확히 일치할 때만** 내보낼 수 있는데([[structured-data]]), JSX 를 허용하면 그 일치를 보장할 수 없다. 링크가 꼭 필요한 문답은 FAQ 가 아니라 본문에 둔다.
- `headingId` 로 제목 id 를 분리한다. 한 페이지에 FAQ 가 둘이면 `aria-labelledby` 가 엉뚱한 제목을 가리킨다.
- `structuredData={false}` 로 JSON-LD 를 끌 수 있다. **한 페이지에 FAQPage 를 두 번 내보내지 않는다.**
- **한 줄에 하나씩 쌓는다.** 한때 데스크톱에서 2열로 폈으나 되돌렸다(2026-08-25 사용자 지시). 2열은 같은 행의 두 칸 높이를 묶어 버려 펼침 버그의 원인이 되기도 했다.
- 금지 표현은 여기에도 적용된다. 질문이 예측을 전제하면 답변에서 그 전제를 바로잡되, **질문 문구 자체가 예측을 약속하게 두지 않는다**([[forbidden-expressions]]).

### 시각 규칙

- **`.faq-list` 의 `align-items: start` 를 지운다.** 2열이던 시절, grid 기본 정렬 `stretch` 때문에 한 항목을 펼치면 **같은 행의 옆 항목도 같은 높이로 늘어나** 빈 채로 열린 것처럼 보였다(실제 버그, 2026-08-25). 지금은 1열이라 증상이 나지 않지만, 다시 여러 열로 펴는 순간 그대로 재발한다.
- **갈매기 크기는 SVG 속성으로도 못박는다.** CSS 에만 맡기면 그 규칙이 안 먹을 때 SVG 가 부모 칸을 통째로 채운다("아이콘이 영역을 다 차지한다" 지적).
- 펼침 상태는 **테두리 색 하나로 알리지 않는다.** 배경(`--color-primary-soft`)과 왼쪽 막대를 함께 바꾼다.
- 답변 왼쪽에 세로선을 둬 어느 질문의 답인지 눈으로 잇는다.
- **FAQ 는 일부러 조용하게 둔다.** 파스텔 카드가 이미 색을 다 쓰고 있어 FAQ 까지 화려하면 하단이 시끄러워진다.
- 답변 톤: 결론을 먼저 말하고 이유를 뒤에 붙인다. 어려운 말은 예를 하나 들어 푼다. 그래도 **사실만** 말한다.

## ScrollArea — 가로로 넘치는 영역

`components/ScrollArea.tsx`. 표 7곳과 합계 히스토그램이 쓴다. `overflow-x: auto` 컨테이너를 새로 만들 때는 `<div>` 대신 이것을 쓴다.

### 왜 있는가 — 두 가지

**① 키보드 접근.** 스크롤 컨테이너 안에 포커스 받는 요소가 하나도 없으면(표·차트가 딱 그렇다) 키보드만 쓰는 사용자는 그 영역을 **좌우로 움직일 방법이 아예 없다.** 화면에는 멀쩡히 보이는데 잘린 열을 영영 못 본다. axe `scrollable-region-focusable` 이 이것을 잡는다(2026-08-21 실측: 표 7곳 + 차트 1곳). `tabIndex={0}` 만으로 규칙은 통과하지만 이름 없는 상자에 포커스가 떨어지므로 `role="region"` + `aria-label` 을 **함께 요구한다**(`label` 이 선택항목이 아닌 이유).

**② 더 있다는 신호**(2026-08-27). 잘려 있다는 것을 모르면 스크롤할 생각 자체를 하지 않는다. 번호추천의 기준 선택에서 같은 지적을 받았고("그냥 보면 메뉴 3개만 있는 것처럼 보여"), 거기서 쓴 **신호 셋**을 그대로 가져왔다.

| 신호 | 역할 |
|------|------|
| 가장자리 페이드 | 내용이 이어진다 |
| 좌우 화살표 | 더 있다 + **실제로 옮기는 수단** |
| 안내 문구 | 화살표를 못 알아보는 사용자를 위해 |

**화살표는 PC 에서 특히 중요하다.** 마우스 휠로는 가로 스크롤이 되지 않아, 화살표가 없으면 데스크톱 사용자는 잘린 열을 사실상 못 본다. 모바일만 생각하고 만들면 이 경우를 놓친다.

### 반드시 지킬 것

- **넘칠 때만 신호를 낸다.** 끝까지 민 뒤에도 페이드가 남으면 거짓말이 된다. `data-more-left` / `data-more-right` 로 방향별로 판정한다.
- **화살표는 레일 안에서 `position: sticky`** 로 세운다. `.scroll-area` 에 `top: 50%` 로 직접 붙이면 **영역 높이의 한가운데**에 놓이는데, 회차 표처럼 세로로 8,000px 인 표에서는 그 지점이 화면 밖이라 아무도 못 본다(실측하고 고쳤다).
- **레일에 `aria-hidden` 을 걸지 않는다.** 조상에 걸면 안의 버튼도 함께 숨겨지고(자손이 되돌릴 수 없다) 포커스는 받는데 이름이 없는 버튼이 되어 axe `aria-hidden-focus` 에 걸린다. 레일은 `pointer-events: none` 으로 클릭만 통과시킨다.
- **안내 문구는 영역 위**에 둔다. 아래에 두면 긴 표에서 8,000px 아래에 놓여 아무도 못 읽는다.
- **문구 자리는 항상 차지하고 보이기만 토글한다.** 넘침 여부는 마운트 뒤에 정해지므로 없다가 생기면 아래가 밀린다(CLS).
- 페이드·화살표는 **스크롤 컨테이너 바깥 래퍼**에 건다. 안에 `absolute` 로 두면 내용과 함께 흘러가 가장자리에 머물지 못한다.

### 캐러셀도 같은 규칙을 따른다

홈의 `RecommendCarousel` 은 `ScrollArea` 를 쓰지 않지만(카드 안에 포커스 받는 버튼이 이미 있어 키보드 접근은 이미 된다) **끝 판정과 페이드는 같은 규칙**을 쓴다.

- 화살표는 **그 방향에 더 있을 때만** 낸다. 처음에는 양쪽이 늘 떠 있어, 끝에 닿아도 화살표가 남고 눌러도 아무 일이 없었다(2026-08-27에 고침).
- 갈매기는 `ScrollArea` 와 **같은 SVG**를 쓴다. 텍스트 글리프(`‹` `›`)를 쓰면 같은 일을 하는 버튼이 다르게 보인다.
- 모바일(~1023px)은 세로 스택이라 넘치지 않으므로 화살표도 페이드도 나오지 않는다 — 상태 계산이 저절로 그렇게 만든다.

### JS 없는 대안이 통하는 곳 / 안 통하는 곳

알약 트랙(`.tabs`)에는 **배경 스크롤 그림자**(`background-attachment: local`)를 쓴다 — 상태 계산도 리렌더도 없다.

⚠ **표와 히스토그램에는 그 기법을 쓸 수 없다.** 표의 행과 차트의 막대가 불투명해서 컨테이너 배경이 한 점도 보이지 않는다. 처음에 셋을 묶어 걸었다가 그림자가 아예 나타나지 않아 되돌렸다. **내용이 배경을 가리는 곳에서는 통하지 않는다**가 판정 기준이다.

## DreamStudio — 꿈해몽 번호

`components/DreamStudio.tsx`. `/dream` 과 `/dream/{키워드}` 가 공유한다.

### 입력

- **150자 상한.** `maxLength` 로 실제로 막고, 남은 글자 수를 옆에 센다. 길수록 엉뚱한 단어가 딸려 온다.
- 도움말은 **무엇을 적어야 하는지**를 말한다 — "꿈에서 본 동물, 사물, 행동 등을 중심으로".
- **추천 개수** 1~10. 번호추천 화면과 **같은 문법**(`.set-count-chips`)이라 한 번 익히면 두 곳에서 통한다. 결과가 이미 있으면 개수를 바꾸는 순간 다시 요청한다. 라벨은 두 화면 모두 "추천 개수" 다 — "조합 개수" 로 부르던 것을 2026-08-27 에 바꿨다.
- **첫 요청은 20초가 걸릴 수 있다**(분석 모델 lazy 로드, [[dream-pipeline]]). 로딩 문구로 미리 알린다. 알리지 않으면 고장으로 여기고 떠난다.

### 말은 쉬운 말로

⚠ **"표제어" 같은 말을 쓰지 않는다.** 사전 만드는 사람의 말이지 꿈 얘기 하러 온 사람의 말이 아니다(2026-08-27 사용자 지적). "자료에 있는 단어" 라고 쓴다. 반대로 *"꿈 내용에서 넓혀 본 단어"* 처럼 **무슨 일이 일어났는지 그대로 풀어 쓴 말**은 길어도 좋다 — 사용자가 그런 표현을 좋게 봤다.

### 분석 결과 — 근거를 낱낱이 보여준다

어떤 단어에서 어떤 번호가 나왔는지 감추지 않는다. 근거가 보이지 않으면 결과를 납득할 수 없고, **보여주는 것 자체가 이 기능의 콘텐츠 가치**다.

| 갈래 (`gubun`) | 화면 이름 | 표시 |
|---|---|---|
| 1 | 정확히 일치하는 단어 | 펼친 채로 — 가장 확실한 근거라 먼저 보여야 한다 |
| 2 | 포함된 단어 | 접어 둔다 |
| 3 | 뜻이 비슷한 단어 | 접어 둔다 |
| — | 꿈 내용에서 넓혀 본 단어 | 접어 둔다 (아래) |

**2026-09-17 레인 카드로 재설계**(사용자 요청 "보기 좋게"). 세 갈래가 소제목 글자로만 나뉘어 훑어볼 때 구분되지 않았다.

- 결과 맨 위에 **적어 주신 문장**을 다시 보여 주고, 원문에 있는 상징 단어에 형광펜을 칠한다. 문자열 표시만 한다 — 원문 포함 판정은 서버(`from_text`)가 이미 했다.
- 세 갈래를 **레인 카드**로 나눈다. 레인마다 모양 아이콘(과녁·품은 상자·물결) · 이름 · 한 줄 뜻 · 조합 라벨(일치/포함/비슷) · "단어 N · 번호 N" 이 붙는다.
- 레인 테두리 **선 모양이 조합 속 볼 테두리와 같다**(실선/파선/점선, `[data-origin]` 재사용). 위에서 본 갈래를 아래 조합에서 다시 알아보게 하려는 것이다. 색을 새로 만들지 않는다.
- **900px 이상은 세 레인을 모두 펼쳐 3열로**, 좁은 화면은 위 표대로 일치만 펼친다. 접힌 레인은 앞 단어 세 개를 미리 보여 준다. 비어 있는 갈래도 레인을 지우지 않는다 — "없음" 도 정보다.
- 스타일은 `styles/dream.css`.

### ⚠ `dream_word` 를 그대로 "적으신 단어" 라고 부르지 않는다

백엔드 형태소 분석이 원문 어절을 **유의어로 확장**하므로, `matched_words[].dream_word` 에는 사용자가 적지 않은 단어가 섞인다([[dream-pipeline]] 의 함정 절). "집으로 들어오는" 이라고 적으면 `건물` 이 `gubun=1` 로 내려오고, 어간 되돌리기 실패로 `크함` · `꾸음` 같은 **말도 아닌 것**이 나오기도 한다. 그대로 나열했더니 "왜 건물이 나왔는지 모르겠다" 는 지적을 받았다(2026-08-27).

**대응**: `result.text` 에 실제로 들어 있는 `dream_word` 만 상단 상징 칩과 갈래 목록에 세우고, 나머지는 *"꿈 내용에서 넓혀 본 단어"* 로 접어 둔다. 접힌 안에서 **번호에는 함께 반영된다고 밝힌다** — 숨기는 것이 아니라 자리를 옮기는 것이다.

⚠ 판정은 **서버가 한다**(2026-08-28 계약 `matched_words[].from_text`). 프론트가 하던 문자열 포함 판정을 그대로 서버로 옮긴 것이라 분류가 달라지지 않는다.

⚠ **`from_text` 를 `?? 원문포함` 으로 읽는다.** 구버전 백엔드는 이 필드를 주지 않는데, `undefined` 를 `false` 로 읽으면 **모든 단어가 '넓혀 본 단어'** 가 되어 상단 상징이 통째로 빈다. 없을 때만 예전 규칙으로 되돌아간다.

⚠ 백엔드가 비단어(`크함`·`꾸음`)도 함께 걸렀다. 응답 필드는 그대로이고 **근거 없는 항목이 사라질 뿐**이라 프론트가 대응할 것은 없다.

**접혀 있다는 것이 한눈에 보여야 한다**(사용자 요구). 갈매기만 두지 않고 **개수 배지 + "펼쳐 보기" 라는 말**을 함께 낸다 — 아이콘만으로는 알아보지 못하는 사람이 있다. 펼치면 문구가 "접기" 로 바뀐다.

⚠ 유사도 점수는 응답에 없고, 있어도 보여주지 않는다. 사용자는 그것을 확률로 읽는다([[forbidden-expressions]]).

### 추천 범위

tier 는 `gubun` 을 **누적**한다(tier1=1, tier2=1+2, tier3=1+2+3). 이름을 그 사실 그대로 짓는다 — "정확히 일치하는 단어만" / "일치 + 포함된 단어" / "일치 + 포함 + 유사한 단어". "얼마나 넓게 찾았는가" 같은 추상적 이름은 위쪽 분석 결과와 이어지지 않는다. 세로로 쌓는다(이름이 길어 가로로는 잘린다).

### 요청한 만큼 안 나올 수 있다 — **이유가 둘이다**

보여줄 수 있는 조합이 요청한 개수보다 적으면 그 차이를 말한다. 말하지 않으면 "5개 골랐는데 1개만 나왔다" 가 고장으로 읽힌다(사용자 지적).

⚠ **어느 쪽 이유인지 갈라서 말한다.** 대응이 다르기 때문이다.

| 이유 | 문구가 가리켜야 할 것 |
|---|---|
| 번호 풀이 좁아 서로 다른 조합을 못 만든다 | 범위를 넓히거나 꿈을 더 구체적으로 |
| 사용자가 뺀 번호 때문에 걸러졌다 | 뺀 번호를 다시 넣거나 범위를 넓히거나 |

실측: 풀 6개 → 서로 다른 조합 1개(C(6,6)=1). 문구는 사실만 말하고 **다음 행동을 함께 준다.** 원인만 말하고 끝내면 막다른 길이 된다.

### 번호마다 **어디서 왔는지**를 글자로 붙인다

이 화면에서 사용자가 가장 좋아한 것이 "왜 이 번호인지 보이는 것" 이었다(2026-08-27). 그래서 조합 안의 번호마다 출처를 **두 글자 라벨**로 적는다.

| 라벨 | 뜻 | 선 모양 |
|---|---|---|
| 일치 | 적으신 단어와 그대로 맞은 번호 | 실선 |
| 포함 | 적으신 단어를 품은 단어에서 온 번호 | 파선 |
| 비슷 | 뜻이 가까운 단어에서 온 번호 | 점선 |
| 관련 | 꿈 내용에서 넓혀 본 단어에서 온 번호 | 옅은 점선 |
| 채움 | 번호가 모자라 채운 자리 | 없음 |

- ⚠ **색만으로 나누지 않는다.** 라벨 글자가 주 정보이고 색·선 모양은 거들 뿐이다. 색을 구별하지 못하는 사용자에게 색뿐인 표식은 아무 정보도 아니다([[accessibility]]).
- ⚠ 라벨은 **두 글자로 맞춘다.** 320px 에서 볼 여섯 개 아래에 나란히 들어가야 한다(실측 통과). 6열 격자라 라벨이 볼 바로 아래에 정렬된다.
- ⚠ 한 번호가 여러 갈래에 걸리면 **가장 가까운 쪽**만 남긴다(일치 > 포함 > 비슷 > 관련). 사용자가 알고 싶은 것은 "이 번호가 내 꿈과 얼마나 가까운가" 이지 몇 군데서 나왔는가가 아니다.
- **번호 목록에도 같은 표식**을 준다. 거기서 갈래를 보고 뺄 번호를 고르기 때문이다. 다만 최대 20개가 늘어서므로 글자 라벨은 붙이지 않고 선 모양만 쓰며, 바로 아래 범례가 그것을 풀어 준다.
- **범례는 목록과 조합 사이**에 놓고, 그 화면에 **실제로 나온 갈래만** 낸다. 안 나온 갈래까지 설명하면 소음이다.
- ⚠ 볼 자체의 색은 건드리지 않는다 — 공식 5구간 색이다([[0009-official-ball-colors-over-mockup]]). 표식은 볼 **바깥**(outline)에 그린다.

### 쓰기 싫은 번호를 뺄 수 있다

번호 목록의 각 번호가 곧 **제외 스위치**다. 누르면 그 번호가 든 조합이 화면에서 빠지고, 다시 누르면 돌아온다.

- **별도 화면이나 대화상자를 두지 않는다.** 빼고 싶은 번호는 목록을 보는 그 순간 눈에 띄므로, 그 자리에서 바로 눌러야 한다.
- ⚠ **44px 터치 타겟.** 볼은 36px 이라 그대로 두면 모바일에서 오탭이 잦고, 여기서 오탭하면 결과가 통째로 바뀌므로 비싸다.
- ⚠ 뺀 상태를 **흐림(색)만으로 알리지 않는다.** 취소선을 함께 긋고 `aria-pressed` 로 상태를 말한다.
- ⚠ **서버가 뺀다**(2026-08-28 계약 `exclude: number[]`, 최대 39). 프론트가 세 배로 받아 거르던 우회를 걷어냈다 — 그 방식은 **채움 번호를 아예 뺄 수 없었다.** 풀에서만 빠지니 "뺐는데 또 나온다" 가 됐다. 이제 풀에서도 채움에서도 빠지고 응답의 `pool` 에서도 빠진다.
- ⚠ **`pool` 에서도 빠지는 것이 함정이다.** 그것만 보고 스위치를 그리면 **뺀 번호가 목록에서 사라져 되돌릴 수 없다.** 제외 없이 받은 결과의 풀을 따로 기억해(`basePools`) 스위치는 그것으로, 조합만 제외가 반영된 결과로 그린다.
- ⚠ 제외 토글은 **재요청**이므로 그동안 스위치를 잠근다. 연타로 요청이 겹치면 늦게 온 응답이 이긴다. 20초 대기는 첫 요청에만 해당하므로 즉시 반응보다 **정확성**을 택했다.
- ⚠ `run()` 이 제외 집합을 **인자로 받는다.** `useState` 값을 그대로 읽으면 토글 직후 호출에서 갱신 전 값이 잡혀 **방금 뺀 번호가 한 박자 늦게** 반영된다.
- 목록 전용 출처 판정을 따로 둔다(`poolOriginOf`). 조합용을 그대로 쓰면 제외된 번호가 `tier.pool` 에 없어 **'채움' 으로 읽히고**, 화면에서는 취소선에 가려도 스크린리더에는 틀린 말이 들린다.
- **제외는 새 꿈을 분석할 때만 비운다.** 개수를 바꾸거나 범위를 옮기는 것은 같은 꿈을 계속 보는 중이라, 그때 풀리면 뺐던 번호가 슬그머니 되돌아온다.

### 채워진 번호를 감추지 않는다

⚠ 풀이 여섯 개보다 적으면 백엔드가 **1~45 무작위**로 나머지를 채운다([[dream-pipeline]]). 그 사실을 고지하고, 조합 안에서 **꿈에서 온 번호에 테두리 표식**을 붙여 구분한다. 전부 꿈에서 왔다고 두면 거짓말이다.

⚠ 풀이 여섯 개 이상이면 표식을 **붙이지 않는다.** 여섯 자리가 모두 꿈에서 온 번호라 전부에 붙어 아무것도 구분하지 못한다.

⚠ 볼 자체의 색은 건드리지 않는다 — 공식 5구간 색이다([[0009-official-ball-colors-over-mockup]]).

### 내보내기

`BulkActions`(전체 복사·이미지 저장·공유)와 조합마다 `NumberActions`. **`sourcePath="/dream"` 을 반드시 넘긴다** — 기본값이 `/lotto/recommend` 라, 빠뜨리면 꿈해몽 번호를 공유했는데 링크가 번호추천으로 가서 받은 사람이 같은 결과를 찾을 수 없다.

## DreamGuide — 꿈해몽 화면의 하단 공통 절

`components/DreamGuide.tsx`. 만드는 법 설명(표본 카드 3장 + 안내 블록)과 자주 묻는 질문을 담는다.

- **`/dream` 과 `/dream/{소재}` 가 같은 것을 본다.** 소재 페이지로 바로 들어온 사용자도 번호가 어떻게 만들어지는지, 꿈과 결과 사이에 관계가 없다는 것을 같은 밀도로 읽어야 한다. 종전에는 소재 페이지에 줄글 몇 문단뿐이라 설명의 밀도가 확연히 낮았다(2026-08-27 사용자 지적).
- **두 페이지에 복사해 두지 않는다.** 복사하면 한쪽만 고쳐지고, 그 순간 FAQPage 구조화 데이터와 화면 텍스트가 페이지마다 달라진다.
- **FAQPage 는 이 컴포넌트가 담당한다.** 이걸 쓰는 페이지에 `Faq` 를 또 두지 않는다 — 한 페이지에 FAQPage 가 둘이면 안 된다([[structured-data]]).
- 같은 말을 두 번 하지 않는다. "꿈을 꾸었다고 당첨 가능성이 달라지지 않는다" 는 안내 블록이 담당하므로 소재 페이지 본문에서 뺐다.

### 소재별 민간 해석은 상자에 넣지 않는다

`.dream-lore` — 소재 페이지에만 있는, 그 페이지의 **유일한 고유 본문**이다([[0013-dream-meanings-in-frontend]]).

- **상자로 가두지 않는다.** 파스텔 상자에 넣었더니 본문에서 떨어져 나가 광고나 알림처럼 읽혔다. 본문 흐름 안에 두고 **글꼴 색으로만** 구별한다(2026-08-27 사용자 요구).
- **왼쪽 세로선 하나는 남긴다.** 색만으로 구분하면 색을 구별하지 못하는 사용자에게 아무 신호도 남지 않는다([[accessibility]] 색 단독 사용 금지).
- 글꼴 색은 `--svc-dream` 원색이 아니라 `--color-text` 와 섞은 값이다. 원색은 본문 배경 위 대비 2.92 로 미달이다 — `--spec-ink` 와 같은 기법으로 한 줄이 라이트·다크 양쪽을 만족한다.
- 첫 줄에 **무엇인지 먼저 밝힌다**("전해 오는 민간 해석 · 재미로만 참고하세요"). 읽기 전에 성격을 알아야 한다.

## RoundNumberHistory — 회차 번호들의 그때까지 기록

`components/RoundNumberHistory.tsx`. 회차 상세(`/lotto/round/{n}`)에만 있다.

### 왜 만들었나

회차 상세 두 장(1238회 vs 1237회)을 실측했더니 **서로 다른 낱말 36개 / 겹치는 낱말 186개**였다. 본문의 84%가 회차마다 똑같은 문구라는 뜻이다. 색인 대상 URL 1,287개 중 **96%가 이 페이지**이므로([[metadata-strategy]]), 회차마다 실제로 다른 문장이 필요했다.

붙인 뒤: **서로 다른 낱말 77개 / 겹치는 226개**, 본문 1,150자 → 1,786자. 고유 낱말 비율 16% → 25%.

### ⚠ 그 회차 시점의 사실만 말한다 — 이 절의 가장 중요한 제약

`/stats/number/{n}` 에 `from_round: 1` · `to_round: 그 회차` 를 **함께** 주면(하나만 주면 422) `count` · `rank` · `recent_appearances` 가 그 구간 기준으로 온다. **그러나 `rounds_since` · `last_seen_round` · `max_gap` 셋은 계약상 언제나 최신 회차 기준이다**([[api-contract-stats]]). 실측으로도 확인했다 — `to_round=900` 으로 물어도 `last_seen_round` 는 1235 를 준다.

**그 셋을 쓰지 않는다.** 900회 페이지에 "3회 만에 나왔습니다" 라고 적으면 오늘의 사실이지 2020년 그 회차의 사실이 아니다. "얼마나 쉬었는지" 는 `recent_appearances` 에서 **이 회차보다 작은 회차 중 가장 큰 것**을 찾아 뺄셈한다 — 구간 기준이라 어느 회차에서도 참이다. 인덱스(`[1]`)로 집지 않는 것은 정렬이 바뀌어도 문장이 틀리지 않게 하기 위해서다.

> 뺄셈은 집계가 아니다. 횟수·순위는 전부 백엔드 값을 그대로 쓴다([[component-boundaries]]).

### ⚠ 여섯 개를 다 받았을 때만 그린다

일부만 받고 그리면 요약이 **거짓**이 된다 — 셋만 보고 "여섯 개 가운데 가장 자주 나온 번호는 X" 라고 적게 된다. 실제로 그런 페이지가 구워진 것을 발견했다(1238회, 2026-08-28). 빌드 순간 백엔드가 재시작 중이면 생기는 일이다. 그때는 절을 통째로 비우고 ISR 재검증 때 채워지게 둔다 — **틀린 문장을 캐시하는 것보다 없는 편이 낫다.**

### ⚠ 장애를 삼키지 않는다 — 없음과 장애를 가른다

**규칙은 하나다: 없음(404)은 캐시해도 되고, 장애는 캐시하면 안 된다.**

둘을 뭉개면 장애가 404 로 굳는다. 백엔드가 죽은 동안 회차 페이지를 요청하면 `notFound()` 가 불리고 그 404 가 ISR 캐시에 **일주일** 남아, 백엔드가 살아난 뒤에도 그 회차는 계속 "없는 페이지" 다(2026-08-28 에 500회에서 실제로 겪었다).

`lib/api.ts` 의 `getJsonOrThrow` 가 404 만 `null` 로, 나머지 실패는 `BackendUnavailableError` 로 가른다. 회차 상세는 `getRound` 와 `getNumberStatStrict` 로 그것을 쓴다.

실측(목 백엔드를 껐다 켜서):

| | 수정 전 | 수정 후 |
|---|---|---|
| 장애 중 요청 | 404 | **500** |
| 백엔드 복구 후 같은 회차 | 404 (일주일 유지) | **200** |
| 진짜 없는 회차 | 404 | 404 (그대로) |

⚠ **같은 데이터라도 화면에 따라 다루는 방식이 갈린다.** `/lotto/stat` 은 `getNumberStat`(삼키는 쪽)을 쓴다 — 거기서는 이 엔드포인트로 **구현 여부만 떠보는** 것이라, 장애로 던지면 다른 데이터로 충분히 서는 페이지가 통째로 500 이 된다. 판정 기준은 **그 데이터가 없을 때 페이지가 성립하는가**다.

⚠ 정적 생성 중에 던지면 **빌드가 실패한다.** 그것이 의도다 — 백엔드가 죽은 채로 구운 404 를 배포하는 것보다 빌드가 멈추고 원인을 알려 주는 편이 낫다.

⚠ `error.tsx` 를 두었지만 **아직 만들어지지 않은 회차를 요청 시 생성하다 실패하면 그 경계가 타지 않고** Next 자체 500 이 나간다(실측). 이 파일이 잡는 것은 이미 만들어진 페이지의 오류다. 캐시를 막는 목적은 두 경우 모두 이루어지므로 그대로 둔다.

### 그 밖

- **직렬로 부른다.** 여섯 개를 `Promise.all` 로 던지면 Next 가 페이지 300장을 병렬로 굽는 것과 곱해진다. 호출 하나가 15ms 라 줄 세워도 0.1초다. 여기서 아낄 것이 없다.
- **회차 번호에 천단위 구분을 넣지 않는다.** 페이지의 다른 문장이 전부 "제1238회" 인데 "제1,233회" 가 섞이면 다른 것을 가리키는 것처럼 읽힌다(실제로 그렇게 나왔다). 출현 **횟수**에는 넣는다 — 그쪽은 세는 수다.
- **문구를 짧게 끊는다.** "45개 번호 가운데 37위" 는 375px 에서 "가 / 운데" 로 쪼개졌다. "45개 중 37위" 로 줄였다. 어느 회차까지인지는 절 제목과 요약이 말하므로 행마다 되풀이하지 않는다.
- **면책을 반드시 붙인다.** 출현 횟수와 순위를 나란히 두면 "많이 나온 번호가 또 나온다" 로 읽히기 쉽다([[forbidden-expressions]]).

## 영상 — `VideoCard` · `VideoEmbed` · `YouTubeAttribution`

`components/video/*`, `app/videos/*`. 2026-08-28 계약 신설([[api-contract]] 영상 절).

### ⚠ 이 화면들의 규칙은 취향이 아니라 **정책**이다

YouTube 개발자 정책과 자료 사용 프레임워크(RMF)가 요구하는 것들이다([[youtube-data-api]]). 디자인 사정으로 바꾸지 않는다.

| 요구 | 지키는 방법 | 어디서 |
|---|---|---|
| III.F.2 — **썸네일 포함** 출처 표시 의무 | `YouTubeAttribution` 을 **썸네일이 있는 모든 곳**에 붙인다. 홈 카드까지다 | `VideoCard` |
| RMF — 최소 200×200px | `.video-embed` 의 `min-width`·`min-height` | CSS |
| RMF — **자동재생 금지** | iframe src 에 `autoplay` 를 넣지 않는다 | `VideoEmbed` |
| RMF — **오버레이 금지** | 플레이어 위에 아무것도 얹지 않는다. 배지도 버튼도 없다 | `VideoEmbed` |
| III.G.1.c — 플레이어 **위·안** 광고 금지 | 광고를 플레이어와 세 블록 떨어진 자리에 둔다 | `/videos/[id]` |
| III.G.1.d — **독립적 가치** 요건 | 회차를 못 붙이는 영상에는 **광고 슬롯 자체를 그리지 않는다** | `/videos/[id]` |

**유튜브 로고를 직접 그리지 않는다.** 로고는 상표이고 브랜드 가이드라인이 색·여백·변형을 규정한다. 정책이 요구하는 것은 로고가 아니라 "YouTube 가 출처임이 보는 사람에게 분명할 것" 이므로, 재생 표시 + 'YouTube' 라는 낱말 + youtube.com 링크로 만족시킨다.

### ⚠ 제목을 고치지 않는다

**금지 표현이 화면에 남았다면 프론트가 제목을 손볼 일이 아니라 수집 필터를 고칠 일이다**([[forbidden-expressions]] 외부 텍스트 절). 영상 제목 변조는 YouTube 정책 위반이라, 우리 정책을 지키려고 남의 제목을 바꾸면 **두 정책을 동시에 어긴다.**

CSS `-webkit-line-clamp` 로 줄 수를 제한하는 말줄임은 된다 — 낱말을 지우는 것이 아니다.

상세 페이지의 `h1` 에는 **남이 쓴 문장**이 들어간다. 그래서 바로 아래에 출처를 밝히고, `<title>`·`description` 은 **우리가 짓는다**("제1238회 로또 당첨번호 영상"). 걸러지지 않은 표현이 검색 결과에 우리 사이트 이름과 나란히 뜨는 것은 다른 문제다.

### ⚠ `shorts_hint` 를 boolean 으로 다루지 않는다

쇼츠를 판별하는 공식 API 필드가 없어 재생시간·게시일로 **추정**한 값이다. `unknown` 을 `일반` 이나 `쇼츠` 어느 한쪽으로 밀지 않고 **`전체` 에서만** 보인다 — 모르는 것을 한쪽으로 밀면 그 순간 추정이 확정이 된다. 필터를 켜면 그 사실을 문구로 알린다.

카드에 쇼츠 배지를 달지 않고, 쇼츠라고 썸네일 비율을 바꾸지도 않는다. 추정으로 레이아웃을 바꾸면 틀렸을 때 화면이 망가진다.

### ⚠ 회차는 `game` 을 함께 봐야 붙는다

회차 번호만 보고 이으면 **연금복권 330회 영상에 로또 330회 당첨번호가 붙는다** — 에러 없이 조용히 틀린 번호가 뜬다. `game === 'lotto' && round !== null` 일 때만 붙인다. 이 판정 하나가 화면의 절반과 **광고 노출**을 가른다.

붙일 수 없으면 당첨번호·당첨금·번호구성·다른영상 블록을 생략하고 `noindex` 로 둔다 — 임베드 하나만 남은 페이지는 고유 본문이 없다.

### 그 밖

### 쇼츠는 세로로 띄운다 (2026-08-31)

세로 영상을 16:9 틀에 넣으면 좌우가 새까맣고 영상이 아주 작아진다. `shorts_hint === 'likely'` 면 **9:16** 으로 띄운다.

- ⚠ **`unknown` 은 가로로 둔다.** 모르는 것을 세로로 밀면 그 순간 추정이 확정이 된다(계약의 `shorts_hint` 규칙과 같은 정신). 가로가 안전한 기본값이다 — 세로 영상이 가로 틀에 들어가면 작아질 뿐이지만, 가로 영상이 세로 틀에 들어가면 **훨씬 더** 작아진다.
- ⚠ **폭과 높이를 함께 묶는다.** 9:16 은 폭 1,120 이면 높이가 1,990 이라 스크롤로도 한 화면에 안 들어온다. `max-width: min(100%, 420px)` + `max-height: 78vh`. 실측 1280px 뷰포트에서 395×702.
- ⚠ **전환 버튼을 둔다.** 계약이 "3분 이하 가로 영상이 쇼츠로 오분류된다" 고 명시했다([[youtube-data-api]]). 그때 영상이 세로 틀에 갇혀 아주 작게 나오는데, 사용자가 바꿀 방법이 없으면 그대로 봐야 한다. 버튼은 **플레이어 바깥**이다 — 위에 얹으면 RMF 의 오버레이 금지를 어긴다.
- 문구가 "쇼츠/일반" 이 아니라 **"세로/가로"** 인 것은, 우리가 아는 것이 화면비뿐이기 때문이다. 이 버튼은 쇼츠인지를 확정하지 않는다.

- **홈·목록에서는 재생하지 않는다.** 썸네일만 걸고 전용 페이지로 보낸다. iframe 스무 개가 한 화면에 뜨면 느려지고, 독립적 가치 판단을 홈까지 끌고 들어오게 된다.
- **썸네일은 핫링크한다.** `next/image` 를 쓰지 않는다 — 그것은 이미지를 우리 서버로 가져와 캐시하므로, 워커의 "썸네일 이미지 파일을 저장하지 않는다" 는 경계를 프론트가 우회하는 꼴이 된다([[component-boundaries]]).
- **`aspect-ratio` 로 높이를 예약한다.** 외부 이미지와 iframe 은 도착 시각이 불확정이라 예약하지 않으면 그대로 CLS 다.
- **갈래 필터는 링크다.** 버튼 + JS 로 만들면 JS 를 끈 사용자가 쓸 수 없고 검색엔진이 각 갈래를 따라가지 못한다.
- **캐시를 24시간 넘게 두지 않는다.** `REVALIDATE.video` 는 6시간이다. 이것은 취향이 아니라 정책 상한 — `lotto_video` 의 행은 30일 안에 갱신되거나 삭제되므로 오래 캐시하면 워커가 지운 영상을 계속 내보내게 된다.
- **개별 영상 URL 을 사이트맵에 싣지 않는다.** 30일 안에 사라지는 URL 을 색인시키면 404 가 쌓인다. 목록(`/videos`)만 싣는다.

### 계약이 정한 프론트 규칙 여섯

| 규칙 | 지키는 방법 |
|---|---|
| `robots: noindex, nofollow` | `admin/layout.tsx` 의 `metadata`. ⚠ **하위에서 `metadata` 를 새로 export 하면 덮인다** — `logs/page.tsx` 가 `metadata` 를 두지 않는 이유다 |

### 로그인 — 아이디 · 비밀번호 · OTP 세 칸 (2026-08-31 계약 변경)

종전에는 64자 랜덤 토큰 한 칸이었다. **아이디·비밀번호'만' 으로 바꾸면 종전보다 약해지므로** 백엔드가 OTP(TOTP)를 2단계로 함께 받는다([[api-contract]]).

| 칸 | 속성 | 이유 |
|---|---|---|
| 아이디 | `autoComplete="username"` | 비밀번호 관리자가 아이디·비밀번호를 **한 쌍으로 묶어야** 저장된다. 끄면 저장이 안 되어 사람이 더 약한 비밀번호를 쓴다 |
| 비밀번호 | `type="password"` · `autoComplete="current-password"` | 어깨너머로 보이지 않게, 브라우저가 평문으로 기억하지 않게 |
| OTP | `type="text"` · `inputMode="numeric"` · `autoComplete="one-time-code"` · `maxLength=6` | ⚠ **`type="number"` 를 쓰지 않는다** — 스피너가 붙고 앞자리 0 이 사라지며 모바일에서 스크롤로 값이 바뀐다. `one-time-code` 라야 iOS·안드로이드가 붙여넣기를 제안한다 |

- **입력값에서 숫자만 남긴다**(`replace(/\D/g, '')`). 인증 앱에서 복사하면 공백이 딸려 오는 일이 잦다.
- ⚠ **실패 이유를 나누어 말하지 않는다.** 아이디·비밀번호·OTP 중 무엇이 틀렸는지 알려 주면 **아이디가 맞는지부터 알려 주는 셈**이다. 401 과 422 도 같은 문구로 답한다. 백엔드가 네 경우를 같은 401 로 답하는 것과 같은 이유다.
- 실패하면 **OTP 칸만 비운다.** 30초마다 바뀌므로 어차피 다시 입력해야 하고, 아이디·비밀번호까지 지우면 매번 다 치게 된다.
- 429(너무 잦은 시도)와 503(설정 안 됨)만 구분한다 — **정상 사용자가 원인을 모르면 계속 두드린다.**

### ⚠ 중계 프록시가 `X-Forwarded-Proto` 를 붙인다

백엔드는 세션 쿠키에 `Secure` 를 붙일지 정해야 하는데, **프론트가 중계하기 때문에** 백엔드에 닿는 요청은 내부망 평문 HTTP 다 — 사용자가 HTTPS 를 써도 백엔드는 알 방법이 없어 **`Secure` 가 영영 안 붙는다**(2026-08-31 백엔드 정정). 화면은 멀쩡히 동작해 증상이 없는 종류의 사고다.

그래서 중계가 브라우저의 실제 스킴을 전달한다.

- 앞단 프록시가 이미 붙였으면 **그 값을 존중**하고, 없을 때만 우리가 아는 스킴(`request.nextUrl.protocol`)을 쓴다.
- ⚠ **스킴을 지어내지 않는다.** `x-forwarded-proto` 는 클라이언트가 위조할 수 있으므로, 우리가 만들어 넣는 값은 **이 서버가 아는 사실**뿐이다.

> **교훈**: 중계 계층이 있으면 "서버가 아는 사실" 의 범위가 줄어든다. 백엔드가 스킴으로 판단하겠다고 한 2026-08-28 결정이 이 구조에서 틀렸던 이유다.
| 사이트맵 제외 | `sitemap.ts` 가 화이트리스트라 자동 제외. 실수로 넣지 않는다 |
| **`robots.txt` 에 `Disallow` 를 넣지 않는다** | 크롤을 막으면 크롤러가 `noindex` 를 **읽지 못해** URL 만 색인될 수 있다. 막는 것과 숨기는 것은 다르다([[crawling-defense]]) |
| 광고 없음 | `AdSlot` 을 두지 않는다 |
| **면책·가이드 문구 없음** | 아래 라우트 그룹 |
| 링크 없음 | 헤더·푸터 어디에도. 주소를 아는 사람만 들어온다 |

### ⚠ 공개 셸을 라우트 그룹으로 갈랐다

헤더·푸터를 루트 레이아웃에 두면 **푸터의 면책 문구가 운영자 화면까지 따라온다**(실측으로 확인하고 옮겼다). 그래서 공개 화면을 `app/(site)/` 로 내리고 그 레이아웃이 헤더·본문·푸터·구조화 데이터를 맡는다.

- 라우트 그룹은 **URL 에 나타나지 않는다.** `/lotto` 는 그대로다 — 주소를 하나도 바꾸지 않았다.
- ⚠ **새 공개 페이지는 반드시 `(site)/` 안에** 만든다. 밖에 두면 헤더·푸터 없이 뜬다.
- ⚠ `robots.ts` · `sitemap.ts` · `icon.svg` 는 **루트에 남는다.** URL 규약이 고정돼 있어 그룹 안으로 들어가면 경로가 깨진다.
- ⚠ `not-found.tsx` 는 루트에 있어 셸 **바깥**이다(어느 그룹에도 매칭되지 않는 주소로 들어오므로). 그래서 **헤더·푸터를 그 파일이 직접 그린다.** 셸을 고치면 두 곳을 함께 봐야 한다.
- `admin/layout.tsx` 는 셸이 없으므로 `<main id="main">` 을 직접 둔다 — 없으면 axe `landmark-one-main` 이 걸린다.

### ⚠ 브라우저가 백엔드를 직접 부르지 않는다 — 중계한다

관리자 인증은 **쿠키**다(`httpOnly` · `SameSite=Lax`). 브라우저가 백엔드를 직접 부르면 프론트와 백엔드가 다른 출처라

1. `SameSite=Lax` 쿠키가 크로스 사이트 XHR 에 붙지 않는다 — 로그인은 되는데 다음 요청부터 401 이 되고 원인이 화면에 드러나지 않는다.
2. 붙이려면 `SameSite=None; Secure` + CORS `allow_credentials` 가 필요한데, 그건 관리자 쿠키를 아무 사이트에서나 실어 보낼 수 있게 여는 일이다.

그래서 `app/api/admin/[...path]/route.ts` 가 중계한다. 브라우저는 같은 출처로만 말하고 **백엔드 주소가 노출되지 않는다.**

- **프론트는 `ADMIN_TOKEN` 을 모른다.** 토큰은 로그인 본문으로 지나갈 뿐 저장하지도 로그에 남기지도 않는다. 인증의 주체는 백엔드다 — 두 곳이 각자 인증하면 규칙이 갈라진다.
- **계약에 있는 경로만 통과시킨다**(`login`·`logout`·`job-logs`). 임의 경로를 넘기는 열린 프록시를 만들지 않는다.
- ⚠ **204·304 에 본문을 실으면 안 된다.** 빈 문자열이라도 넣으면 `Response` 생성자가 던져 프록시가 500 을 낸다 — 로그아웃이 실제로 그렇게 깨졌다.
- ⚠ `Set-Cookie` 는 `getSetCookie()` 로 읽는다. `get()` 은 여러 개를 쉼표로 이어 붙여 **만료 날짜 안의 쉼표와 구분되지 않는다.**
- 이 경로는 **캐시하지 않는다**(`force-dynamic` · `no-store`). 운영자 응답이 캐시되면 다른 요청이 남의 세션 결과를 볼 수 있다.

### 화면 규칙

- **실패가 눈에 띄어야 한다.** 이 화면의 목적이 "무엇이 잘못됐는지 나중에 고치는 것" 이다. 실패가 있는 요약 카드는 테두리째 바뀌고, **실패한 실행은 처음부터 펼쳐 둔다** — 실패를 찾으러 온 화면에서 한 번 더 누르게 하지 않는다.
- **`stat` 의 키를 하드코딩하지 않는다.** 잡마다 다르고 앞으로 늘어난다. 받은 키를 그대로 순회해야 워커가 단계를 추가해도 화면이 따라간다(계약).
- `stat`·`logs` 는 **`null` 일 수 있다**(2026-08-28 이전 실행). 빈 상자를 남기지 않고 "남은 상세 기록이 없습니다" 라고 말한다.
- **마지막 성공 시각을 따로 낸다.** '마지막 실행' 만 보면 계속 실패 중인 잡이 정상으로 읽힌다. 한 번도 성공한 적 없으면 붉게 표시한다.
- 페이징은 **커서**(`next_before_id`)다. 잡 이력은 끊임없이 쌓여 `OFFSET` 이면 경계에서 같은 행이 두 번 보이거나 빠진다.
- 시각은 **문자열에서 잘라 쓴다.** 로케일 함수를 쓰면 서버와 브라우저의 시간대가 달라 hydration 이 어긋난다. 응답이 KST 로 온다.
- 오류 전문은 `white-space: pre` + 가로 스크롤. 강제로 접으면 스택트레이스가 어디서 끊겼는지 알 수 없다.

## AI 번호추천 — 메인 시뮬레이터

`components/simulator/*`, `lib/simulator-steps.ts`. 2026-08-28 신설(시안 `docs/raw/추천알고리즘설명화면.png`).

### ⚠ 두 갈래를 탭으로 나란히 둔다 (2026-08-31 개편)

처음에는 위아래로 쌓고 **"메인 / 서브 시뮬레이터"** 라고 이름 붙였다. 두 가지가 잘못됐다(사용자 지적).

1. **아래 것이 묻힌다.** 위 도구를 쓰고 나면 스크롤을 더 내릴 이유가 없어, 다른 방식이 있다는 것을 모른다.
2. **'메인 / 서브' 는 우리 사정이다.** 사용자가 알고 싶은 것은 어느 쪽이 주력인지가 아니라 **무엇이 다른가**다.

그래서 **이름이 차이를 말하게** 바꾸고 탭으로 나란히 놓았다.

| 탭 | 배지 | 무엇이 다른가 |
|---|---|---|
| **AI 번호추천** | `7단계 분석` | 네 가지 분석을 종합하고 가상 추첨까지 돌린다. 15초쯤 걸린다 |
| **기준별 추천** | `바로 추천` | 여섯 기준 중 하나만 보고 곧바로 뽑는다 |

탭 라벨이 이름을, 배지가 **고르는 데 필요한 사실**(걸리는 시간)을, 탭 아래 한 줄이 차이를 말한다. 그래서 `AiRecommender` 안에서는 제목·설명을 **걷어냈다** — 같은 말을 두 번 하면 화면만 길어진다.

### ⚠ 탭의 접근성

WAI-ARIA 탭 패턴을 지킨다. `role="tablist"` · `role="tab"`(+`aria-selected`·`aria-controls`) · `role="tabpanel"`(+`aria-labelledby`·`tabIndex={0}`).

- **좌우 화살표로 탭을 옮긴다.** 탭은 Tab 키로 하나씩 도는 것이 아니라 화살표로 고르고 Tab 으로 패널에 들어가는 것이 표준이다. 그래서 선택되지 않은 탭은 `tabIndex={-1}`(로빙 tabindex)이고, 끝에서 반대편으로 감는다.
- 선택 상태를 **색만으로 알리지 않는다.** 테두리 굵기와 글자 굵기가 함께 바뀐다.
- ⚠ **숨긴 패널도 DOM 에 남긴다.** `hidden` 으로 감출 뿐 언마운트하지 않는다 — 언마운트하면 탭을 오갈 때마다 그 안의 추천 결과가 사라져, 두 방식을 **견주어 보려는 사용자**가 매번 다시 뽑아야 한다.
- ⚠ 각 방식의 **설명 본문은 탭 밖(페이지 하단)에 서버 렌더링**한다. 탭 안은 도구이고, 검색엔진이 읽어야 하는 글을 탭에 숨기지 않는다([[metadata-strategy]]).

### 일곱 단계 — 말투는 시안을 따른다

시안이 "지난 20년간 당첨번호를 공책에 적어 온 판매점 사장님" 이라는 비유로 알고리즘을 풀었다. **그 말투를 지킨다** — 통계 용어를 그대로 던지면 대부분의 사용자에게 아무 뜻도 전달되지 않는다. 그렇다고 **없는 능력을 말하지 않는다**: 각 단계는 "무엇을 세는가" 를 말할 뿐 그 결과가 다음 추첨을 맞힌다고 하지 않는다([[forbidden-expressions]]).

⚠ 단계 문구·설명·수치 추출은 **`lib/simulator-steps.ts` 한 곳**에 있다. 팝업과 페이지 본문이 같은 배열을 읽으므로 두 곳이 갈라지지 않는다.

### ⚠ 연출이지 거짓말이 아니다

| 지키는 것 | 이유 |
|---|---|
| 단계마다 최소 2.2초 | **읽을 시간**을 준다. 사용자 요구가 "2초 이상" |
| 수치는 **응답의 실제 값**만 | 지어낸 수치를 띄우는 순간 정보형 대시보드가 아니라 연출이 된다 |
| 계산 못 한 단계는 **수치 없이 설명만** | 계약이 `null` 을 주고 화면은 "수치를 함께 보여드리지 못했습니다" 로 넘어간다. **0 으로 채우지 않는다** |
| 응답이 먼저 와도 **건너뛰지 않는다** | 어떤 실행은 일곱 단계, 어떤 실행은 두 단계가 보이면 사용자는 무엇이 달랐는지 모른다 |
| 응답이 늦으면 **마지막 단계에서 기다린다** | 없는 결과를 먼저 보여줄 수 없다 |

실측: 총 **16초**(7단계 × 2.2초 + 여유).

### ⚠ 타이머 effect 에 콜백을 의존성으로 넣지 않는다

호출부의 `onFinished` 는 렌더마다 새 함수일 수 있고, 그러면 effect 가 매 렌더 재실행되어 **타이머가 설정되자마자 취소된다** — 실제로 단계가 2에서 멈췄다(실측). `useRef` 에 담아 최신 값을 읽되 effect 는 다시 돌지 않게 한다.

같은 이유로 `onCancel` 도 `useCallback` 으로 안정화한다. 인라인이면 `useModalBehavior` 의 effect 가 매번 재실행되어 **포커스가 첫 요소로 되돌아간다.**

### 팝업 규칙

- **배경 클릭으로 닫히지 않는다.** 도는 중에 실수로 닫으면 처음부터 다시 해야 한다. `Esc` 는 남긴다 — 키보드 사용자가 갇히면 안 된다.
- 설명 팝업은 진행 대화상자 **위에** 뜬다. 포커스 트랩이 둘 겹치는데, 실측으로 axe 위반 0 을 확인했다.
- 진행 상황은 `aria-live="polite"` 로 읽어 준다. 화면을 보지 않는 사용자에게도 단계가 넘어가는 것이 들려야 한다.
- 상태를 **색만으로 알리지 않는다.** 지난 단계는 체크 표시, 현재 단계는 굵기와 배경이 함께 바뀐다.
- `.sim-slot` 으로 **광고 자리의 높이를 미리 잡아 둔다.** 나중에 채울 때 대화상자 높이가 바뀌지 않게 하려는 것이다(사용자 계획).
- `.sim-now` 에 `min-height` 를 둔다. 단계마다 문구 길이가 달라 높이가 출렁이면 읽기 어렵다.

### 단계 설명은 페이지 본문에도 둔다

팝업 안에만 있으면 **검색엔진이 읽지 못하고**, 이 설명이 이 페이지의 고유 본문이다([[metadata-strategy]]). `sim-outline` 이 같은 배열을 서버 렌더링한다.

### 문구 — '조합' 대신 '추천'

세는 자리에서 '조합' 은 낯설게 읽힌다("5조합"). 화면 전체에서 **`추천 N개`** 로 쓴다(사용자 지시). 카드 제목도 "n번째 조합" 이 아니라 **"추천 n"** 이다. 공유 문구·이미지 파일명·전체 내보내기 라벨까지 함께 바꿨다 — 한 곳만 남으면 그 화면만 다른 말을 쓴다.

### 백엔드가 없어도 돈다

계약의 `POST /api/lotto/simulate` 가 `404` 면 기존 API 를 조합해 같은 화면을 채운다(`simulateFallback`). ⚠ 그 폴백에서도 **수치를 지어내지 않는다** — 패턴 비율과 몬테카를로 실행 횟수는 백엔드만 아는 값이라 `null` 로 두고 설명만 보여준다. 사용자가 고른 `trials` 를 실제 실행 횟수처럼 적지 않는다.

### 2026-09-17 재설계 — "무엇을 돌리는지가 모양으로 보이게"

사용자 지적: 설정 화면이 "뭔지 모르겠고 재미없고, 누가 봐도 랜덤하게 뽑는 것 같다", 설명이 "절차를 정리한 문서 같다", 6가지 추천의 선택이 "난잡하다", "시뮬레이션을 한다는 느낌이 없다". 위 절의 일부(칩 열 개·접이식 설명·세로 단계 목록)는 이 개편으로 대체됐다. 스타일은 `styles/recommend.css`.

### 2026-09-17 (2차) — 5만·10만 번도 뽑는 장면이 보이게

사용자 지적: "1만 번은 번호 고르는 게 보이는데 5만·10만 번은 휘리릭 지나간다". 원인은 서버 계산 시간 — 응답이 늦으면 단계가 빈 번호판으로 먼저 흘러가고 마지막 단계에서 기다렸다.

- **응답 전에는 '추첨 준비' 에서 기다린다**(단계 번호 없음, 끝을 모르는 진행 막대). 이 동안 번호판에서 번호 여섯이 **하나씩 뽑혔다 비워지는** 연출과 여섯 칸 슬롯이 돈다.
- 응답이 오면 일곱 단계를 **실제 수치로** 재생한다. 단계 시간은 균등하지 않다 — 일반 520ms, **가상 추첨 1,900ms**(뽑기 연출 + 실제 횟수까지 오르는 카운터), 마지막 900ms(응답의 **추천 1 번호**를 진하게 켠다).
- 응답은 왔는데 수치가 없으면(요청 실패) 단계를 돌리지 않고 곧바로 닫는다 — 빈 번호판으로 "분석했다" 고 보이지 않게.
- 뽑기 칸(`data-pick`)은 옅은 칸 + 테두리, 결과 칸(`data-lit`)은 진한 칸이다. 연출과 결과가 모양으로 갈린다.

R12 는 **"모바일에서는 가로 스크롤을 쓰지 않고 세로로 쌓는다"** 고 정했다. 근거는 "40대+ 사용자에게 옆으로 숨은 카드는 발견성이 낮다" 였다. **2026-08-31 에 사용자가 카드 슬라이드 방식을 명시적으로 요청**해 뒤집는다.

발견성 문제는 그대로 남으므로 **신호 셋으로 막는다** — `ScrollArea` 에서 쓴 규칙과 같다.

1. **다음 카드가 반쯤 보이게** 폭을 잡는다(모바일 86%). 잘린 것이 보이는 것이 가장 강한 신호다. 100% 면 옆에 더 있다는 것을 모른다 — 그것이 R12 가 걱정한 바로 그 문제다.
2. **좌우 화살표.** 단, 좁은 화면에서는 감춘다 — 손가락으로 미는 것이 주된 조작이고 화살표가 카드를 가리면서 얻는 것이 없다.
3. **위치 점.** 몇 장 중 몇 번째인지 알리고, 눌러서 이동도 된다.

### 그 밖

- `scroll-snap-type: x **proximity**`. `mandatory` 는 손을 떼는 즉시 가장 가까운 카드로 끌어당겨 **살짝 밀어 엿보는 동작을 막는다.**
- ⚠ 컨테이너에 `tabIndex={0}` 을 주지 **않는다.** 카드 안에 링크·버튼이 있어 키보드로 이미 닿는다 — 주면 포커스가 빈 상자에 한 번 더 멈춘다(`ScrollArea` 와 다른 점이다).
- ⚠ 점은 8px 이지만 **누르는 자리는 24px** 이다. 점 크기대로 두면 손가락으로 못 누른다(WCAG 2.2 target-size).
- 현재 위치를 **색과 길이로 함께** 알린다(활성 점은 20px 로 늘어난다). 색만으로는 구별하지 못하는 사용자가 있다.
- **영상 카드가 너무 커지던 문제도 여기서 풀렸다.** 격자(`minmax(260px, 1fr)`)는 화면이 넓어질수록 카드가 함께 커져 영상 하나가 화면을 다 먹었다. 슬라이더는 카드 폭이 고정이다.
- `RecommendCarousel` 의 자체 캐러셀 로직을 걷어내고 이것으로 통일했다. **같은 일을 두 벌 두면 한쪽만 고쳐진다** — 실제로 "끝에 닿아도 화살표가 남던" 문제가 그렇게 생겼다.

## MobileTabBar — 모바일 하단 바로가기

`components/MobileTabBar.tsx`. 홈 · 통계 · AI추천 · 꿈해몽 넷.

- **네 개만 둔다.** 다 넣으면 햄버거와 같아지고 좁은 화면에서 라벨이 뭉개진다. 전체 메뉴는 여전히 헤더 햄버거에 있다.

- ⚠ **본문 아래 여백을 만든다**(`body { padding-bottom }`). 고정 바가 마지막 내용을 가리면 그것을 영영 못 본다.

- ⚠ 아이콘만 두지 않는다. **글자를 함께** 둔다 — 아이콘만으로 뜻이 전해지는 경우는 드물다.
- 현재 위치는 `aria-current="page"` + 색 + 굵기. 홈(`/`)만 **정확히 일치**로 판정한다 — `startsWith` 면 모든 주소가 홈으로 잡힌다.
- ⚠ 여기에 **`backdrop-filter` 를 쓰지 않는다.** 아래 헤더 함정과 같은 이유다.

## ⚠ `backdrop-filter` 는 `position: fixed` 를 가둔다

2026-08-31 에 **모바일 햄버거가 깨진 원인**이다. 드로어가 전체 화면이 아니라 **헤더 높이(60px) 안에** 갇혀 머리만 보이고 메뉴 목록이 잘렸다(실측 320×60).

`.site-header` 에 `backdrop-filter: blur(8px)` 이 있는데, 그 속성은 **`position: fixed` 의 컨테이닝 블록을 만든다**(`transform` · `filter` · `will-change` · `contain` 도 같다). 헤더 안에서 `position: fixed; inset-block: 0` 을 줘도 화면이 아니라 헤더가 기준이 된다.

**해결: 포털로 `document.body` 에 그린다.** 헤더의 blur 는 디자인이고, 여기서 고칠 문제는 "떠 있는 것이 어디에 붙는가" 다. 검색 오버레이도 같은 함정을 안고 있어 함께 옮겼다.

### ⚠ 포털과 `useModalBehavior` 를 함께 쓸 때

**훅을 포털 *안쪽* 컴포넌트에서 부른다.** 포털이 첫 렌더에 `null` 을 돌려주면 그 시점 `ref.current` 가 비어 있고, 훅의 effect 는 `if (!node) return` 으로 아무것도 하지 않고 끝난다. 의존성이 그대로라 마운트 뒤에도 **다시 돌지 않아 Esc · 포커스 트랩 · 배경 스크롤 잠금이 조용히 전부 죽는다.**

포털로 옮기면서 실제로 그렇게 깨뜨렸고, **열리기는 열리므로 axe 도 잡지 못했다.** 검증에서 "드로어가 뜬다" 만 보면 통과한다 — 모달 동작(스크롤 잠금·Esc·포커스 복원)을 따로 재야 한다.

푸터의 링크 목록은 **사람용 사이트맵 역할**을 한다 — `/sitemap.xml` 링크를 걷어낼 때 그 근거로 삼았다([[crawling-defense]]). 그래서 접되 **DOM 에는 남긴다.** 검색엔진도 `details` 안을 읽는다.

### 구현

- `<details>` + `<summary>` 다. **JS 를 쓰지 않으므로 푸터는 서버 컴포넌트 그대로**다.
- ⚠ **데스크톱에서는 접지 않는다.** `summary` 를 `display: contents` 로 두고 `ul` 에 `display: block` 을 줘 UA 스타일시트를 덮는다. `open` 속성을 JS 로 조작하지 않는 것은 그러면 서버 렌더와 어긋나기 때문이다.
- ⚠ **`summary` 를 `display: none` 으로 지우면 제목(`h2`)도 사라진다.** 제목이 그 안에 있다. `contents` 로 상자만 없앤다.
- ⚠ `contents` 를 쓰면 **자식이 그대로 흐른다.** 개수 배지·갈매기를 데스크톱에서 따로 숨기지 않으면 제목 옆에 그대로 붙는다.
- 펼친 목록은 **2열**이다. 전체 폭을 쓰므로 라벨이 깨지지 않는다.

갈매기 선 하나로는 **눌러도 되는 것인지, 눌러서 무엇이 나오는지** 알 수 없다는 지적을 받았다. 셋을 함께 낸다 — 꿈해몽의 접이식에서 쓴 것과 같은 문법이다.

|---|---|
| 제목 | 무엇의 묶음인가 |
| **개수 배지**(7·5·4) | 안에 몇 개가 있는가 — 눌러 볼 값어치를 가늠하게 한다 |
| **동그란 갈매기** | 눌리는 것임을 알린다. 선 하나는 장식으로 읽히지만 테두리가 있으면 버튼으로 읽힌다 |

⚠ **갈매기는 마크업의 SVG 다.** CSS 그러데이션 두 장을 겹쳐 그렸더니 선이 교차해 **`×` 가 됐다**(실측). 모양을 정확히 그려야 하는 것은 CSS 트릭으로 흉내 내지 않는다 — `Disclosure`·`Faq` 도 같은 이유로 SVG 를 쓴다.

### 간격은 구분선이 맡는다

그룹 사이 여백을 **0 으로** 두고 `border-top` 으로 나눈다. 간격으로만 나누면 좁힐수록 한 덩어리로 뭉치는데, 선이 경계를 맡으면 붙여도 각 항목이 분리돼 보인다. `summary` 높이도 44 → 40px 로 줄였다(터치 타겟은 넉넉하다).

**543 → 489px.** 데스크톱은 325px 그대로.

### 그 밖

⚠ **없는 토큰을 쓰면 그 속성이 0 이 된다.** `margin-top: var(--space-10)` 이라고 적었는데 `--space-10` 은 정의되어 있지 않고, `var()` 가 무효가 되면 **앞선 값으로 폴백하지 않고 초깃값**이 된다(실측 `margin-top: 0`). 정의된 간격 토큰은 **4·8·12·16·20·24·32·48·64** 뿐이다.

**내 번호 분석 카드**(`MyNumbersCard`) — **실제 로또 용지의 수동 칸을 본뜬 번호판**이다(사용자 요청). 한 줄에 일곱 칸(1~7 · 8~14 …), 번호마다 인쇄된 동그라미, 고르면 연필로 칠한 듯한 타원이 찍힌다. 여섯 개를 고르면 `/lotto/analyze?numbers=…`('샀다면?' 화면)로 보낸다. 무작위로 채우기는 **입력 도우미**이지 추천이 아니다(추천은 `/lotto/recommend` 의 일). 계산은 하지 않고 주소만 만든다.

⚠ **막대는 세 목록이 같은 자**(가장 많이 나온 횟수)를 쓴다. 목록마다 제 최댓값으로 그리면 0번과 6번이 같은 길이가 되어 두 목록을 나란히 둔 뜻이 사라진다. 미출현 목록만 세는 것이 기간이라 그 안에서 따로 그린다.
⚠ **번호판은 넷째 카드를 눌러야 열린다**(2026-09-18 2차 요청). 늘 펼쳐 두면 순위를 보러 온 사람에게 45칸이 먼저 막아선다. 카드가 곧 여는 버튼(`aria-expanded`)이고, 다른 통계 화면의 카드는 `/lotto/stat#mynum` 으로 보내 도착하자마자 열리게 한다. '무작위로 채우기' 는 **누를 때마다 여섯을 새로 뽑는다** — 남겨 두고 채우면 다시 눌러도 그대로라 "안 눌렸나?" 가 된다.
⚠ 목록은 **모든 화면에서 한 줄**이고 머리글(순위·번호·출현·비교·최근 출현·추세)을 둔다. 좁은 화면에서 막대를 둘째 줄로 내렸더니 한 항목이 두 줄이 되어 화면을 가득 메웠고 추세 배지만 떠 보였다(사용자 지적). 막대는 **고정 폭**(56/78/110px)이다 — 견주는 그림이지 길이 자체가 값이 아니다.
⚠ **횟수가 막대보다 먼저다**(사용자 요청). 사람이 먼저 찾는 것은 숫자이고 막대는 그것을 견주는 그림이다. 칸마다 **폭을 고정**해 줄마다 세로선이 맞는다 — `auto` 로 두면 "7번 35%" 와 "0번 0%" 의 시작점이 흔들린다.
⚠ 목록 안의 추세 배지는 **기호만** 남기고 말은 감춘다(낭독기에는 남는다). 두 목록을 나란히 두면 카드가 520px 안팎이라 말까지 달면 막대가 90px 로 눌린다. 뜻은 목록 바로 아래 범례가 글자로 설명한다.
⚠ 용지는 **공식 용지 흉내가 아니다.** 동행복권 상표·로고를 쓰지 않고 머리글에 '행운상자 · 연습용' 을 적는다. 375px 에서 칸이 38px 이라 `::after` 로 보이지 않는 3px 여백을 둘러 터치 타겟 44px 을 만든다.
⚠ 빈도·패턴 화면도 같은 4카드를 쓴다. 그 화면에는 번호판이 없으므로 넷째 카드는 `/lotto/stat#mynum-title` 로 건너뛴다.
⚠ 걷어낸 CSS: `.stat-card*`(옛 3카드) · `.stat-table-rank`·`.stat-table-overdue`·`.trend-legend`(옛 표) · `.stat-blocks`.
⚠ 조회 바(`StatQueryBar`)·도움말(`HelpTip`)·번호 하나 보기(`NumberInspector`)는 **기존 부품 그대로** 쓴다 — 같은 일을 하는 부품이 두 벌이 되면 한쪽만 고쳐진다.



### 2026-09-18 (3차) — 결과로 데려가기 · 6가지 추천도 뽑는 과정을 보여 준다

- **결과가 나오면 그 자리로 화면을 옮긴다**(`lib/scroll-to.ts`). 버튼은 위에 있고 결과는 아래에 그려져, 팝업이 닫혀도 사용자는 설정 화면을 보고 있었다. 정밀 분석·6가지 추천·꿈해몽 셋 다 적용했고, 목표 요소에 `scroll-margin-top` 을 줘 sticky 헤더에 가리지 않게 했다(실측 top=0 → 80). 움직임을 줄인 사용자에게는 부드러운 스크롤을 쓰지 않는다.
- **6가지 추천에 뽑기 연출**(`simulator/DrawRunner`, 세 걸음 × 0.7초). 종전의 1초짜리 알림(`RecommendProgress`)은 걷어냈다. 번호판이 무작위로 깜빡이다가 **마지막에 응답의 첫 조합이 진짜로 켜진다** — 연출 칸(`data-pick`)과 결과 칸(`data-lit`)은 모양이 다르다. 정밀 분석(일곱 단계 × 5초)과 구분되게 짧게 두고, 없는 분석을 지어내지 않는다.

## 꿈해몽 점집 풍 개편 (2026-09-18)

사용자 요청: "조금 더 세련되고 꿈을 분석해 주는 것 같은 풍으로… 마치 점집에 들어온 것 같은", "꿈해몽하는 것과 같은 팝업으로 과정이 보여지고 결과가 나왔으면".

- **머리(`.dream-hero`)**: 밤하늘 그라디언트 + 달 + 깜빡이는 별. "간밤의 꿈, 무슨 뜻일까요?"
- **입력 카드(`.dream-desk`)**: 공용 `Card` 대신 이 화면 전용 바탕. 버튼은 "꿈 풀이 보기".
- **풀이 팝업(`DreamReading`)**: 세 걸음(꿈 이야기를 듣는다 → 해몽 자료를 펼친다 → 얽힌 번호를 센다) + 적어 준 꿈을 되읊는 인용 + **번호가 하나씩 놓이는** 연출. 끝나면 결과로 스크롤.
- ⚠ **사진을 쓰지 않았다.** 무료 이미지라도 출처·이용 범위 판단이 필요하고(법적 판단은 사용자 몫) 무게도 늘어난다. 밤하늘·달·별은 CSS 로 그렸다.
- ⚠ 분위기는 점집이되 **문구는 사실에 머문다** — '좋은 꿈 · 대박 · 당첨' 을 쓰지 않는다. 마지막에 드러나는 여섯 개는 **응답의 첫 조합**이고 지어낸 값이 아니다.
- ⚠ 팝업은 **새 꿈을 풀 때만** 뜬다. 개수 변경·번호 제외는 같은 꿈을 계속 보는 중이라 장면을 다시 띄우지 않는다.
- ⚠ 첫 요청은 모델 로드로 20초가 걸릴 수 있다. 마지막 걸음에서 기다리며 "조금 더 걸리고 있습니다" 를 덧붙인다 — 멈춘 것이 아니라는 신호가 없으면 떠난다.

사용자 지적: "세련되고 요즘 트렌드에 맞게. 썸네일도 이상하다. 60초 같은 건 필요 없다. 흥미를 끌어서 게임을 하게끔".
