# Wiki Schema — 행운상자

이 파일은 이 위키의 **설정 파일**이다. 위키에 들어오는 모든 세션은 다른 무엇보다 **이 파일을 먼저 읽는다.** 여기 적힌 규약이 `llm-wiki` 스킬의 기본값을 덮어쓴다.

이 스키마는 사용자와 함께 진화한다. 반복되는 패턴이 여기 없으면 추가를 제안하고, 맞지 않게 된 규약은 쳐낸다.

---

## 이 위키의 성격

일반적인 LLM Wiki 는 **외부 자료(논문·기사)를 축적**하는 연구 노트다. 이 위키는 다르다. **하나의 소프트웨어 프로젝트를 세 개의 독립된 Claude Code 세션이 병렬 개발하기 위한 공유 지식체계**다.

이 차이가 두 가지 규약 변경을 낳는다.

1. **`sources/` 디렉토리가 없다.** 이 위키의 1차 출처는 외부 문서가 아니라 **이 저장소의 코드와 `docs/raw/` 의 기획 문서**다. 각 페이지는 `sources:` frontmatter 에 코드 경로(`backend/app/prediction/ensemble.py:16`) 또는 raw 문서(`raw:작업지시초안.md#8.3`)를 적어 추적 가능성을 유지한다.
2. **`10-contracts/` 는 다른 페이지와 지위가 다르다.** 계약 페이지는 서술이 아니라 **구속력 있는 명세**다. 아래 "계약의 특별 지위" 절 참조.

## 위치

| 항목 | 경로 |
|------|------|
| 위키 루트 | `docs/wiki/` |
| 1차 출처 (기획·시안) | `docs/raw/` — **읽기 전용. 수정 금지** |
| 1차 출처 (코드) | `worker/` `backend/` `frontend/` |
| 색인 | `docs/wiki/index.md` |
| 변경 로그 | `docs/wiki/log.md` |

> 작업지시서(`docs/raw/작업지시서초안_보완.md` 4.1)는 색인 파일명을 `INDEX.md` 로 적었으나, `llm-wiki` 번들 스크립트가 `index.md` 를 기대하므로 소문자를 쓴다.

## 페이지 타입과 디렉토리

| `type` | 디렉토리 | 담는 것 |
|--------|---------|--------|
| `decision` | `00-decisions/` | ADR. **되돌리면 안 되는 결정과 그 이유.** 파일명 `NNNN-slug.md` |
| `contract` | `10-contracts/` | 세션 간 구속력 있는 명세 (DB 스키마, API, 잡, 환경변수) |
| `design` | `20-design/` | 디자인 토큰, 반응형 규약, 컴포넌트 사양, 접근성 |
| `seo` | `30-seo/` | 메타데이터, 구조화 데이터, 애널리틱스, 애드센스, 검색엔진 등록 |
| `domain` | `40-domain/` | 로또 도메인 지식, 알고리즘 명세, 금지 표현 |
| `ops` | `50-ops/` | 로컬 셋업, 마이그레이션, 배포 |
| `external` | `90-external/` | 외부 의존성의 사실관계 (네이버 API, 차단 이력, 상표) |
| `synthesis` | `99-synthesis/` | 질의 결과를 되먹인 분석. **아직 없음** — 첫 질의 때 생성 |

새 타입이 필요하면 여기에 먼저 추가하고 페이지를 만든다.

## Frontmatter

모든 페이지에 필수:

```yaml
---
type: decision | contract | design | seo | domain | ops | external | synthesis
title: "사람이 읽는 제목"
description: "한 줄 요약. index.md 와 검색에 쓰인다"
tags: [contract, db]
owner: shared | worker | backend | frontend
status: draft | stable | deprecated
sources: ["backend/app/models.py", "raw:작업지시서초안_보완.md#8.1"]
created: 2026-07-09
updated: 2026-07-09
---
```

`type`, `title`, `tags`, `created`, `updated` 는 `wiki_lint.py` 기본 필수 필드다. 여기에 `description`, `owner`, `status`, `sources` 를 더한다.

- **`owner`** — 이 페이지를 고칠 책임이 있는 세션. `shared` 는 오케스트레이터(루트 세션)만 고친다. **자기 `owner` 가 아닌 페이지를 고치지 않는다.** 고쳐야 한다면 `log.md` 에 남기고 사용자에게 알린다.
- **`status`** — `draft` 는 아직 신뢰할 수 없다는 뜻. `stable` 이어야 세션이 근거로 삼는다. `deprecated` 는 삭제하지 않고 남기되 대체 페이지를 링크한다.
- **`sources`** — 이 페이지의 주장이 어디서 왔는지. 코드는 `경로:줄번호`, raw 문서는 `raw:파일명#절` 형식. **출처 없는 주장을 쓰지 않는다.**

## 태그 분류 체계

작게 유지한다. 태그가 200개인 위키는 태그가 없는 위키다.

| 태그 | 뜻 |
|------|-----|
| `contract` | 세션 간 구속력 있는 명세 |
| `decision` | 되돌리려면 사용자 확인이 필요한 결정 |
| `db` | Postgres 스키마·권한 |
| `api` | REST 계약 |
| `job` | 워커 배치·스케줄 |
| `design` | 디자인 토큰·레이아웃 |
| `a11y` | 웹 접근성 |
| `seo` | 검색엔진 최적화 |
| `analytics` | GA4·네이버 애널리틱스 |
| `adsense` | 애드센스 정책 |
| `algorithm` | 예측·꿈해몽 알고리즘 |
| `policy` | 서비스 포지셔닝·금지 표현 |
| `security` | 시크릿·인증·권한 |
| `ops` | 로컬 셋업·배포·운영 절차 |
| `migration` | 데이터 이관 |
| `external` | 외부 서비스 의존 |
| `tbd` | 미결정. 결정되면 태그를 뗀다 |
| `pitfall` | 알려진 함정. 밟으면 시간을 크게 잃는 것 |

`tbd` 와 `pitfall` 은 다른 태그와 함께 쓴다.

## 계약의 특별 지위

`10-contracts/` 는 위키의 나머지와 근본적으로 다르다.

> **일반 페이지**: 코드와 위키가 어긋나면 **위키가 틀린 것**이다. 위키를 고친다.
> **계약 페이지**: 계약과 코드가 어긋나면 **코드가 틀린 것**이다. 코드를 고친다.

계약을 바꾸려면:

1. 세 세션 전부에 미치는 영향을 먼저 조사한다.
2. 사용자 승인을 받는다.
3. 계약 페이지를 고치고 `log.md` 에 기록한다.
4. 영향받는 세션에 알린다.

계약을 **말없이 바꾸지 않는다.** 계약이 흔들리면 세 세션이 동시에 재작업한다.

## 페이지 크기

- 소프트 캡: **400줄**. 넘으면 분할을 검토한다.
- 하드 캡: **800줄**. 반드시 분할한다.
- 원자성: 한 페이지는 한 주제. "## 변형" 아래 실질적 산문이 다섯 절 붙었다면 그것들은 각자의 페이지다.

## 위키링크

본문 상호참조는 `[[페이지-슬러그]]`. 슬러그는 디렉토리 접두어와 `.md` 를 뺀 파일명이다 (`[[db-schema]]`, `[[0003-worker-writes-backend-reads]]`).

모든 페이지는 인바운드 링크가 최소 하나 있어야 한다. 없으면 고아 페이지이고 lint 가 잡는다.

역링크 찾기: `grep -rl "\[\[슬러그\]\]" docs/wiki/`

## 그래프 레이어

**사용하지 않는다.** `docs/wiki/graph/` 와 `ontology.yaml` 이 없으므로 이 위키는 pre-graph 상태다. 그래프 관련 스크립트를 돌리지 않는다.

근거: 그래프 레이어는 `founded`, `proposed` 같은 서술적 관계를 가진 연구 위키에 맞는다. 이 위키의 관계는 대부분 "이 세션이 이 테이블을 소유한다" 처럼 계약 페이지 본문이 이미 명시하는 것이라, 타입드 엣지를 따로 유지하면 이득 없이 유지보수만 늘어난다.

나중에 페이지가 100개를 넘고 "이 계약을 바꾸면 무엇이 깨지는가" 를 기계적으로 묻고 싶어지면 그때 도입한다.

## 색인 구조

현재 **평면**: `docs/wiki/index.md` 하나가 전체 페이지를 나열한다.

페이지가 ~150개를 넘거나 `index.md` 가 300줄을 넘으면 `docs/wiki/indexes/<카테고리>.md` 로 샤딩하고 이 절을 갱신한다.

## 워크플로 커스터마이즈

`llm-wiki` 스킬의 기본 워크플로(ingest / query / lint)를 이 프로젝트에 맞게 조정한다.

**ingest** — 이 위키에는 외부 소스가 거의 들어오지 않는다. 대신 다음이 ingest 에 해당한다.
- 새 기능·확장을 설계할 때 → `00-decisions/` 에 ADR 을 **먼저** 쓰고 개발한다.
- 외부 API·정책을 조사했을 때 → `90-external/` 에 사실을 기록한다.
- 코드에서 발견한 함정 → 해당 페이지에 `pitfall` 태그와 함께 추가한다.

**query** — 세션이 "이걸 어떻게 하지?" 를 물을 때. `index.md` → 후보 페이지 → 필요하면 역링크. 위키에 답이 없으면 **지어내지 않고** 없다고 말한 뒤 페이지를 새로 만든다.

**lint** — 아래 cadence 참조.

## 사용자 선호

- **모든 페이지는 한국어로 쓴다.** 코드 식별자·SQL·명령어는 원문 유지.
- 표는 열거 가능한 짧은 사실에만 쓴다. 설명은 산문으로.
- 결정 페이지(ADR)는 **"왜"** 가 본문의 절반 이상을 차지해야 한다. 무엇을 결정했는지는 한 줄이면 족하다. 6개월 뒤에 이 결정을 뒤집으려는 사람을 설득하거나 납득시키는 것이 ADR 의 목적이다.
- 함정(`pitfall`)은 **증상 → 원인 → 해법** 순으로 쓴다. 증상이 먼저다. 사람은 증상을 보고 검색한다.

## Lint cadence

```bash
python3 ~/.claude/skills/llm-wiki/scripts/wiki_lint.py docs/wiki/ \
  --required-fm type,title,tags,created,updated
python3 ~/.claude/skills/llm-wiki/scripts/wiki_stats.py docs/wiki/
```

- 구조 lint: 페이지를 5개 추가할 때마다.
- 의미 lint(모순·중복·누락): 각 Phase 종료 시.
- 계약 정합성 검사(계약 ↔ 코드): 각 세션의 완료 기준 검증 시 **필수**.
