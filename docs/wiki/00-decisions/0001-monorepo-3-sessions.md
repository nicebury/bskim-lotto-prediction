# ADR 0001 — 모노레포 유지, 3개 세션으로 분리

## 결정

한 저장소 안에 `worker/` `backend/` `frontend/` 를 두고, Claude Code 세션을 각 디렉토리에서 열어 격리한다. 저장소를 셋으로 쪼개지 않는다.

## 맥락

기존 저장소는 `backend/`(FastAPI 모노리식) + `frontend/`(Vite CSR) 구조다. 신규 서비스는 워커를 독립시키고 프론트를 Next.js 로 재작성해야 한다. 세 컴포넌트를 세 개의 Claude Code 세션이 병렬로 개발한다.

## 왜 모노레포인가

**계약이 한 커밋에서 검증되기 때문이다.** 이것이 결정적인 이유다.

세 세션은 [[db-schema|DB 스키마]]와 [[api-contract|API 계약]]으로 연결된다. 스키마에 컬럼 하나가 추가되면 백엔드 응답이 바뀌고, 그러면 프론트의 타입이 바뀐다. 저장소가 셋이면 이 변경이 세 개의 PR 로 쪼개진다. 세 PR 이 각각 언제 머지되는지 아무도 통제하지 못하고, 그 사이 기간에 저장소들은 서로 거짓말을 한다. 어느 순간의 `main` 세 개를 체크아웃해도 함께 동작한다는 보장이 없다.

한 저장소면 계약 변경과 세 컴포넌트의 대응이 한 커밋에 담긴다. `git bisect` 가 의미를 갖는다.

**두 번째 이유는 위키다.** [LLM Wiki](../SCHEMA.md)는 세 세션이 공유하는 지식체계다. 저장소가 셋이면 위키는 네 번째 저장소가 되거나 서브모듈로 세 번 복제된다. 서브모듈은 커밋 포인터를 갱신해야 하고, 사람은 그것을 잊는다. 세 세션이 서로 다른 버전의 계약을 읽는 순간 이 설계 전체가 무너진다.

**세 번째는 배포다.** 각 디렉토리가 `pyproject.toml` / `package.json` / `env.sample` 을 갖춰 그대로 하나의 컨테이너 이미지가 된다. `deploy/docker-compose.yml` 이 셋을 조립한다. 저장소가 셋이면 조립 지점을 어디에 둘지가 또 하나의 문제가 된다.

## 세션 격리는 어떻게

**cwd 로 한다.** Claude Code 를 `worker/` 에서 열면 그 디렉토리의 `CLAUDE.md` 가 적용된다. 루트 `CLAUDE.md` 는 상위에서 함께 로드되므로 전 세션 공통 규칙만 담는다.

각 세션 `CLAUDE.md` 는 "자기 디렉토리 밖의 코드를 수정하지 않는다" 를 명시한다. 강제 장치는 아니다 — 규율이다. 대신 진짜 강제가 필요한 곳(백엔드의 DB 쓰기)에는 [[0003-worker-writes-backend-reads|권한]]을 쓴다.

## 기각한 대안

**3개 별도 Git 저장소.** 위의 세 이유로 기각. 물리적 격리는 확실하지만, 이 프로젝트의 병목은 "실수로 남의 코드를 고치는 것" 이 아니라 "계약이 어긋나는 것" 이다. 별도 저장소는 후자를 악화시킨다.

**모노레포 + git worktree.** 세션마다 worktree 를 파서 브랜치를 격리한다. 동시 편집 충돌은 줄지만, 계약이나 위키가 바뀔 때마다 세 worktree 를 리베이스해야 한다. 이 프로젝트는 세 세션이 같은 파일을 동시에 만질 일이 거의 없다 — 디렉토리가 이미 나뉘어 있다. 얻는 것 없이 머지 부담만 는다.

## 결과

- 루트 `CLAUDE.md` 는 40줄 이내로 유지한다. 매 턴 세 세션 모두에 주입되기 때문이다.
- 계약 변경은 [스키마의 "계약의 특별 지위"](../SCHEMA.md#계약의-특별-지위) 절차를 따른다.
- `work_order/` 는 과거 작업지시서 아카이브로 남기고 수정하지 않는다.

## 되돌리려면

컴포넌트 중 하나가 별도 팀·별도 릴리스 주기를 갖게 되면 그때 분리를 재검토한다. 그전까지는 분리 비용이 이득보다 크다.
