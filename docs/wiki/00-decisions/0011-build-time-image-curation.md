# 상세페이지 이미지는 빌드타임에 큐레이션한다

## 결정

가이드 등 상세페이지에 들어가는 이미지(Pexels 실사 또는 AI 생성 일러스트)는 **개발/빌드 시점에 사람이 골라 `frontend/public/` 에 내려받아 커밋**한다. 런타임에 브라우저나 서버 컴포넌트가 Pexels API 를 호출하지 않는다. 워커도 이미지를 수집하지 않는다.

## 왜 런타임 호출이 아닌가

런타임에 Pexels API 를 부르는 방식이 언뜻 "자동" 이라 매력적으로 보인다. 그러나 이 사이트의 구조와 충돌한다.

**키가 새거나, 안 새면 못 쓴다.** 이미지를 클라이언트에서 부르려면 키가 브라우저 번들에 들어가야 하는데, 그러면 `PEXELS_API_KEY` 가 공개된다([[env-vars]] 의 `NEXT_PUBLIC_` 규칙 위반). 서버 컴포넌트에서만 부르면 키는 지키지만, 상세페이지는 대부분 SSG/ISR 이라 매 요청 호출이 무의미하고 쿼터를 태운다.

**레이아웃이 흔들린다.** 외부에서 실시간으로 받은 이미지는 크기·도착 시각이 불확정이라 CLS 를 만든다. 이 프로젝트는 CLS < 0.1 을 완료 기준으로 못박았고([[responsive-rules]]), 뉴스 썸네일도 같은 이유로 외부 이미지를 포기했다([[naver-search-api]]).

**저작권을 자동화할 수 없다.** 사용자는 "이 사이트에 써도 되는 이미지인지 반드시 확인" 을 요구했고, 그 판단은 사람 몫이다([[pexels-image-usage]]). 런타임에 무엇이 뜰지 모르는 채로는 이 확인을 할 수 없다. 빌드타임 큐레이션은 **커밋 전에 사람이 최종 검수**하는 지점을 자연스럽게 만든다.

## 왜 워커가 수집하지 않는가

워커가 이미지를 긁어 저장하고 백엔드가 내려주는 방식도 가능하다. 하지만 워커의 경계는 "외부 데이터를 Postgres 에 쓴다" 이고, 이미지 파일 스토리지는 그 경계 밖이다. 무엇보다 이 프로젝트는 **뉴스 썸네일 스크래핑을 이미 하지 않기로 결정**했다([[naver-search-api]], log 2026-07-10) — 이미지 수집 파이프라인을 새로 들이는 것은 그 결정과 상충하고, 정적 삽화 몇 장을 위해 과설계다.

## 결과

- `frontend/public/` 아래 정적 파일. `next/image` 미사용(현행 `unoptimized`)과 정합.
- 이미지가 하나도 없어도 화면은 완성 상태로 동작한다 — 삽화는 장식이고, 대체 텍스트/레이아웃이 먼저다(요청이미지정보.md 의 원칙 계승).
