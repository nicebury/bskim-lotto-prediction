# ADR 0003 — 워커가 쓰고, 백엔드는 읽기만 한다

## 결정

Postgres 에 로그인 롤을 둘 만든다. 워커는 `app_writer` 로 접속하고 Alembic 마이그레이션을 소유한다. 백엔드는 `app_reader` 로 접속하며 `SELECT` 만 가능하다.

## 맥락

세 세션이 병렬로 개발한다. 세션들은 서로의 코드를 읽지 않는다. 유일한 접점은 [[db-schema|DB 스키마]]다.

## 왜 권한으로 막는가

**규율은 잊히고 권한은 잊히지 않기 때문이다.**

백엔드 세션의 `CLAUDE.md` 에 "DB 에 쓰지 마라" 라고 적을 수 있다. 대부분의 턴에서 지켜질 것이다. 그러나 언젠가 "조회 카운트를 기록하면 편할 텐데" 같은 합리적인 이유가 생기고, 그때 규칙은 협상 가능한 것이 된다. 한 번 백엔드가 쓰기 시작하면 스키마의 소유자가 둘이 되고, 두 세션이 서로 모르는 채 같은 테이블을 마이그레이션한다.

`GRANT SELECT` 만 받은 롤은 협상하지 않는다. `INSERT` 는 `permission denied` 로 즉시 실패한다. 개발 중에, 코드 리뷰 전에, 배포 전에.

**두 번째 이유는 계약의 명료함이다.** "워커가 쓴다" 가 한 문장으로 참이면, 데이터가 언제 어떻게 들어오는지 물을 곳이 하나뿐이다. 백엔드도 쓸 수 있다면 어떤 행이 어디서 왔는지 추적하는 데 두 곳을 봐야 한다.

**세 번째는 시크릿 분리다.** 롤이 둘이면 비밀번호도 둘이다. 백엔드 컨테이너에는 쓰기 비밀번호가 아예 존재하지 않는다. 백엔드가 침해되어도 데이터를 지울 수 없다. `.env` 를 컴포넌트별로 나누는 [[env-vars]] 결정과 같은 뿌리다.

## 기각한 대안

**워커 → 백엔드 내부 API 로 POST.** 백엔드가 DB 단일 소유자가 되고 결합도는 낮아 보인다. 그러나 배치가 성공하려면 백엔드가 항상 떠 있어야 한다. 1,231회차 시드 적재를 HTTP 로 하면 느리고, 실패 지점이 늘고, 트랜잭션 경계가 애매해진다. 무엇보다 백엔드에 쓰기 엔드포인트가 생기면 그것을 인증해야 하고, 로그인 없이 운영한다는 전제와 충돌한다.

**둘 다 read/write.** 단순하다. 그러나 위의 세 이유를 전부 잃는다.

## 결과

- Alembic 은 `worker/migrations/` 에만 존재한다. 백엔드에 마이그레이션 도구를 설치하지 않는다.
- 백엔드는 절대 `403 permission denied` 를 사용자에게 흘리지 않는다. 그것이 보이면 권한 설정이 잘못된 것이다 ([[api-contract]]).
- **`ALTER DEFAULT PRIVILEGES` 를 빠뜨리면 새 테이블마다 백엔드가 깨진다.** 이 함정은 [[db-schema]] 에 자세히 적었다.
- 백엔드 세션은 자기 롤로 쓰기를 시도하는 테스트를 하나 갖는다. 권한 분리가 실제로 작동하는지 검증한다.

## 백엔드에 쓰기 요구가 생기면 ★

이 질문은 반드시 다시 나온다. **답은 "워커에게 HTTP 로 던진다" 가 아니다.**

워커는 쓰기 서비스가 아니라 **배치 잡 러너**다. 잡 레지스트리·크론·잡별 락·외부 소스 크롤러를 갖고 있고, 사용자 요청을 동기적으로 처리하도록 만들어지지 않았다. 백엔드가 워커를 호출하기 시작하면 넷이 동시에 무너진다. 워커가 사용자 요청 경로에 올라오고, 1 프로세스여야 하는 컴포넌트가 병목이 되고, 백엔드가 `WORKER_JOB_KEY` 를 갖게 되며([[0004-manual-trigger-on-worker]] 가 없애려던 뒷문이다), 백엔드가 워커의 존재를 알게 되어 세션 격리가 깨진다.

**권한은 컴포넌트가 아니라 데이터 소유권을 따라 나눈다.** 백엔드가 읽기 전용인 것은 "백엔드라서" 가 아니라 **"워커가 소유한 테이블에 대해서"** 다. 백엔드가 자기 데이터를 갖게 되면 그 데이터에는 당연히 쓸 수 있어야 한다.

| 상황 | 올바른 구조 |
|------|------------|
| 워커 소유 테이블에 써야 함 | **그럴 일이 없다.** 있다면 그건 수집이고, 워커의 잡이다 |
| 백엔드 고유 데이터가 생김 | `app_user` 롤 + 자기 스키마. **프록시 아님** |
| 백엔드가 워커에게 작업 지시 | Postgres outbox 테이블. **HTTP 호출 아님** |
| 운영자가 수동 수집 | 워커의 `/internal/jobs/*` 를 SSH 터널로 직접 |

```sql
CREATE ROLE app_user LOGIN PASSWORD :user_pw;
CREATE SCHEMA user_data AUTHORIZATION app_user;           -- 백엔드가 소유
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_user;  -- 워커 테이블은 읽기만
```

백엔드가 워커에게 일을 시켜야 한다면(예: "이 회차를 다시 가져와라") outbox 테이블을 쓴다. 백엔드가 자기 소유 테이블에 한 행을 넣고, 워커가 자기 주기에 읽어 처리한다. 두 컴포넌트는 여전히 서로를 모르고, 접점은 계약된 스키마 하나이며, 워커는 루프백에 남는다.

**그 전에 물어야 할 것**: 정말 서버에 써야 하는 데이터인가? 초안 9·17장은 이 서비스가 로그인 없이 운영되고, 사용자 정보를 서버에 저장하지 않으며, 추천 이력을 개인 단위로 남기지 않는다고 못 박았다. 저장한 번호와 최근 본 회차는 localStorage, 조회수와 체류시간은 [[analytics|GA4·네이버 애널리틱스]], 문의는 외부 폼이나 메일이다 — DB 에 넣는 순간 개인정보를 저장하게 되어 개인정보처리방침이 무거워진다.

**읽기 전용 롤은 자의적 제약이 아니라 그 설계 결정의 귀결이다.** 지금 백엔드에는 쓰기 요구가 하나도 없다.

## 배포 형태와의 관계

권한 분리가 침해 시나리오까지 막으려면 **backend 컨테이너에 `app_writer` 자격증명이 존재하지 않아야** 한다. 따라서 worker 와 backend 는 같은 호스트에 있더라도 **별개 컨테이너**로 배포한다 ([[deployment]]).

한 컨테이너에 합치면 `app_reader` 는 SQL 인젝션과 코딩 실수를 여전히 막지만 — 커넥션의 롤은 프로세스 위치와 무관하므로 — 컨테이너가 침해되면 옆에 있는 쓰기 비밀번호로 새 커넥션을 열 수 있다. 그때 남는 이득은 이 ADR 의 첫 번째 논거("규율은 잊히고 권한은 잊히지 않는다")뿐이다. 그것도 여전히 값지지만, 합치는 것은 결정 사항이므로 조용히 하지 않는다.

## 되돌리려면

되돌리지 않는다. 확장한다 — 위의 `app_user` 경로로.
