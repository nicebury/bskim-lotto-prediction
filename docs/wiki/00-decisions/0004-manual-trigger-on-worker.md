# ADR 0004 — 수동 트리거는 워커에 두고 외부에 노출하지 않는다

## 결정

워커가 자체 FastAPI 서버를 `127.0.0.1` 에 띄우고 `POST /internal/jobs/{job_name}/run` 을 제공한다. `X-Job-Key` 헤더로 인증한다. nginx 에 노출하지 않는다. 관리자 UI 를 만들지 않는다.

## 맥락

요구사항은 "관리자 기능까진 아직 고려 안 하고 있고, 특정 키를 붙여서 웹서버를 호출하면 수동 동작하게" 였다. 잡은 둘이고(`lotto`, `news`) 스케줄이 다르며, 각각 독립적으로 부를 수 있어야 한다.

## 왜 백엔드가 아니라 워커인가

**공격 표면 때문이다.**

백엔드에 `/api/admin/jobs/{job}/run` 을 두면 편하다. 이미 공개된 웹서버이니 어디서든 `curl` 로 부를 수 있다. 바로 그 점이 문제다. 인터넷 전체가 그 엔드포인트를 스캔한다. 키 하나가 유일한 방어선이 되고, 그 키는 백엔드 `.env` 에 있어야 하며, 백엔드는 [[0003-worker-writes-backend-reads|읽기 전용이어야 할]] 컴포넌트다. 읽기 전용 컴포넌트가 쓰기 작업을 촉발하는 키를 갖는 것은 그 결정을 우회하는 뒷문이다.

워커의 엔드포인트를 루프백에 묶으면 인터넷에서 도달할 수 없다. 키는 두 번째 방어선이 된다. 첫 번째는 네트워크다.

**두 번째 이유는 경계다.** 백엔드가 트리거를 프록시하면 백엔드가 워커의 존재를 알아야 한다. 주소, 키, 잡 이름을. 그 순간 두 컴포넌트가 결합되고, [[api-contract|API 계약]]에 워커 개념이 새어 들어온다. 지금은 백엔드가 워커를 전혀 모른다. 이 무지가 자산이다.

## 왜 관리자 UI 를 만들지 않는가

요구된 것은 트리거이지 화면이 아니다. 화면을 만들면 인증이 필요하고, 인증은 세션과 CSRF 와 비밀번호 재설정을 부른다. 이 서비스는 로그인 없이 운영한다(초안 9장). 관리자 로그인 하나를 위해 그 전제를 깨는 것은 비용이 크다.

원격 실행이 필요하면 SSH 터널이면 충분하다. 운영자는 한 명이다.

```bash
ssh -L 8003:127.0.0.1:8003 user@server
curl -X POST -H "X-Job-Key: $KEY" http://127.0.0.1:8003/internal/jobs/lotto/run
```

## 기각한 대안

**CLI 전용** (`docker compose run worker job lotto`). 가장 안전하고 가장 단순하다. 그러나 서버에 접속하지 않고는 실행할 수 없어 "웹서버를 호출하면 수동 동작" 이라는 요구를 충족하지 못한다. HTTP 엔드포인트는 SSH 터널 위에서도 동작하고, 나중에 내부망 대시보드가 생기면 그대로 쓰인다.

**백엔드의 관리 엔드포인트.** 위의 두 이유로 기각.

## 세부 결정

**상수 시간 비교.** `secrets.compare_digest` 를 쓴다. `==` 는 첫 불일치 바이트에서 반환하므로 타이밍으로 키를 추측할 수 있다. 네트워크 지터에 묻힐 만큼 작은 차이지만 방어 비용이 한 줄이다.

**빈 키로 기동 거부.** `WORKER_JOB_KEY` 가 비어 있으면 워커가 시작을 거부한다. 빈 문자열끼리 비교하면 통과하기 때문이다. 이 검사가 없으면 `.env` 를 채우지 않은 배포가 조용히 무인증 상태로 뜬다.

**`202` 이지 `200` 이 아니다.** 수집은 수십 초 걸린다. 요청을 붙들지 않고 `run_id` 를 돌려준다.

**잡별 독립 락.** 로또 수집이 뉴스 수집을 막지 않는다. 자세한 내용은 [[worker-jobs]].

## 되돌리려면

운영자가 여럿이 되거나 잡이 열 개를 넘으면 관리 화면이 필요해질 수 있다. 그때는 내부망 전용으로 만들고, 공개 웹서버에는 여전히 노출하지 않는다.
